# The catalogue and editing pairs (`common/catalog.py`, `ui/catalog_editor.py`, `ui/pair_editor.py`, `ui/flags_editor.py`, `ui/remote_picker.py`, `ui/tk_renombrar.py`)

Formerly AGENTS.md «The catalogue», «Editing pairs from the UI», «The remote folder picker», «The flags editor». Writing the TOML itself: `engine.md`. The fleet registry beside the catalogue: `fleet.md`.

## The catalogue

`nas:/prdrive-catalog/remote.toml` (formerly `pairs.toml`, see «Two names» below): same schema as `sync_config.toml`, shared by every device, read by the installer when provisioning. **A pair is created or deleted there first**; each device only *chooses* which it uses. Do not collapse that split: the catalogue side (`plan_catalog_save`/`_remove`/`_defaults`) writes the remote and changes nothing local; the device side (`plan_enable`/`_remove`/`_override`/`_revert`) writes `sync_config.toml` and never the remote. `[defaults]` is catalogue-governed too. No pair is sacred.

`sync_config.toml` holds **complete** pair entries, not references (`sync.py` must work with no network). Provenance is **derived**, not stored: `catalog.diff_keys()` compares the local entry against `state/catalog.toml` (the last successful pull) → `catálogo` / `modificada aquí` / `huérfana` / `sin usar`. **Do not add a `from_catalog` key**: `config_file.save()` demands strict round-trip equality and the file is hand-editable.

`catalog.push()` is the riskiest thing in the project: it generates and verifies the text (`config_file.dumps_checked`), **re-reads the remote and refuses if it changed**, copies the file to its `.bak`, and only then uploads. Rewriting keeps the header block and **loses interleaved comments**. It runs the device's rclone (`run()`) unless given another: the installer's keychain step passes `ejecutar=` (its own rclone and ephemeral conf), `donde_pedido=` and `cachear=False`, since the installer's `state/` belongs to no device (`llavero.md`). `catalog.load()` never raises: no network falls back to `state/catalog.toml`, and a cached catalogue is **not editable** (`Catalog.editable`). `catalog.NET_FLAGS` keeps a dead remote from freezing the window.

**`catalog.run(args, apuntar=None)` creates its child exactly like `subprocess.run`**: no session or process group of its own, inherited stdin, `CREATE_NO_WINDOW` on Windows. `sync.py` calls it at the end of every pass (`fleet.publicar()` → `copyto`), and `store.matar_arbol()` only reaches that rclone through the pass's group: a `start_new_session` here would leave it orphaned, holding the volume, when a pass is cut. A **read** is also noted in `store` while it runs (`store.correr_apuntado()`) so that `store.matar_hijos()` can cut it when a window closes: `cat`, `lsjson`, `lsf`, `lsd`, and `copy`/`copyto` whose destination is inside the system temp folder (`catalog.es_lectura()`; how `fleet.leer()` pulls `devices/`). **Writes are never noted**: `copyto` to the remote, `moveto`, `delete`, `deletefile`, `mkdir`, `purge`, and a copy to any other local folder; cutting one halfway leaves the remote worse than letting it finish. A command `es_lectura()` cannot read (flags before the paths, no destination) is not noted. `apuntar=True/False` overrides the choice and nobody passes it, so test stubs of `run` keep taking just `args`. A read that `matar_hijos()` cuts comes back as a failed `CompletedProcess`: the re-read at the start of `push()` fails closed (nothing is written), and so does the first listing of `renombrar()`/`apartar_sobrante()` («no he podido mirar», nothing touched).

The catalogue carries `[keychain]` as an opaque table: `llave_interna` (the key-file-only keychain, `llavero.md`) travels in it and `config_file.dumps_checked` round-trips it, but the catalogue itself neither validates nor enforces it: `model._build_llavero()` validates it when a device's config is read, and `common/cifrada.py` enforces it on the device.

**The pairs screen opens with the local copy and reads the remote in the background (#66).** `open_dialog()` paints `catalog.cached()` (nothing, on a fresh device: only its own pairs) and `leer_catalogo()` hands `catalog.load()` to `segundo_plano`; on arrival it repaints with the remote, keeping the selected row, or keeps the copy and says why.

- What it says and allows is `catalog_editor.lectura(cat, aviso, leyendo)`, pure: the chip in two words («copia local · <fecha>», «catálogo leído · <fecha>», «sin catálogo»), the line under the header (`tk.Indicador`; the long `catalog.load()` warning lives there, not in the chip) and `editable`: **only what was just read from the remote, and never while reading**. So the catalogue buttons and «Releer» stay off until the real answer, and «Examinar…» follows the same answer.
- «Releer» reads the same way. A catalogue change goes up through `working()`, then the screen shows what `push()` left in the copy (still not editable) while it re-reads; device-side plans stay synchronous (local disk). `catalog.SIN_FECHA` is the stamp of a copy without metadata.

**The local copy is two files behind one lock.** `state/catalog.toml` and its metadata `state/catalog.json` (when it was read, from which file, the duplicate mark) are each replaced whole (`store.write_text()`), one after the other. Everything that writes **or reads** them takes `catalog._CERROJO_COPIA`: `_write_cache()`, `apuntar_duplicado()`, `apuntar_renombrado()`, and the readers `cached()`, `duplicado()` and `ultimo_leido()` (the last two through `_metadatos()`). A reader waits for a write in progress (two small files) and gets text and metadata of the same read; a new reader of either file goes through the lock too. The lock is per process, which is enough: only the window and its threads touch the copy (`sync.py`, the service and the agent never do, and the installer pushes with `cachear=False`). What it prevents, measured with the readers outside the lock (Windows 11 on NTFS and Linux on ext4, twelve copies of `tests/test_catalog.py` at once, 10/10/2026):

- On any system, a reader between the two files pairs one read's text with the previous read's date and endpoint.
- On Windows, `os.replace()` is not atomic for whoever looks: while it runs the destination does not exist (seen missing for 1.4 ms, with only the `.tmp` in the folder, inside a replace that took 20 ms on a loaded machine) or refuses to open for longer than the retries last, so `cached()` answered «no copy» and the window painted «sin catálogo» (about one run of the test in twenty); and metadata that could not be opened read as «fecha desconocida» with the factory endpoint.
- On Windows, a reader that has the destination open at that instant makes the replace fail (WinError 5) and `store.write_text()` returns False: between one in ten and one in five writes of the text were lost, and a lost metadata write leaves the new text with the old date until the next read.

`cached()` still retries a few times on `PermissionError` (`_REINTENTOS_COPIA`), for a program outside prdrive that holds the copy open without sharing it (an antivirus scanning it right after it is written); giving up at once would paint «sin catálogo».

**The path names the file, never its folder (#48).** `rclone cat` of a folder does not fail: it concatenates every file inside, recursively (the catalogue, the `.bak`, the `devices/` notes; measured with rclone v1.75.1), and `tomllib` answers "Cannot declare ('defaults',) twice".

- Both readers (`catalog.pull()`, `remote.pull_catalog()`) therefore ask `catalog.explicar_carpeta()`, which runs `lsjson --stat` (and, for a folder, `--stat` of its `remote.toml`, then its `pairs.toml`, to suggest one) **only when something smells**: the content did not parse, or the path does not end in `.toml` (which also catches an empty folder and one holding only the catalogue file, both of which `cat` reads with rc 0). Never on the happy path and never after a failed `cat` (offline, the question would time out too). An unanswerable `--stat` diagnoses nothing.
- What is **typed** is refused without network by `catalog.problema_de_ruta()`: the wizard's Conexión (`profile.from_form`/`from_rclone_conf`; `with_catalog_path` does not raise, it runs per keystroke, and `Profile.problema_catalogo` holds the step shut) and both `[defaults]` forms, only when `catalog_path` **changes** (`validar_ruta_editada()`): an extension-less path already on a device keeps working.

## Two names: `remote.toml` and `pairs.toml`

The file was renamed because it no longer holds only pairs. New remotes are born `remote.toml` (`DEFAULT_CATALOG_PATH`); a remote from before keeps `pairs.toml` until someone renames it. Devices never need to agree on which:

- **Reading** (`catalog.leer()`, shared by `pull()` and `remote.pull_catalog()`): if `catalog_path` names either name, `candidatos()` tries `remote.toml` first and then `pairs.toml` **in the same folder, whichever it names**, moving on when rclone says «not there» (`RC_NO_EXISTE`: `cat` of a missing file exits 3, measured with v1.75.1 on the local backend) **or returns nothing**: on bucket remotes (S3, B2, GCS…) listing a missing prefix is not an error (`backend/s3/s3.go`, without `--s3-directory-markers`), so `cat` of a missing `remote.toml` exits 0 and empty, and treating that as the catalogue would read an un-renamed remote as empty and the next push would create `remote.toml` beside the real one. With nothing anywhere, the first empty read stands (an empty catalogue, as before). Any other failure stops: offline, the second `cat` would time out too. A path with any other name is read as is. `Catalog.endpoint` is the file actually read, and so is `state/catalog.json`'s `endpoint` (`ultimo_leido()`).
  - `remote.toml` first is what makes «if both exist, `remote.toml` wins» true by construction, and it is the cheap order in the end state: after the rename every read is one `cat`, whatever each device's `catalog_path` says. Before it, a device that names `pairs.toml` pays one failed `cat` per read. **No `catalog_path` is ever rewritten**, not even by the rename.
- **Writing** (`push()`): the pre-write re-read uses the same rule, and the write goes to the file it just read, so a rename between reading and pushing lands the change in `remote.toml`. Never create the other name: a device from before only reads `pairs.toml`, and two files split the fleet in two catalogues. A push that wrote `pairs.toml` then stats `remote.toml`: if it appeared meanwhile (the rename raced the upload), the change went to the losing file, and `push()` says so and marks the duplicate.
- **The duplicate mark** (`apuntar_duplicado()`, `duplicado()`): `state/catalog.json` remembers «both names are in the folder» when something that looked saw it (that push, the rename screen, `renombrar()`). A plain read cannot see it (it would cost a round trip per read) but clears it when it falls back to `pairs.toml` because `remote.toml` is missing; `_write_cache()` keeps it for the same folder and drops it for another. «Reparación» shows it (`revision._catalogo_duplicado()`, key `catalogo`) without a button: the fix is a remote operation.
- **Renaming** (`renombrar()`): `lsjson --files-only` of the folder first (`nombres_en()`), because `moveto` overwrites silently; refuse with both names present, or with `remote.toml` already there. Then `moveto` `pairs.toml` → `remote.toml` and, if present, its `.bak` (a failed `.bak` move is reported, not fatal). Content is untouched: no `push()`, no lost comments. `apartar_sobrante()` handles the duplicate: `pairs.toml` → `pairs.toml.apartado-<date>`, never deleted.
- **«Ajustes → Catálogo del remoto»** (`ui/tk_renombrar.py`, decisions in `catalog_editor.renombrado()`/`plan_renombrar()`): offered only while the last read came from `pairs.toml` or a duplicate is marked (`ofrecer_renombrado()`, no network; no read yet → not offered). The screen reads the folder and, only when it is needed to decide, the fleet (`leer_renombrado()`, in the background; its `Sondeo` and `Indicador` come from the panel, `panel.sondeo()`/`panel.indicador()`, so a hidden pane pauses them: `ui.md`). The button enables only if **every other** note carries `remote.toml` in `entiende` (`fleet.ENTIENDE`, see `fleet.md`); this device does not count (its note may predate its own update). It lists the blockers with their version and last seen, and says that a device which never published a note cannot be seen. Confirmation goes through `confirmar_plan()` (`NombrePlan`), the work through `working()`.
- An installer from before reads only `pairs.toml`: the rename plan warns about it.

An optional **`[remote]`** table carries the non-secret definition of the rclone remote (type, host, user…): the first device writes it, the rest inherit it via `profile.align_with_catalog()`. **The catalogue decides the remote's name**: every `remote_path` resolves against `[defaults].remote`, so a differently-named remote would fail every sync with "unknown remote". The key never goes there.

**What `[remote]` never carries or inherits** (`profile.OPCIONES_QUE_EJECUTAN`, `profile.es_secreta()`; the catalogue is writable by anyone with access to the remote and read by every device):
- **Commands** (`ssh`, `bearer_token_command`): rclone would run them on each host. `align_with_catalog()` and `with_catalog_remote()` drop them through one helper (`_opciones_del_catalogo()`), and `align_with_catalog()` says so in a note («Según el catálogo» in the wizard). What the user types in the wizard (`from_form()`) is theirs and does admit them.
- **Secrets** (`es_secreta()`, by name only, values are never inspected: credentials inside a `url` are not detected. A name that is `key`, `pass`, `password` or `2fa`; contains `pass`, `token`, `secret`, `credential`, `_pem`, `sas_url`, `account_key`, `access_grant`, `connection_string`, `cookie`, `authorization` or `headers`; or ends in `_key` / carries `_key_` (`api_key`, `sse_customer_key`, `sse_customer_key_base64`) unless it ends in `_key_id`, which is an identifier such as `access_key_id`): `to_catalog_remote()` leaves them out of the text the wizard offers to save, and the readers ignore them if a hand-edited catalogue has them (with a note). Each device carries its own, those of the connection it was installed with.
- **A profile with its own secret or command is never combined with the catalogue's endpoint.** If the connection the wizard just verified carries any option that is secret or in `OPCIONES_QUE_EJECUTAN`, `align_with_catalog()` keeps the profile's options exactly as they are (the remote *name* is still the catalogue's), and adds a note when the catalogue's filtered `[remote]` describes another connection: its passwords/keys/commands are not handed to a connection that was not checked. Only a profile with none of them adopts the catalogue's filtered `[remote]`. The private key is not an option, so it does not count: a key-based sftp profile (no option secrets) adopts the catalogue's `host` and `user`, and `known_hosts` is what protects that connection. Catalogue values go through `_texto_rclone()` before being compared or written (TOML `true` becomes `"true"`, not Python's `"True"`), so the same value never reads as another connection.
- A `[remote]` that, without the commands it dropped, lacks something rclone requires (`faltan()`, e.g. an sftp that relied on an inherited `ssh` and has no `host`) is not used at all: the profile's options stay and a note says what is missing. The note blames the dropped option only when keeping it would have made the `[remote]` valid.
- `render_conf()` is the last line of defence: it raises `InstallError` for a remote name outside rclone's rule (`NOMBRE_RCLONE`: no `,` `:` `=` quotes `[` `]` or line breaks, no leading `-`, no trailing space; it is `model.NOMBRE_REMOTE` itself, the rule the config loader applies, imported rather than copied), an option name outside `[A-Za-z0-9_]+` or a value with a line break (`rclone.conf` has no escape for it), so a catalogue cannot write extra options into the device's conf. It does not use the stricter `NOMBRE_VALIDO`, which only `from_form()` applies to names typed in the wizard: a remote already in use (`Mi NAS`, `nas@home`) must keep working, and renaming it would shelve every bisync baseline.

## Editing pairs from the UI (`ui/pair_editor.py`): the dangerous part

**The screen (`tk_pairs.open_dialog`, a thin wrapper over `PantallaParejas(parent, compartida).abrir()`).** What the screen knows is attributes of that class (`raw`, `config`, `cat`, `cambiado`, `ventana`…) and each button calls one of its methods; the Tk window is `dlg`. A switch at the top («Qué estás editando»: «Este dispositivo» | «Catálogo», `VISTAS`) decides what the whole screen edits; the catalogue view adds an amber notice and its own `[defaults]` button and action bar. The list is `ListaParejas` (one canvas, `tk_tabla.TablaLienzo`, not a `Treeview`: each row carries a mode chip and a status chip; one list per view); its rows come from `pair_editor.catalog_rows()` (device view, local path as written) or `catalog_only_rows()` (catalogue view, the catalogue's own entries), and `row_status()` decides each row's tone and chip. **The screen is for choosing and acting: it has no fields.** The buttons are enabled by the selected row (`habilitar()`; the pure rule is `pair_editor.botones()`), so tests read their state rather than expect an explanatory message. «Nueva pareja…» opens `formulario()`, the same `EditorPareja` in one column with everything unfolded. The screen `gc.collect()`s on close, and again each time a pair's window closes: Tk variables sit in cycles and must not be freed from a background-read thread.

**A pair's fields are changed in its own window (`VentanaPareja`).** «Modificar…» (one per action bar; the catalogue's is keyed `Modificar… del catálogo`), a double-click on the row, or Intro in the list, call `PantallaParejas.modificar()`, which opens it for the selected pair **and the view of that moment** (`nombre`, `del_catalogo`, fixed for the window's life) and waits. It is modal over the screen (`mostrar()` hands the grab back when a dialog above it closes: `ui.md`), so no other pair is selected and the view does not change while it is open; even so it saves **the pair it shows, never the list's selection** (`guardar()` passes `nombre`). It holds the title, a scope sentence (`ALCANCE_PEN`/`ALCANCE_CATALOGO`), a chip (`HuecoChip`: «Modificada aquí», «Úsala aquí para cambiarla», «Afecta a todos los dispositivos», «Ya no existe»), the `EditorPareja` (two columns, «Avanzado» folded), a note line and two buttons: «Cancelar» («Cerrar» when the fields cannot be changed) and «Guardar aquí…» (`plan_override`) or «Guardar en el catálogo…» (`plan_catalog_save`). Saving goes through `PantallaParejas.plan_de()` and `confirmar_plan()`, shown over the window (`delante()`). **A plan that runs closes the window** (`cerrar_ventana()`, before the screen repaints); one that does not (the confirmation is refused, the plan is rejected, the config changed outside) leaves it open with what was typed. Closing it with unsaved edits asks first (`askokcancel`; the title bar's ✕ too). A pair that cannot be changed opens all the same, read-only: in the device view, one this device does not use (use it first); in the catalogue view, any pair while `lectura().editable` is false. The save button follows `que_cargar()["editable"]`.

**What is typed survives the remote catalogue arriving.** `refrescar()` (the catalogue's arrival and «Releer» end there) calls `VentanaPareja.poner_al_dia()` when a window is open; `cargar()` keeps its `editor.cargar()` arguments (`que_cargar()`) in `base`. With unsaved edits (`hay_cambios()`) the fields are kept **only if the entry being edited is unchanged** (`actual`): a fresh `actual` that differs (another device changed the pair in the catalogue; the config changed on disk) reloads the fields and says so in the window's note, because saving the kept fields would silently revert that change field by field. With nothing unsaved, a change in `CAMPOS_DEL_EDITOR` (the pair, whether it is editable) reloads them, so a catalogue-view window opened while the remote was still being read turns editable when it answers. What only surrounds the fields (the `[defaults]` remote hint, the catalogue entry compared against and its hints, the remote «Examinar…», the chip) goes through `EditorPareja.poner_alrededor()` and `pintar()` without touching them, so the catalogue arriving with the same pairs calls no `editor.cargar()`. If the entry is unchanged but can no longer be saved, the typing is kept and only the save button goes off. A note for the screen's footer also goes to the open window's note (`PantallaParejas.decir()`): with the window in front the footer is hidden, and «sync_config.toml ha cambiado fuera…» is the answer to a «Guardar…» that did nothing. `tests/test_tk_segundo_plano.py` runs it with real threads and a slow catalogue; `tests/test_tk_screens.py` and `tests/test_tk_parejas_vista.py` check the wiring and the in-place rules.

**The screen changes in place (stage 2).** Nothing in it is rebuilt to show one change; `tests/test_tk_parejas_vista.py` checks each point against the same screen drawn from scratch (`tests/_vista.leer_vista` for the widgets, the list's `leer()` and its canvas items for the list).

- **The list is one widget: a canvas** (`ListaParejas` is an adapter over `tk_tabla.TablaLienzo`, `ui.md` «The one-canvas table»). With labels in a grid a row cost nine widgets (casilla, name, path, two chips, their two surface cells, the row's background and a separator) and 50 pairs about 450 system windows that Windows creates, lays out and paints one by one; opening «Parejas» grew with the pairs. Now each row is about ten canvas items and the list is pixel-for-pixel the old one at 100, 125 and 200 % (screenshots on both Tks; the dark theme checked at 100 and 200 %) (every row takes the height of its own tallest cell, as the grid did). Its columns are the casilla (`CeldaCasilla`: it only says, «Usar aquí»/«Quitar…» change it, choosing a row does not), the name, «local ↔ remoto», the mode chip and the status chip; `ListaParejas.fila_tabla()` turns a `CatalogRow` with its `row_status()` into that `FilaTabla`.
- **`ListaParejas.poner()` diffs by name** through the table: a row whose `FilaTabla` is the same touches nothing, a changed one is drawn again (only it), a gone one is deleted, a new one drawn, a new order moves rows. `filas[name]` keeps `fila` (the `CatalogRow`), `tono`, `sup` and `apagada`; `orden`, `elegida`, `elegir(name, avisar)` and `fila()` are as before, and `leer()` returns what is drawn per row: `☑`/`☐`, name, path as shown, mode, status. `poner()` returns whether the list's requested size changed (a row came or went, or a name or a chip wider than the rest of its column changed it), which is what the size guard below uses. `elegir()` recolours only the row it leaves and the row it takes.
- **«Local ↔ remoto» stretches and is cut with «…».** It asks for `ANCHO_RUTA` (240 design px) and takes whatever width the screen has left; a path that does not fit ends in «…» (the pair's window shows it whole), so a long path no longer widens the window. Before the screen is shown the list is drawn at the width it asks for, so `leer()` there may show a shorter cut than once the window is up.
- **Chips are drawn on their row's own fill.** A chip is the pill of the theme's chip style, its disc and its word, painted over the row's rectangle, so what shows through its corners is always the row's colour: normal, selected, amber or red. The 0.7.0 bug (a chip whose parent was the card showed a card-coloured box on a coloured row), fixed in Task 10 with a surface cell per chip, cannot come back; `tests/test_tk_tabla.py` checks the colour under each chip corner in the canvas model and, on X11, on screen.
- **Without a mouse.** Tab gives the list the focus, and the keys show its ring (a 2 px accent ring inside the selected row); ↑/↓, Inicio/Fin and RePág/AvPág choose another row. Intro opens the selected pair's window, as a double-click on its row does (`al_activar`, which is `modificar()`); neither calls `al_elegir` again. A click chooses a row without showing the ring. The list does not scroll the screen to the row the keys chose (neither did the old one). The wheel over the list scrolls the screen.
- **Two lists, one visible.** `dlg.lista` always names the visible one. The catalogue's list, its action bar, its amber notice and «Ajustes del catálogo…» are created the first time «Catálogo» is chosen (`montar_catalogo()`), and switching view is `grid_remove()`/`grid()`: a hidden list is stale by definition and is diffed (`poner()`) when it is shown again, so it needs no mark. Tk's Tab walks a frame's children in stacking order, which is creation order, so pieces made late would come after «Cerrar»: `montar_catalogo()` puts each next to its device-view twin (the list above `lista_d`, with `tk.Misc.lift` because a canvas's own `lift` raises items; the bar above `barra_d`; the notice below the `[defaults]` band), and both views tab from top to bottom: switch, band, list, action bar, «Dispositivos…», «Cerrar» (`tests/test_tk_parejas_vista.py` walks `tk_focusNext`). Tests that read a catalogue button while in the device view read a widget that does not exist yet: switch view first.
- **The rest of `refrescar()` is in place.** The catalogue chip and the `[defaults]` origin chip (and the header chip of an open pair window) are replaced only when their `(text, type, icon)` changes (`HuecoChip.poner()`); labels are configured only when their text differs; the indicator only when its `(line, waiting, tone)` does; `habilitar()` applies `pair_editor.botones(fila, lectura)` (the pure rule) and only touches a button whose state differs.
- **The size guard is logical.** `Visor.crecer()` measures with `update_idletasks()` on the whole window, so `refrescar()` calls it (and `centrar()` only if it grew) just when something may have asked for room: the list says so (`poner()` returned `True`), the view changed, or a text that wraps (indicator line, `[defaults]` line, footer) became another one that is not shorter (`_pide_sitio()`). The catalogue arriving with the same pairs asks for nothing. Chips and the endpoint are not wrapping texts and are not watched: the widest blocks are the `[defaults]` band and the footer (in the catalogue view, the amber notice), so they do not decide the window's width; a very long endpoint does, and the window is already sized for it when it opens.
- **The screen repaints the same way with a pair window open.** `refrescar()` ends by calling `VentanaPareja.poner_al_dia()` (rule above): the window reloads its fields, updates what surrounds them, or touches nothing, and asks its own `Visor` to grow only when it changed something (`crecer()`).
- **«Avanzado» is built when first unfolded, and the pair window grows for it.** `EditorPareja(al_crecer=…)` calls back when it may ask for more room (unfolding «Avanzado», a mode whose amber warning appears); `VentanaPareja` passes its `crecer()`, so the window grows (and re-centres) instead of putting the block behind a scrollbar, up to what the screen allows. `EditorPareja(plegable=True)` has no include/exclude boxes or flags line until «Mostrar»; before that `cargar()` keeps the patterns (`patrones`) and `datos()` returns them exactly as the boxes would (an empty box reads `['']`: Tk ends its text with a newline), so unfolding is not an unsaved change. `formulario()` (`plegable=False`) builds it at once. `modo_cambiado()` only rebuilds the mirror warning when the mode's warning differs.
- **The config is read through `pair_editor.LecturaConfig`**: `leer()` stats `sync_config.toml` (`st_mtime_ns`, `st_size`) on every call and parses only when they changed, returning the same `(raw, config)` objects while it is unchanged; `cambio` says whether the last call found a different file from the previous call. `refrescar()` reads through it, and so do `plan_de()` and `aplicar_plan()`.
- **A hand edit is never overwritten.** `plan_de()` reads first: if the file changed since the screen last showed it, no plan is made, the screen is read again and the footer says `AVISO_CAMBIADO` («sync_config.toml ha cambiado fuera de esta pantalla…»), and so does the note of the pair window the save came from. `aplicar_plan()` checks again **right before `plan.execute()`** of a device plan, comparing by identity with the `raw` the plan was made from (`base`): the confirmation window can stay open for minutes and a refresh in between (the catalogue arriving) would have consumed `cambio`, so identity is what is robust. If it changed, nothing runs. Catalogue plans write the remote, not this file, but still go through the `plan_de()` check since they take `raw`.
- **Baseline and filter states are read once.** `pair_editor.rows(config, estados)` / `catalog_rows(..., estados)` take `{name: (PairState, FiltersState)}` and read only the bisync pairs missing from it (`estados_de()` completes the dict without changing the one it is given); «requiere resync» is computed from the given states (`_pide_resync()`, the rule of `bisync.resync_reasons()`, which a test ties), never by looking at the filters again. At open the first `estados_actuales()` takes them from `compartida.para(config)`, the config just read from disk and not the one the main window passed (a hand edit since then would otherwise show another pair definition's baseline), when there is a valid shared read; after that the dialog keeps its own and reads only what is missing. A new config object, or a device plan executed, drops them and the shared read is not used again (a plan can change `state/` and `filters/` in ways the snapshot's stamps do not see).
- **The state is visible to tests.** `dlg.pantalla` is the `PantallaParejas` itself, so tests read its attributes (`dlg.pantalla.cambiado`, `.vista_puesta`, `.ventana`…). A pair window's `Toplevel` carries `ventana` (the `VentanaPareja`: `.chip`, `.nota`, `.boton_guardar`, `.base`, `.hay_cambios()`) and `editor`. Tests open it by pressing «Modificar…» with `mostrar()` (or `wait_window`) replaced for the length of that window.

`bisync.expected_prefix()` derives from `local`, `remote`, `remote_path`, `mode`. Change any and the expected listing name changes; reusing the old baseline under the new name would tell bisync that a listing of the *previous* destination describes the *new* one, so everything missing from the new side reads as deleted and propagates, with `--max-delete 25` as the only brake. Hence the plan shelves, never renames.

- `bisync.shelve_baseline()` renames `state/<pair>/` → `state/<pair>.old-<date>/`, leaving the pair `fresh` and forcing an explicit `--resync`. Shelved dirs are inert (scans only look at the top level).
- **Renaming a pair is free**: the prefix doesn't depend on the name. `bisync.rename_pair_state()` moves `state/<name>/` and `filters/<name>.*` together (the `.md5` must travel with its file).
- **The decision compares prefixes, not keys.** `_prefixes(raw)` parses the before and after configs and compares `expected_prefix()` per pair; `ENDPOINT_KEYS` only produces the human-readable message. That is what makes `[defaults]` editable: `remote`/`device_remote` feed *every* pair, so `EditPlan.shelve` is a **list**. A prefix that *disappears* (bisync → another mode) also shelves.
- `plan_*()` return an `EditPlan` **without touching anything**; its `consequences` are shown before confirming. `EditPlan.execute()` does the disk surgery **before** writing the config and undoes it if the write fails (it can only fail towards "baseline shelved for nothing", which a `--resync` fixes). **Rename runs before shelve**, else `filters/<old name>.txt` is orphaned.
- `simular_args(raw, name)` is the whole of «Simular»: `[name, "--dry-run"]`. **No `--yes`**: a pair with no baseline must come back "Saltada: requiere --resync", precisely what you want to read before approving anything. The output window is modal and the screen re-`grab_set()`s afterwards.
- `ruta_local_relativa(path)` turns a directory picked with the system dialog into the pair's `local`, relative to `DEVICE_ROOT`, and **refuses** anything outside the device (a `../..` local syncs whatever machine it is plugged into).

## The remote folder picker (`ui/remote_picker.py` + `tk_pairs.explorador_remoto`)

«Examinar…» beside `remote_path`. `listar()` is `rclone lsd` through `catalog.run()`, and `_LINEA` parses its fixed five-field line as a whole regex, not by splitting on spaces: a folder name with spaces must survive intact, and a line that is not a listing must not become a folder. `crear()` is the only thing that writes and it is a `mkdir`. **Deleting remote folders is deliberately not offered**: the remote belongs to the whole fleet and there is no consequences ceremony behind this dialog.

The button is disabled exactly when the catalogue block is (`catalog_editor.lectura().editable`: just read from the remote, not while reading), the proxy for "there is a connection". Listing and `mkdir` go through `working()`: its window is modal, so the path being looked at and its contents cannot contradict each other mid-navigation; the first listing, before the picker shows, hangs off the form that opened it. Each folder is the `Treeview`'s tree column (`#0`) so it can carry the folder icon; nothing expands in place, you enter.

`confirmar_plan()` draws each warning with `pair_editor.partir_aviso()`: the mirror warning is split into title and body like the pairs screen's (`aviso_espejo()`), any other goes whole. The `[defaults]` form (`defaults_form()`) is one column, label above each field and its hint (with «Catálogo: …», ✎ when it differs) below; the include/exclude boxes sit side by side.

## The flags editor (`ui/flags_editor.py`)

Flags are written in TOML syntax (a text box, not a row-per-flag form) and parsed with **`tomllib`, not by hand**: the destination is a `[pair.flags]` table, and `dump()` renders through `config_file.dumps_table()`, so only what the serializer can write back is accepted.

- `RESERVED` (`model.FLAGS_RESERVADOS`) rejects the flags `sync.py` supplies per run and the filter ones (a second `--workdir` or `--filters-file` points bisync at the wrong baseline). `_validar()` and `parse_extra()` also go through `model.problema_flag()`/`problema_valor_flag()`/`problema_extra()`, the same rules `model.comprobar_seguridad()` applies (flags that run a program or write a host file, flags smuggled in a value, `engine.md`), so the dialog refuses while typing what the loader would refuse later. A refused flag *name* (reserved, running a program or writing a host file), in the TOML box or in the extra-arguments box, is a `FlagReservado`; a refused *value* is a plain `ConfigError`.
- `effective()` resolves the four layers into what rclone would actually receive; `warnings()` compares **merged** flag sets, never one layer, so it catches `--max-delete` rising because the pair's own value was deleted or the mode changed. Editing flags never shelves a baseline.
- `tk_pairs.flags_form()` does **not** close on invalid input: the reason shows in a red `theme.aviso` under the TOML box, titled by `flags_editor.titulo_error()` (`FlagReservado`, a `ConfigError` subclass, → «Este flag no se puede poner aquí»; anything else → «Esto no se puede guardar así»). Its «what rclone would receive» table is a `tk.Tabla` (one canvas: the dialog is 27 widgets with 0, 3 or 10 flags) with a chip per layer; the pair's own flags are tinted with the accent. The red notice is built the first time what is typed is refused and from then on only gets its title and body reconfigured and is `grid_remove`d when it is valid (+5 widgets, never rebuilt; the height its holder frame asked for stays after it goes, as it did when the notice was destroyed: Tk keeps the size of a frame whose last child leaves); `pair_editor.merge_form()` (shared with `catalog_editor`) makes an emptied box delete the key.
