# The keychain (`common/llavero.py`, `common/cifrada.py`, `common/kdbx.py`, `common/keepassxc.py`, `common/registro.py`, `install/keepassxc_bin.py`, `install/llavero.py`, `ui/llavero_editor.py`, `ui/tk_llavero.py`)

Formerly: none (new with the keychain). Design and its reasons: `docs/superpowers/specs/2026-10-04-llavero-keepassxc-design.md`; real-hardware findings (K/B/PK/S/H-n codes): `docs/superpowers/pruebas/2026-10-04-keepassxc-portatil-resultados.md`.

A KeePassXC database (passkeys and passwords) travels in `.keychain/` at the volume root, with KeePassXC itself in `.prdrive/keepassxc/`, and syncs by itself against `keychain/` in the remote's catalogue folder. Windows (x64, and ARM64 running the x64 build emulated) and Linux (x64 with the AppImage, extracted on each host; ARM64 with the host's own KeePassXC): phase 2 of the spec, untested on real hardware.

## KeePassXC as a component

- **Pinned** in `pins.py` (`KEEPASSXC_VERSION`, `KEEPASSXC` = `{paquete: (file, sha256)}`, `KEEPASSXC_PARA` maps each platform to a package: Windows ARM64 uses `windows-x64`, because the only ARM64 ZIP, 2.8.0-beta1, could not talk to the browser, H-7; Linux x64 uses `linux-x64`, the official AppImage; Linux ARM64 has none, since there is no aarch64 AppImage, and opens with the host's own KeePassXC). The sum is written by hand after checking the PGP signature with KeePassXC's key (fingerprint in the docstring; the 2.7.12 AppImage checked the same day as the ZIP, same subkey); no `.DIGEST` is read at run time (three formats, H-2).
- **Two package shapes.** `windows-x64` is the ZIP, extracted into the package folder (`KeePassXC.exe`). `linux-x64` is the AppImage, kept whole under the fixed name `components.KEEPASSXC_APPIMAGE` (`KeePassXC.AppImage`, so finding it does not depend on the version) and never run from the drive: each Linux host extracts it once (below). `components.keepassxc_programa(paquete)` names the program of each; `keepassxc_bin.es_appimage()` tells them apart.
- **`install/keepassxc_bin.py`** follows `veracrypt_bin`: the official package in a per-version cache (`ensure_zip()`, for the ZIP and the AppImage alike; a hand-placed one is verified the same way and a bad one is reported, never downloaded over), every ZIP member path validated before the first write (`components.ruta_relativa_segura()`), the single top folder stripped (the AppImage is copied as one file, `_copiar_appimage()`, with the exec bit where the file system keeps one), each written file re-read and re-hashed, the stamp (`PRDRIVE-KEEPASSXC`, version + package + per-file sha256 with relative `/` paths) written **last**, and the folder swapped like `traveler.sustituir()` after a free-space check.
- **Pending** (`components.keepassxc_pendiente()`): unlike rclone, a **missing** KeePassXC counts too, but only when the device has the keychain (`llavero_activo()`: `[keychain]` in its `sync_config.toml`) and only for the packages of the platforms it carries (`paquetes_keepassxc()`: Windows and Linux x64; a Linux ARM64-only device asks for none). That is how enabling the keychain from «Ajustes» gets KeePassXC: the usual amber «Actualizar…». It also counts when `comprobar()` left a record that a file of the package does not match (next bullet).
- **Checked before it is launched or registered** (`pins.KEEPASSXC_EJECUTABLES`, `keepassxc.comprobar()`). `.prdrive/keepassxc/` is **not** in the agent's code fingerprint (`agent.md`: 78 MB, and a configuration KeePassXC rewrites as it is used), so the only thing between a drive and the host running a program from it is a SHA-256 table: `{version: {package: {file: sha256}}}`, for the three Windows executables (`KeePassXC.exe`, `keepassxc-cli.exe`, `keepassxc-proxy.exe`, hashed from the official ZIP after checking it against `KEEPASSXC["windows-x64"]`) and the Linux AppImage (the package's own sum, not repeated). The version that picks the row is the stamp's (`PRDRIVE-KEEPASSXC`); it never supplies a sum, so a rewritten stamp can only choose another *pinned* row. `comprobar(ruta, paquete)` (an indirection point; `tests/_harness.py` replaces it with a no-op and keeps the real one as `REAL_COMPROBAR`) raises `NoOficial` (an `OSError` whose text is the notice, in Spanish) when the stamp is missing, its version is not in the table, the table does not name the file, the file cannot be read, or the sum differs; the hash is remembered per process by `(path, size, mtime_ns)` (`RESUMENES`). **Every launch path goes through it**, and `tests/test_keepassxc_pin.py` walks `common/keepassxc.py` so a new function that launches or registers something without checking fails: `abrir()` (Windows: `KeePassXC.exe` *and* `keepassxc-proxy.exe`, before touching the config or the registry, because KeePassXC registers the proxy beside it by itself at start; also when ours is already open), `abrir_navegador()` (the proxy it registers), `cli_lanzable()` (the `keepassxc-cli.exe` that «Combinar», «dejar sin contraseña» and `llave_vale()` run; `_cli_listo()` says why in the console) and `preparar_appimage()` (Linux: the *copy* in the host's cache is hashed against the pin, so what is extracted is what was checked; a cache hit needs no read of the drive because `PRDRIVE-EXTRAIDO` is that pinned sum). The KeePassXC of the host (Linux ARM64, `del_equipo()`) is not the drive's and is not checked. **Not checked, on purpose:** the DLLs and every other file beside the executables, and the browser JSONs KeePassXC rewrites in `<exe>/config/`; and the file can still change between the check and the launch (a removable drive cannot be locked), except on Linux. **«Actualizar…» puts back a file that does not match, with the stamp up to date.** Two halves, because the stamp only says where the package came from, not that its files are still those, and hashing 11 MB (47 MB for the AppImage) cannot happen while the window paints. (1) The installer/applier, in the background, hashes: `keepassxc_bin.al_dia()` is the stamp **and** every executable in `pins.KEEPASSXC_EJECUTABLES[version][package]` having its sum (`ficheros_que_no_cuadran()`; a missing or unreadable file does not match; a package with no row there is not up to date, since nothing could vouch for it; the DLLs are still not looked at), so `instalar()` replaces such a package, saying which file, and activating the keychain again does too. (2) The window cannot, so `comprobar()` and `preparar_appimage()` leave a record when a file of the package **does not match** (a different sum, or a file that is missing or unreadable; a missing stamp, an unknown version or an unlisted file are not recorded: the version already counts as pending): `state/keepassxc-no-oficial.json`, `{package: {"version": stamp's, "fichero": name}}` (`components.keepassxc_anotar_alterado()`, via `keepassxc._alterado()`; best effort and it never raises: if `state/` cannot be written the notice still comes out). `components.keepassxc_pendiente()` reads it: with the stamp up to date and a record **for that same version**, the package is pending, shown as «lleva 2.7.12 (con ficheros que no cuadran)», and it is `actualizables()` like any other (a record of another version is ignored, so it dies by itself when the package changes version). `keepassxc_bin.instalar()` forgets the record (`keepassxc_olvidar_alterado()`) when it replaces the package and when `al_dia()` finds the files already match (fixed by hand), but not when it fails. Nothing else clears it: a record whose file matches again only goes away through «Actualizar…», which then copies nothing. The notice says only «Actualizar…» (`SALIDA_ACTUALIZAR`); it no longer asks to delete the package folder (`SALIDA_BORRAR` is gone).
- **Moving `KEEPASSXC_VERSION`** adds the new version's entry to `KEEPASSXC_EJECUTABLES` and **keeps** the old one (a device whose code is newer than its KeePassXC keeps opening its own); the old Linux entry is written out as a literal first, because the current one reuses `KEEPASSXC["linux-x64"]`. Both files enter the fingerprint, so changing a sum or the check makes the agent ask again.
- **The applier postpones it** while anything runs from its folder (`store.procesos_desde()`, moved from `install/components.py`, which re-exports it so its tests still patch it there): KeePassXC itself or `keepassxc-proxy.exe`, which lives as long as the browser is connected (K6, H-16).

## The pair, built in code

`[keychain]` in `sync_config.toml` (and the catalogue) makes `model.parse_config()` append `Pair(name="keychain", local=".keychain", remote=<catalog remote>, remote_path=<catalog folder>/keychain)`, bisync with `versions = true` and `LLAVERO_FLAGS` (`conflict-loser = num`, H-14: the loser stays beside it to be merged; `resync-mode = newer`, H-13, which `sync.build_command()` passes only on a resync: rclone reads it as `--resync`, and on every pass it left no conflict copy, the older base going to `.prversions/` instead). The TOML cannot change it: neither `[defaults.flags]` nor `[defaults]` filters reach it.

- **`Config.names` and `Config.del_usuario` leave it out**: the window, the console menu, the service's pair list and «Parejas» (`pair_editor.rows()`) never show it. `Config.pairs` keeps it, last, so `sync.py` with no names runs it, `sync.py keychain` runs it alone, `--list` marks it, and «Reparación», conflicts, versions and `pen_environment()` see it.
- **Its name is reserved** only while `[keychain]` is there (a user pair called `keychain` is a `ConfigError`). The base name must be a bare `*.kdbx`.
- **Filters, generated** (`Pair.reglas`, emitted right after `- .prversions/**` by `filters_content()`): `LLAVERO_REGLAS`, only the bases (`*.kdbx`, conflict copies included thanks to `suffix-keep-extension`) and `LEEME.txt`; never `QSaveFile` temporaries (H-11), `*.old.kdbx`, `.passkey` or plain-text exports (S6).
- **Root pairs** (`local = "."`) get `model.REGLA_SIN_LLAVERO` (`- /.keychain/**`) while the keychain is on, right after `REGLA_SIN_PROGRAMA` (`engine.md`), so the base never travels by another road. In a bisync pair it precedes the pair's own `+` rules; in copy/sync it is an ordinary `--exclude`, which rclone always adds after the `--include`s (`fs/filter/filter.go`, `NewFilter`), so a root mirror with a broad `include` could still carry it. The agent's `IGNORAR_CAMBIOS` and `install/device.RUIDO` include `.keychain`.
- **Moving the catalogue** (`catalog_path`, `catalog_remote`) changes its `expected_prefix()`, so the defaults plan shelves its baseline like any other (`catalogue.md`); `resync-mode = newer` loses nothing.

## Before every pass (`llavero.preparar()`, from `sync.run_pair()`)

- **The fixed companion**, `LEEME.txt` (H-12: with a single file, a save would read as "every file changed" and bisync would stop). Created if missing with `store.crear_exclusivo()` and the exact bytes of `LEEME_TEXTO` (`\n` on every OS, or two devices would write different files and fight over it); never rewritten if someone changed it. The text never changes, **and neither does its time** (#115): `asegurar_leeme()` gives it `LEEME_HORA` (2000-01-01 00:00:00 UTC; whole, even seconds, because FAT and exFAT keep 2 s steps, inside their 1980–2107 range), the same on every device and version. Each device used to create its own with the time of that moment, so the second one to arrive looked «newer»: its first `--resync` (`resync-mode = newer` is `ci.UpdateOlder`, `setResyncConfig()` in `cmd/bisync/resync.go`) updated the remote's time (`NeedTransfer()`, `fs/operations/operations.go`, rclone v1.75.2: it honours `modify-window`, so a difference under 2 s counts as equal and the base's exFAT rounding no longer matters, but one over it does), and the first device saw **both** of its files changed. One that already has the same bytes and another time (a device from before #115) is corrected on its next pass; one within `TOLERANCIA_HORA` is left alone (no rewrite of a pendrive on every pass); one with other text keeps its text **and** its time; a file system that will not take the time is ignored (`OSError`); a `--dry-run` does not correct an existing one (`preparar(simulacro=)`), so the correction waits for the real pass, but a `LEEME.txt` created then still gets its time. Moving a device from the old time to the new one is one pass in which `LEEME.txt` changes time on one side and, if the remote's was touched by another device meanwhile, on both: that is the case the next section repeats.
- **Every base must be whole** (`common/kdbx.py`, no key needed): signatures, the TLV header up to `EndOfHeader`, and for KDBX 4 the header SHA-256 plus the HMAC block chain ending exactly at EOF with a zero-size block. KDBX 3 cannot say where its encrypted body ends; with AES or Twofish (CBC) it must be a multiple of 16 bytes, which catches 15 of 16 random cuts. An unknown format is `None`, not broken. A broken base is looked at again after `ESPERA_ENTERA` (2 s; `llavero.dormir()` is the indirection point); if it is still broken the pass does not run and the pair records `sync.LLAVERO_ROTO` (2), retried on the next pass. Checked by hand against real bases (a KDBX 4.0 and 3.x from KeePassXC's test data, 3.1 from `keepassxc-cli` 2.7.6): no cut of the 4.0 passes, 1 in 16 of the 3.x.
  - **`keepassxc-cli` cannot make a KDBX 4** (#119, checked on 15/10/2026 against the pinned 2.7.12 AppImage, SHA-256 verified, reading the version bytes of each file). `db-create` has `-p`, `--set-key-file`/`-k`, `-q` and `-t`/`--decryption-time`, and writes **KDBX 3.1 with the AES-KDF** whatever it is given: `-t` only sets the rounds (1 000 000 by default, 21 582 734 for `-t 1000`) and the file is still 3.1; `import` (from XML), `db-edit` and `merge` keep the version they get. Nothing in the CLI picks the format or Argon2, so there is nothing to use: **prdrive creates no base itself** (a new one is made in KeePassXC and given with «Usar esta base…»; `db-edit` in `convertir()` only changes the protection of an existing one), and the only `db-create` callers are `tests/test_llavero_combinar.py` and `tests/integracion/llavero_real.py`, whose bases are 3.1 because of this. The keychain must work with any program that opens a `.kdbx`, and every current one opens KDBX 4; the weak whole-base check above is what a 3.1 base from the CLI gets.
- `.keychain/` is hidden (`store.hide()`) when `sync.py` creates it.

## It resyncs itself

Unlike every other pair, the keychain never waits for a `--resync` approval (`sync._bisync_preflight()`, `engine.md`): with no baseline (first pass, a shelved one after moving the catalogue) or changed filters it resyncs on its next pass, attended or not. `resync-mode = newer` keeps the newer base and the backup dir keeps the other side's in `.prversions/`. It is therefore never a «requiere resync» chip nor a `resync` finding.

Before that resync `sync.crear_carpeta_remota()` runs `rclone mkdir` on the pair's remote folder (`keychain/` beside the catalogue): nothing else creates it, and `bisync --resync` aborts when the remote root is missing ("error reading source root directory: directory not found"), so on a freshly activated remote the first pass always failed. It is a no-op when the folder exists, `--dry-run` creates nothing, and a failure is only said (the pass reports it again with its log). Found provisioning a real device in the cloud (`2026-10-05-llavero-nube-resultados.md`). The same `mkdir` also runs before the repeat of a pass that found the remote folder **emptied or deleted by hand** while a baseline exists (next section): with a baseline there is no resync, so nothing else would create the folder again.

## When rclone's brake stops a pass (`sync.repetir_sin_freno()`)

Three of rclone's brakes repeat a keychain pass **once**: the two that `--force` skips (`common/frenos.py`) and the empty-remote one, which only `--resync` skips. Nothing else in prdrive forces the keychain (`engine.md`: a person cannot, `frenos.se_puede_forzar()`), and it is safe here because everything either side would overwrite goes to `.prversions/` (the backup-dir, also on a conflict and on a `--resync`).

- **Too many deletes**, when every deletion is a conflict copy of a base (`llavero.solo_copias_borradas()`): the repeat has `max-delete = FRENO_SIN_COPIAS` (100). See «Merging», below.
- **All files were changed** (#115), `Safety abort: all files were changed on PathN` (`operations.go` in rclone's `cmd/bisync`, v1.75.2). A keychain is two files, a base and `LEEME.txt`, so a time change on both reads as «everything changed»; that is how bringing the keychain to a second device left the first one failing on every pass, and nothing mended it: the keychain only resyncs by itself with no baseline or with changed filters. The repeat adds `--force`. Checked against rclone's source (v1.75.2): `--force` skips exactly two checks, `excessDeletes()` and this one (`opt.Force` in `operations.go`, both inside one `if !opt.Force`, so a strict `--max-delete` could not be kept alongside it), and the delete check runs first, so a log that says «all files were changed» had already passed it. **But the repeat is another rclone run that lists both sides again, and with `--force` anything deleted in between would propagate with no brake**, so it is simulated first: `sync.lo_que_borraria_forzando()` runs the same command with `--dry-run --force` and reads what rclone says it would skip (`frenos.borrarian()`: `Skipped delete` and, with `versions`, `Skipped move into backup dir`; the overwrites are not counted, the backup-dir keeps them). Only a simulation that succeeds and deletes nothing lets the real repeat run. Checked with the real rclone: five files whose times all change, nothing else, is forced and ends well; the same with one of them deleted on the remote (1 of 5 = 20 %, under the 25 % brake, so the first run reached «all files were changed») is simulated, reported as «forzar la pasada borraría X3.kdbx: no se fuerza, el freno manda», and left failing.
- **The remote is empty** (`llavero.remoto_vacio()`): `Empty current Path2 listing. Cannot sync to an empty directory`, rc 7 (`checkListing()` in `cmd/bisync/listing.go`, from `findDeltas()` on the current listing). It happens when someone deletes `keychain/` (or every file in it) on the remote by hand, e.g. to «reset» the base there: the baseline is still there, so the pass is a normal one, `crear_carpeta_remota()` does not run (it goes only before a resync) and rclone refuses to sync against an empty side, which it cannot tell from an unmounted one. With the mode's `resilient` the error is «retryable without --resync»: rclone does **not** set the listings aside as `.lst-err`, `pair_state()` still reads `ok` and every later pass fails the same way, for ever (reproduced with the pinned v1.75.2 on two local folders, and end to end through `run_pair()` with a local `alias` remote: rc 7 on every pass before this, rc 0 after). `bisync.referencia_vacia()` does not cover it: that is two empty **prior** listings. The repeat runs `crear_carpeta_remota()` and then the same pass as a `--resync` (with `resync-mode = newer`, `orden.flags_de_la_pasada(resync=True)`): a resync deletes nothing, the device's base goes up again and whatever the remote has meanwhile (another device that got there first) is kept by the newer-wins rule and the backup-dir. **Only Path2**: the device's side is never empty, since `preparar()` writes `LEEME.txt` before every pass, and an «Empty current Path1 listing» is left failing. So deleting the remote folder does not reset the keychain: the first device to pass puts its base back (the user guide says so); a base is replaced by changing it on one device.

- **One repeat per pass, whichever brake**: if the repeated pass stops again, for the same or the other brake, the failure stays. Never a second real repeat (the simulation before the `--force` one is not a repeat: it changes nothing). The brakes' repeat is also **unattended** (the service, the agent and the watcher run it with no one to answer), which `AGENTS.md` («Safety invariants») names as the one exception to «`--force` is never an unattended path».
- **Never after a `--resync`** (`need_resync`): it does not go through the delete and «all changed» brakes, and a resync that finds the remote still empty has already done what the empty-remote repeat would do. The empty-remote repeat is itself a resync; the other two are not. And never another pair: `sync.run_pair()` calls it only for `pair.llavero` (a user pair with an empty remote keeps failing until a person decides).
- **It does not go through `RunContext.force`.** The repeat runs a derived `Pair` (`replace(pair, flags={…, "force": True})`, like the other repeat does with `max-delete`), so `sync.py keychain --force`, «Reparación» and `orden.flags_de_la_pasada(forzar=)` still refuse to force the keychain. `_bisync_preflight()` is prdrive's own check and runs before the first rclone, so a missing local folder with a baseline still aborts with rc 2: `--force` never reaches it.
- **The log of the stopped pass is kept** in `logs/` even if the repeat goes well (its log is thrown away like any good pass's), and a line names it: it is the proof of why `--force` was used, or of why the remote was rebuilt with `--resync`. The line also says that each side's overwritten file lands in `.prversions/`. (The copies repeat throws its log away: removing conflict copies is routine.)
- **If it stops again it is not a mute «code 1»**, and the text does not claim a repeat that may not have happened (the one allowed repeat can have been the copies one, the log can be unreadable, or the simulation can have refused): "prdrive repite solo la pasada una vez con --force cuando es esto lo único que la para y forzarla no borraría nada… si la ves aquí, no ha podido hacerlo o no ha bastado". The console says what to do (`frenos.explicacion_llavero()`, replacing the «fuerza UNA pasada» of the other pairs) and «Reparación» and `--doctor` show a `freno` finding («El llavero: el freno de seguridad ha parado la sincronización», `frenos.salida_llavero()`). `revision._fallos()` reads the keychain's last pass (`results.fallos_de([model.LLAVERO])`, though it is not in `Config.names`) and keeps it **only when it is a brake**; a failure of another kind (no network) still has no finding, the window's line says it and the pass retries by itself. The finding offers no «Forzar» (`repair.puede_forzar()` excludes the keychain). The way out is `python sync.py keychain --resync`: the pass keeps the newer base and the other goes to `.prversions/`, so nothing is lost (it is what mended the reporter's device by hand). For deletes the text is the old one: check that no base is missing on a side and use «Combinar».

## Who attends it, and when a pass is due

One thing at a time, in this order (the spec's §5b):

- **The root's service, if alive here** (`llavero.atiende_el_servicio()`: `model.daemon_lock()` held by a live pid of this host and boot). Both write that file: runsync's service and the resident agent. An agent's record (`"agente": true`) counts only if its `pairs` list `keychain`: an agent from before the keychain holds the root without attending it, and the watcher stays. The agent keeps that list in step with the config it serves (`Agente._al_dia_el_lock()`, `agent.md`), so turning the keychain on while it serves the root is seen at once. runsync's service is this device's own code, so it always does.
  - **The agent** treats `[keychain]` as a watched pair (`agente.leer_servicio()` appends `keychain` with `vigila=True` and `.keychain` as its folder, whatever the chosen pairs are): its own stat polling and `PoliticaCambios` (`agent-scheduling.md`), and the service interval for the remote.
    - **KeePassXC open** (`Agente._mirar_keepassxc()`, every `PoliticaCambios.sondeo`, only on roots it serves that carry the keychain; `agente.keepassxc_abierto()` is `llavero.keepassxc_abierto()` on the root's `.prdrive/`, asked only if `agente.hay_keepassxc()` says something on the host is called like it: `agent.md`): the keychain pair gets its own interval, `min(the root's, REMOTO_ABIERTO)` (`pl.Pareja.intervalo`), also on a `sync`-mode root, where nothing else would pull or watch it.
    - **A metered network does not hold it** (everything else waits; pause, battery and power saving hold it too): `pl.deja_pasar()` over `pl.retiene_al_llavero()`, `agent-scheduling.md`.
    - **Opening and closing** reset its mark to «never tried», so a pass follows at once: on opening it brings the latest before the base is unlocked (with the agent serving, «Abrir llavero» runs no pass of its own); on closing it uploads the last save. A keychain pass already running defers the change to the next look (that pass may have started before). A root the agent stops serving (its window, its own «Pausar») is forgotten, not «closed».
    - **The tray's «Abrir llavero» while passes are held** (the tray's «Pausar», battery, power saving: `pl.retiene_al_llavero()`, not a metered network) would otherwise open a stale base silently: `--llavero` sees the agent and runs no pass, and the pass of the opening is held. So `Agente._traer_al_abrir()`, right after launching `--llavero`, queues ONE urgent keychain pass (`urgentes` skip moderation, like «Sincronizar ahora»), and the diary says so («se trae lo último de su llavero aunque no se sincroniza (en pausa)»). Only for a root the agent holds (`con.lock`) whose served pairs carry `keychain`, not while it is being locked, not if its KeePassXC is already open (then opening only brings it to the front, as in `mirar_apertura()`), and not twice. KeePassXC is not held back: it opens at once and the pass runs while the password is typed, the same race the unpaused flow has with the opening's pass. Everything after it stays held (the opening's pass, the 5-min pull, saves, closing), so what is saved goes up when syncing resumes. Unlike «Expulsar», which uploads nothing while moderating (`agent.md`): opening is a request to read the keychain, and a stale base turns the next save into a conflict copy. A root paused from its own window is not the agent's, so `--llavero` brings the latest itself.
  - **runsync's service** runs one keychain pass after each cycle and, while it waits for the next, `atender_llavero()` every `POLL_SECONDS`.
- **Otherwise, the keychain watcher**, `runsync.py --vigilar-llavero` (`vigilar_llavero()`), started detached by «Abrir llavero» (`llavero.lanzar_vigilante()`, an indirection point in `common/` so the window can call it: no-op if the service attends or a watcher lives). One at a time (`llavero.registro_vigilante()`, `state/llavero.lock.json`, taken with `store.tomar_registro()`). It leaves when the service takes the root, when the device goes, on `state/llavero.stop` (`llavero.parada_vigilante()`, for «Expulsar»; one left over from before it started is removed) and when KeePassXC closes (after `ARRANQUE_KEEPASSXC`, 30 s, if it never saw it), uploading whatever is pending first. cwd in the temp dir, so it never holds the volume.

**The rules are pure** (`llavero.Vigilancia`, the agent's `PoliticaCambios` values): a photo every `sondeo` (10 s) of each base's size, `mtime_ns` and KDBX seed (`llavero.huella()`; the seed tells apart two same-size saves in one exFAT clock tick); a change waits `calma` (20 s, each new save moves it) and at least `separacion` (120 s) since the last pass; with KeePassXC open (`keepassxc_abierto()`: only `KeePassXC.exe` running from the device counts, not the browser's proxy) the remote is pulled every `REMOTO_ABIERTO` (5 min). A failing pass doubles the separation up to `TOPE_REINTENTO` (30 min), so an offline keychain does not retry every two minutes. Whether KeePassXC is open is asked with the photo, not every turn: on Windows it walks every process.

**«Pending upload»** (`llavero.pendiente()`) needs no record of its own: a base differs from its line in bisync's `path1` listing of the last good pass (`listado_local()` parses rclone v1.75.1's `lineFormat`, nanoseconds and zone included) by size, or by a time that is `llavero.TOLERANCIA_HORA` (2 s, `model.VENTANA_HORA`) or more away in either direction, rclone's own `modify-window` rule (`engine.md`): on exFAT/FAT32 under Windows the base that has just come down is stored up to 2 s ahead of its line, and with exact times every pass that brought it would read «con cambios que aún no han subido» (#114, #116 step 2). With no listing every base is pending. **A device that has not touched the base has no conflict (#116).** The same window is why: the copy that came down is stored up to < 2 s ahead of the remote's on exFAT/FAT32 under Windows, which used to make it the «newer» side of a later save of another device (so the old copy won and the good base became `conflicto-remoto1`); with `modify-window` rclone calls them equal and the remote's save arrives as a plain download. Checked in the cloud on a real Windows exFAT, with the saves 1.2 s apart (the worst case, +1.877 s) and more than 2 s apart (F32, `2026-10-15-llavero-exfat-resultados.md`: both pass with #114 alone, and the same script fails the `LEEME.txt` and «all files were changed» steps on `main` without #115). Comparing the KDBX seeds (`kdbx.semilla()`) before accepting a conflict, which the issue proposed, was **not needed and is not built**; if it is ever added it must keep working with any program that opens a `.kdbx`, not only KeePassXC. It also catches a save made **during** a pass (`Vigilancia.acaba_pasada(sin_subir=…)`), which the agent's generic watch absorbs. **The window's blind spot** (found in #115's CI, not built around): bisync compares size and time only, so a base that has **the same size** as its line in the listing and a time less than 2 s away reads as unchanged, to rclone (`No changes found`, rc 0; reproduced with the pinned v1.75.2 on two local folders) and to `pendiente()` alike. A KDBX is 16-byte quantised and its size moves by ±100 bytes between saves, so equal sizes are not rare (of the order of 1 in 25 for two saves); it needs a second save within 2 s of the first one's time **and** a pass between them (the watch waits for calm plus 120 s, so in practice only a periodic or start-up pass can land there). Nothing is lost: the base stays on the device and the next change uploads it, but the window says «al día» and the remote is stale until then. `tests/integracion/llavero_real.py` waits 2.5 s before «Combinar» for this reason (it merged 0.4 s after the pass and failed once in about ten CI runs). Closing it for good means comparing something besides size and time (e.g. `--compare size,modtime,checksum` where both sides have a hash, or `kdbx.semilla()`), a design change that is not part of #115.

## Opening it («Abrir llavero»)

The button of the main window's keychain line, `runsync.py --llavero` (what `Llavero.bat` and `llavero.sh` run; it does **not** stop the service) and the tray's «Abrir llavero» (`PIDE_LLAVERO` → `Agente._lanzar_llavero()`: that same `runsync.py --llavero` with the agent's windowed Python, cwd `equipo.DIR`, with the window's guards except an open window, which it does not mind; only for a listed root with its code accepted, only where `resumen()["abre_llavero"]`, i.e. Windows and Linux, `agente.ABRE_LLAVERO`; while the agent holds passes back it also queues the urgent pass that brings the latest, `Agente._traer_al_abrir()`, «Who attends it» above), and the agent's global shortcut «Abrir el llavero» (none by default; recorded in «Atajos de teclado…»), which sends that same `PIDE_LLAVERO` for the last used of the drives that carry a keychain, so it brings the latest the same way (`tray.md`, «Global keyboard shortcuts»). Three layers:

- **`common/keepassxc.py`**, KeePassXC on this host: what is needed (`mirar_apertura()` → `Apertura`, touches nothing) and doing it (`abrir()`). `paquete_del_equipo()` (an indirection point) is `windows-x64` on Windows x64 and ARM64, `linux-x64` on Linux x64, `None` elsewhere; with `None`, `del_equipo()` (another one) looks for the host's KeePassXC on Linux (below), and without either `sin_programa()` says why. **The package, not the host OS, picks the flow** (`es_appimage()`), so each OS's tests run on the other.
- **`ui/llavero_editor.py`**, no Tk: the window's line (`linea()`: no line without `[keychain]`; amber without KeePassXC or after a failed pass; otherwise open / pending / up to date) and the flow (`abrir(config, avisar, esperar, elegir_llave, decir_sin_traer)`), the spec's §6 steps in order with the three questions passed in as functions.
- **`ui/tk_llavero.py`** gives it Tk dialogs (`avisar()`, `working()`, `elegir_llave()`; the first and last are indirection points). `ui.abrir_llavero()` hangs them off `root_oculto()`; if that root cannot be created, it falls back to the console and asks nothing. A failure halfway never re-runs the steps.

**The steps.** No `[keychain]`, no package, or no `KeePassXC.exe` → say so (the last: «Actualizar…» puts it). **Ours already open** (`llavero.keepassxc_abierto()`) → just launch with the base, which `SingleInstance` hands to the running one and brings to the front; no pass, no question, and its config is not touched (it rewrites it on exit). **Another KeePassXC on this host** (`otro_abierto()`: any `KeePassXC.exe` from `store.procesos()` not running from the device) → say so and stop: ours would hand it the base, with another config. **Bring the latest** (`llavero.pasada()`, `sync.py keychain` with no terminal) when the base is missing, or when the last good pass (`results.ultimas_buenas()`) is older than `DESDE_LA_ULTIMA` (2 min) and no service attends the root (it would collide with the service's own bisync lock). A failed pass still opens; the window says it in its line, standalone says it in a notice (`decir_sin_traer`). No base after the pass → say why and stop. **Conflict copies of the base** (`conflicto_de_la_base()`, a fresh scan of `.keychain/`) → first the key file, if `[keychain] fichero_llave` (its path on this host: `state/keychain.json`, `{"equipos": {host: {"fichero_llave": path}}}`, `llavero.equipo()` = `prefs.HOST`, if still there, else a file dialog titled with `nombre_llave`, then recorded by `apuntar_llave()`; the file is never opened; `llavero_editor.llave_de_este_equipo()`, shared with «Combinar»), because merging needs it, then the merge plan through `confirmar` («Cancelar abre KeePassXC sin combinar»); it comes after the pass, which is what brings the copy. **Opening never passes `--keyfile`**: KeePassXC does not just fill the field, `DatabaseOpenWidget::enterKey()` calls `openDatabase()` at once with an empty password, and with a password + key file base that failed with «Desbloquear la base de datos ha fallado y no introdujo una contraseña» (checked against 2.7.12's source); the person picks the key file in KeePassXC's own dialog, so with no copies nothing is asked. Then `keepassxc.abrir()`, and the watcher.

**Config, line by line** (`ajustar_config()`, KeePassXC closed). Lives in `.prdrive/keepassxc/config/windows/`, outside the package folder that `keepassxc_bin` swaps whole, and is passed with `--config`/`--localconfig`. `editar_ini()` changes only the requested keys' lines (case-insensitive, like QSettings on Windows; `Group/Key` → `[Group]`, the rest is `[General]`), appends missing ones at the end of their section or in a new one, keeps every other byte and the file's line ending (`\r\n` for a new file), and reads/writes with `surrogateescape`. Every launch: `SIEMPRE` (`UseAtomicSaves`, H-11; `Browser/UpdateBinaryPath`; `GUI/CheckForUpdates=false`; `Browser/UseCustomProxy=false`, because this file lives on the drive and outside the agent's fingerprint, and with a custom proxy KeePassXC would register in the browser whatever program the file named, past the SHA-256 check). Only when the file is created: `AL_CREAR` (`Browser/Enabled`, `RememberLastKeyFiles=false`, `UpdateCheckMessageShown`…) and `AL_CREAR_LOCAL` (`Security/QuickUnlock=false`, H-1). Both files always exist after it: `Config::init()` treats a `keepassxc_local.ini` without its `keepassxc.ini` as an old layout and moves it. **Recent paths** (`RECIENTES`, all `Local`) move from the previous root (`raiz.txt`) to this one (`mover_raiz()`: each list element starting with it, with `/` or QSettings' `\\`); a root QSettings would escape (non-ASCII, commas, quotes: `forma_ini()` → `None`) is not searched for.

**The browser** (`abrir_navegador()`, every launch with ours closed): the four `HKCU\Software\…\NativeMessagingHosts\org.keepassxc.keepassxc_browser` keys (`NAVEGADORES`: Chrome shared with Vivaldi and Brave, Mozilla with Tor, H-5; Edge; Chromium) get their default value (QSettings' «Default») pointed at `<exe>\config\org.keepassxc.keepassxc_browser_<name>.json`, where `.portable` puts the JSONs; KeePassXC's `updateBinaryPaths()` rewrites both at start (B2, B3, B5). `common/registro.py` wraps `winreg` (`leer`/`escribir`/`borrar`/`vacia`/`subclaves`, HKCU only; also used by `common/explorador.py`, `drive-name-icon.md`). **Undoing it** is `cerrar_navegador()` (wired into «Expulsar» later): only keys that are prdrive's (`de_la_unidad()`: inside this volume, or a `…\<app dir>\keepassxc\…` path that no longer exists) go back to an installed KeePassXC's JSON in `%LOCALAPPDATA%\KeePassXC` (any name sharing that key) or are deleted. Never raises.
  - **`NativeMessagingHosts` goes only if prdrive created it and it is left empty** (#119: closing used to delete an empty `HKCU\Software\Chromium\NativeMessagingHosts` that was already there before the first launch). `abrir_navegador()` asks, per browser and before writing, whether that key exists (`registro.vacia()` is `None` when it is absent, or cannot be opened, in which case the write fails too) and notes the ones it is about to create in `llavero-navegador.json` (`NOTAS_NAVEGADOR`, `{"creadas": [key, …]}`, lower-cased), **in `equipo.DIR`, not in the drive's `state/`**: the keys are the host's, any drive's window reads them on eject, and the agent's sweep of a drive that left reads them too (`agent.md`, «Files and ownership»; `anotar_creadas()` creates the folder, which an agent-less host does not have). The note is written after the key, so a crash in between leaves no note, and **no note means no deletion**: a missing, unreadable or unwritable file reads as «prdrive created none» (a keychain opened by a version before this one left none; the keys it created stay, empty, which is harmless; deleting one that was there is not). A second drive opening finds the keys already there but does not touch the note, so they stay prdrive's. `cerrar_navegador()` reads the note only when a key is about to be deleted (the agent's idle turns touch nothing under `equipo.DIR`), deletes the parent only if it is in the note and empty, and then forgets it (`anotar_creadas(quitar=…)`, also when the key went back to an installed KeePassXC's JSON); the file goes when nothing is left to remember. `Software\Chromium` itself, which `escribir()` also creates on a host without Chromium, is not noted and stays.

**Launch** (`orden()`, `entorno()`, `lanzar()`): `KeePassXC.exe --config … --localconfig … <base>`, `KPXC_INITIAL_DIR` = the volume root (exports land in sight, PK5), detached, cwd in the temp dir. `esperar_arranque()` watches it for `ESPERA_ARRANQUE` (1.5 s): `VC_FALTA` (`0xC0000135`, both signs) means no Visual C++ runtime (K3) and the notice gives Microsoft's installer (`REDISTRIBUIBLE`, x64 also on ARM64); another non-zero code is said with its value (on Linux, with the `AppRun` to run from a terminal: `Abierto.programa`); 0 is a hand-off to a running instance.

### On Linux

- **The AppImage is never run from the drive.** `preparar_appimage()` extracts it once per host and version into `cache_equipo()/<version>/squashfs-root/` (`~/.cache/prdrive/keepassxc/`, an indirection point): it copies it to the cache first and checks the copy against the **pinned** sha256 (`esperado()`, above; a stamp or a version the table does not know raises `NoOficial`), runs `--appimage-extract` there (`extraer_appimage()`, an indirection point; the AppImage's own runtime, no FUSE), writes `PRDRIVE-EXTRAIDO` (that sha256) **last** and swaps the folder in with a rename, putting the old one back if that fails. Next time `PRDRIVE-EXTRAIDO` is enough, whatever is on the drive by then. Old versions go when nothing runs from them, and `.<version>.nuevo-<pid>` leftovers only when their pid is dead (another window may be extracting). So no FUSE 2 is needed, a `noexec` or exFAT volume (no exec bit, no symlinks) does not matter, and neither KeePassXC nor its proxy holds the volume (LX7). Checked in the sandbox with the real 2.7.12: 1.4 s to extract, ~125 MB.
- **It runs `AppRun`** (`AppRun` → `AppRun.wrapped` → `exec keepassxc "$@"`) with `config/linux/` (`carpeta_config(paquete)`; `\n`; `SIEMPRE_LINUX`): `Browser/UpdateBinaryPath=false` (prdrive writes the browser manifests, and rewriting them at start would overwrite an installed KeePassXC's), and `Browser/UseCustomProxy=true` + `CustomProxyLocation=<extracted>/usr/bin/keepassxc-proxy`, because the AppImage build writes `$APPIMAGE` into a manifest (`getInstalledProxyPath()`, `KEEPASSXC_DIST_APPIMAGE`), which an extracted run does not have; a path QSettings would escape (`forma_ini()`) is left out. `entorno()` drops `APPIMAGE`/`APPDIR`. Checked in the sandbox: the config lands in `config/linux/`, not in `~/.config/keepassxc` (LX3), and SIGTERM closes it in 2 s.
- **Which KeePassXC is this drive's** (`llavero.pids_keepassxc()`): on Windows a `KeePassXC.exe` running from a package folder; on Linux (`llavero.MIRAR_ORDENES`, which tests turn on anywhere) a `keepassxc` whose command line (`store.orden_de()`, `/proc/<pid>/cmdline`, an indirection point) names something of the drive (`--config` inside its `keepassxc/`, or a base in its `.keychain/`), compared resolved. `keepassxc_abierto()`, `otro_abierto()` (single instance is per user whatever the config, `Application.cpp`) and `procesos_de_la_unidad()` go through it; on Linux the proxy is not killed on eject (it runs from the host cache and holds nothing). **On Linux a process is told by its name, not its executable** (`store.nombres()`): KeePassXC makes itself non-dumpable at start (`prctl(PR_SET_DUMPABLE, 0)`, `Bootstrap::disableCoreDumps()`), so its `/proc/<pid>/exe` becomes root's and only root can read it, while `comm` and `cmdline` stay readable. `store.sin_exe()` (an indirection point) lists those by their `comm`. Before it, prdrive never recognised its own KeePassXC for anyone but root: the watcher left after `ARRANQUE_KEEPASSXC`, eject did not close it, the agent could not close a gone drive's (found in `ubuntu-latest`; the cloud runs were as root). **«Runs from the cache»** (`abiertos_de_la_cache()`, for the version sweep and `plan_cerrar_navegador_linux(muertas)`): the executable when it can be read, else a `keepassxc` that prdrive launched (`lanzado_por_prdrive()`: its `--config` is in some drive's `keepassxc/config/linux/`), of unknown version, so no old version is swept while one is open.
- **The browser on Linux** (`abrir_navegador_linux()`, each launch with ours closed; the registry's B2 counterpart): one manifest per browser of `NAVEGADORES_LINUX` (KeePassXC's `TARGET_DIR_*`: Chrome, Chromium, Vivaldi, Brave, Edge under `XDG_CONFIG_HOME`, Firefox under `~/.mozilla`, Tor under `XDG_DATA_HOME`; `bases_navegador()` is the indirection point), only where the browser's folder exists and only where there is none or it is ours (`manifiesto_nuestro()`: its `path` resolves inside `cache_equipo()`). An installed KeePassXC's is never touched: its proxy reaches ours anyway (the socket is the same path, `BrowserShared::localServerPath()`) and an overwritten one could not be given back. `manifiesto()` writes what `constructFile()` would, byte for byte (checked against the real 2.7.12, which also used our `CustomProxyLocation`, and which left a foreign manifest alone with `UpdateBinaryPath=false`). **Undoing it** (`cerrar_navegador_linux()`, from `cerrar_navegador()` when `MANIFIESTOS`): ours are deleted, others stay; with `muertas` (the agent) only while no `keepassxc` runs from the cache (the proxy alone does not count: it lives as long as the browser).
- **Linux ARM64** has no package: `del_equipo()` finds the host's KeePassXC without running anything (`keepassxc` on `PATH`, or Flathub's `org.keepassxc.KeePassXC` installed) → `Externo`. It opens with the person's own config and manifests (`orden_externo()`); Flathub's gets `--filesystem=<root>` and `KPXC_INITIAL_DIR` through `--env`. No «another KeePassXC open» check: handing the base to the one already open is what is wanted. `version_del_equipo()` (`keepassxc-cli --version` or `flatpak info`, an indirection point) feeds `sin_passkeys()`: below `PASSKEYS_DESDE` (2.7.7; Debian 12, Ubuntu 24.04) it opens and says so.
- **`store.pid_alive()` treats a zombie as dead** (`/proc/<pid>/stat` state `Z`): KeePassXC is the window's child, and after it closes it lingers until reaped, so «Expulsar» from that same window waited out `ESPERA_CIERRE`. Found running the real AppImage; Windows already asked for the exit code. One that is being reaped right then is dead too: state `X` (EXIT_DEAD), or a `/proc/<pid>/stat` that can no longer be read after signal 0 found the pid, in which case signal 0 is asked again (with no `/proc` at all it still answers and the process counts as alive). An orphan killed with its tree is reaped by init at its own pace, so a caller polling for its death did get «alive» for an instant after «dead»: `tests/test_install_device.py` failed about 1 run in 1000 under load on it (`tests/test_keepassxc_linux.py` pins both cases).

## Turning it on and off («Ajustes → Llavero»)

The pane (`tk_llavero.construir_ajustes(panel)`, also alone as `tk_llavero.ajustes()`) opens at once and reads the catalogue in the background (`segundo_plano`, the same `"catalogo"` read as «Parejas», `catalog.load()`; its `Sondeo` and `Indicador` come from the panel, `panel.sondeo()`/`panel.indicador()`, so a hidden pane stops polling and animating: `ui.md`); what it offers depends on the remote's `[keychain]` (`llavero_editor.tabla_remota()`), and every write needs that fresh read (`Catalog.editable`). The decisions are `LlaveroPlan`s in `ui/llavero_editor.py` (`EditPlan` shape, through `confirmar_plan()` and `working()`); `plan.activa` tells the caller to run the first pass.

- **`plan_activar(raw, cat, origen, pide, nombre_llave, llave)`.** `origen` is «Usar esta base…» (a `.kdbx` chosen by the person) or `None`, «Traer el del remoto». A base is checked with `kdbx.comprobar()` (broken → refused; KDBX 3 → warning that KeePassXC converts it to 4; unknown → warning) and its name normalised (`llavero.nombre_de_base()`: `.kdbx` lowercase, because the `+ *.kdbx` filter is case-sensitive; the model now refuses `.KDBX`). **The original is copied, never touched** (`llavero.poner_base()`: temp + re-read + `os.replace`). **If the remote already has a keychain, its base is the one**: the local `[keychain]` is the remote's, nothing is pushed, and a base of one's own goes in as `<base>.conflicto-dispositivo1.kdbx` (`llavero.copia_propia()`, rclone's own Path1 loser name) for «Abrir llavero» to merge; the same happens if `.keychain/<base>` already holds a different file. Otherwise the catalogue gets `[keychain]` first (`catalog.push()`; if that fails nothing local changes), then `.keychain/` (`preparar_carpeta()`: created, hidden, `LEEME.txt`), the copy, `[keychain]` in `sync_config.toml` (validated with `parse_config()` before confirming), `Llavero.bat` and `llavero.sh`, and the key file's path on this host. Warnings: a root bisync pair will ask for a resync (it gains `REGLA_SIN_LLAVERO`), and «this host cannot open it yet» (no package for it and no KeePassXC installed, `sin_programa()`; or the package missing: the amber «Actualizar…» puts it, `components.pendientes()`).
- **On a host root** (`model.es_equipo()`, `host-root.md`) everything is the same except the launcher: a host root carries no launchers and no Python of its own, so no `Llavero.bat` nor `llavero.sh` (and `plan_desactivar()` only mentions those that are there); the consequence says it opens from the window or the agent's tray. KeePassXC is the host's own platform (`paquetes_keepassxc()` follows the root's rclone), the watcher and «Combinar» use the window's Python (the agent's), and the wizard's «En este equipo» route has no «Llavero» step: it is turned on from the root's window. The window offers no «Expulsar» for it (a host folder is not removed: `vista["del_equipo"]`); an encrypted one's «Bloquear» closes the keychain first (below).
- **`plan_pide_llave()`** writes `fichero_llave`/`nombre_llave` to the catalogue and here (prdrive cannot tell from the KDBX header); refused unless the remote's `[keychain]` is this base. «Dónde está el fichero llave…» only records the path on this host, no plan.
- **`plan_desactivar()`** removes `[keychain]` here, asks the watcher to stop and removes `Llavero.bat` and `llavero.sh` (each only if it is still ours, byte for byte: `quitar_lanzador()` returns the names it removed). `.keychain/` and the remote stay, and other devices keep it. Warnings: KeePassXC open; a root pair would now carry `.keychain/`.
- **`Llavero.bat`** (`llavero.LANZADOR_BAT`, CRLF, ASCII) is `call "%~dp0runsync.bat" --llavero`, and **`llavero.sh`** (`LANZADOR_SH`, LF) `exec sh "$(dirname "$0")/runsync.sh" --llavero`, through `sh` so no exec bit is needed (exFAT): the same Python search as the window. Both are written together on activation (`escribir_lanzador()`, since the drive travels between systems; `lanzadores_puestos()` says which are there), not by the components updater; `llavero.sh` gets the exec bit where the file system keeps one. A drive activated before Linux has only `Llavero.bat`; turning the keychain off and on again, or the installer's step, adds the other.
- The «Crear una nueva con KeePassXC» exit of the spec is not there: a new base is made in KeePassXC and then given with «Usar esta base…».
- **The rule is one** (`llavero.decidir_alta()` → `Alta(tabla, destino, copia, subir, aviso_formato)`): the window's plan and the installer's both call it and only word it.

### In the installer (step «Llavero»)

`ui/tk_install._paso_llavero()` after «Parejas y configuración», optional («Sin llavero» keeps «Siguiente» on; `_ok_llavero`): «Usar una base propia» (with «La base usa un fichero llave» when the remote has none) or «Traer el del remoto» (only if the catalogue has `[keychain]`), and the key file's path on this host when the base asks for one. `install/llavero.pensar()` re-plans on every change and the step shows what will happen; «Poner el llavero» runs `aplicar()` under `working()`, **outside in**: KeePassXC for every platform the device carries that has a package (`keepassxc_bin.instalar()`: the 78 MB ZIP for Windows, the 47 MB AppImage for Linux x64), then `[keychain]` into the catalogue (re-read first: if another device added one meanwhile it stops, since the base would be theirs; `catalog.push(ejecutar=…, donde_pedido=…, cachear=False)` runs through the wizard's rclone and leaves no cache in the installer's own `state/`), then the device: `.keychain/` (`preparar_carpeta(raiz)`), the copy, `[keychain]` in its `sync_config.toml`, `Llavero.bat` and `llavero.sh`, and the key file's path in **its** `state/keychain.json` (`apuntar_llave(…, estado=)`). «Inicialización» then adds `keychain` to the names it resyncs. The «already a prdrive» panel has no «Añadir el llavero…»: an existing device does it from its window («Ajustes → Llavero», plus the amber «Actualizar…» for KeePassXC), which needs no second connection.

## Key file only («sin contraseña», `[keychain] llave_interna`)

Spec: `docs/superpowers/specs/2026-10-06-llavero-sin-contrasena-design.md`; hardware test plan: `docs/superpowers/pruebas/2026-10-06-llavero-sin-contrasena-plan.md`. Nothing here was run against a real KeePassXC with a screen: `tests/integracion/llavero_real.py` step 8 checks the CLI premises (CI only) and the open with `--keyfile` and an empty password is a manual test.

A base with **no password**, opened only with a key file that prdrive generates and that **never travels**, for **encrypted** devices (VeraCrypt or BitLocker): the device's encryption is then the other factor, and the daily password goes away.

- **The flag lives in the catalogue's `[keychain]`** (and the device's copy): `llave_interna = true`, which needs `fichero_llave = true` (`model._build_llavero()`, a `ConfigError` otherwise; the other keys stay untyped, so no config that loads today stops loading). `Pair.llave_interna` carries it. Older versions ignore the key and preserve it on rewrite, but they do not enforce the encryption rule. **Devices that already have the keychain active are not told** when the flag turns on elsewhere (nothing compares the local `[keychain]` with the catalogue's); only a device that activates reads it.
- **The key file** is always `.keychain/llave.keyx` (`model.LLAVERO_LLAVE`): fixed name, so `state/keychain.json` is not used in this mode. No filter of `LLAVERO_REGLAS` lets it through (`+ *.kdbx`, `+ LEEME.txt`, `- **`), and a root pair already leaves out `.keychain/` while the keychain is on. `llavero.generar_llave()` writes 64 random hex characters (no newline, `O_EXCL`, mode 600); `llavero.poner_llave()` copies a given one (`poner_base()` + `chmod 600` where it applies).
- **«Is this device encrypted?» is one function**, `common/cifrada.py` `estado()` → `Cifrado(cifrada, como, motivo)`, asked **at run time** and failing closed (an exception, an unreadable volume or an unknown BitLocker state is «not encrypted»): a drive is encrypted if `vestibulo.raiz_fisica(fleet.device_id())` finds a physical root with its mark and `PRDRIVE.hc` that is not where it runs (a stale mark on the same folder does not count), or its volume is BitLocker-`protected` (Windows only: the reader moved to `common/bitlocker.py`, and `install/crypto.py` re-exports it with the names its tests replace; `bitlocker_de()` is the indirection point); a host root, if the agent lists it with a `contenedor` (`Unidad.cifrada`), or BitLocker. Suspended, waiting, encrypting or locked BitLocker is not encrypted. The wizard cannot use it (it would look at the installer's own machine): it passes the device's own answer from the «Cifrado» step (`tk_install._cifrado_del_dispositivo()` → `install/llavero.pensar(cifrado=)`; without one, not encrypted).
- **Where it is enforced** when the flag is on and the device is not encrypted: `llavero.decidir_alta()` (the one rule for window and wizard, `ValueError` → `ConfigError`/`InstallError`); **every pass** (`sync.run_pair()`, before `llavero.preparar()`: `sync.LLAVERO_SIN_CIFRAR` = 3, no rclone, a failure in «Reparación» and the window; it does not touch what is on disk: dropping encryption later leaves base and key where they are); `keepassxc.mirar_apertura()` (a `motivo`); the window's line (amber, no button).
- **Opening** passes `--keyfile .keychain/llave.keyx` (`Apertura.llave_interna`, `keepassxc.orden()`/`orden_externo()`) **only** in this mode: with an empty password, `DatabaseOpenWidget::buildDatabaseKey()` adds no `PasswordKey`, so the auto-unlock that breaks a password + key file base unlocks this one (source reading, 2.7.12: to be confirmed by hand). Before opening, `keepassxc.llave_vale()` probes `keepassxc-cli ls -q --no-password --key-file K BASE` (`sonda_cli()`, an indirection point; `None` = could not probe, which opens anyway): `False` stops with `LLAVE_NO_VALE` and the way to give the right key («Dar el fichero llave…»).
- **A new device with the flag in the remote** (`plan_activar()`, the wizard): only «Traer el del remoto» (an own base is refused: its credentials would not match, and `merge --same-credentials` could not merge it), only on an encrypted device, and the key file must be given (the one saved when the keychain was created): it is **copied** to `.keychain/llave.keyx`, never recorded as a path. `plan_pide_llave()` is refused in this mode; `plan_desactivar()` warns that the key stays (and, with a root pair, that dropping the keychain would let `.keychain/` — key included — travel with it).
- **Creating it** («Ajustes → Llavero → Usar esta base, sin contraseña…», `plan_llave_interna()`; the wizard does not create one, since it needs a console mid-wizard): only with no keychain in the remote, on an encrypted device, with `keepassxc-cli` with `db-edit` (`keepassxc.sin_conversion()`; the pinned 2.7.12 has it, a host ARM64 one below 2.7.6 does not) and a copy path **outside the device and not existing** (`llavero.guardar_copia_llave()`). `hacer()` in this order, undoing everything it created if anything fails **before** the catalogue is written: copy the base (the original is never touched), generate the key, **export the copy of the key** (losing it loses every password), `keepassxc.convertir()` (a visible console like «Combinar», `en_consola()`: `runsync.py --convertir-llavero BASE LLAVE [--actual K]` → `convertir_aqui()` → `keepassxc-cli db-edit [--key-file ACTUAL] --set-key-file LLAVE --unset-password BASE`; the CLI asks the current password, prdrive never sees it, and it **replaces the base's protection**), `llave_vale()` must not say `False`, and only then `catalog.push()`, `[keychain]`, launchers.
- **Merging** in this mode (`sin_contrasena` through `plan_combinar()` → `CombinarPlan` → `keepassxc.combinar()` → `runsync.py --combinar-llavero … --sin-contrasena` → `orden_combinar()`): `merge --same-credentials --no-password --key-file K`, no password prompt. `llavero_editor.llave_de_este_equipo()` returns the device's key and asks nothing. Without the key the plan is refused.
- **Not in v1**: leaving the mode (back to a password), rotating the key, telling devices that already have the keychain, creating it from the wizard, a BitLocker stamp (it is read live, so a device whose BitLocker is suspended simply stops syncing).

## Merging conflict copies («Combinar»)

`conflict-loser = num` leaves the losing save beside the base as `personal.conflicto-remoto1.kdbx` (or `-dispositivo1`; the pair has `versions`, so `--suffix-keep-extension`, which `conflicts.esquema()` now knows). Choosing a version would lose the other's saves; merging keeps both (S4).

**The agent says so** (`Agente._copias_del_llavero()`): it reads what the root's `sync.py` records in `state/conflicts.json` after every pass (`conflicts.actualizar_pareja()`; JSON, not code: the agent has no model of the root), after each keychain pass and otherwise at most every `MIRAR_EMBLEMA` (a merge removes them with no agent pass). One notice per new copy per connection, saying nothing is lost and how to merge (`LLAVERO_EN_CONFLICTO` + `COMBINAR_AQUI`, or `COMBINAR_A_MANO` where prdrive cannot open it: neither Windows nor Linux); none left forgets what was told, so a new conflict with the same name is told again. `resumen()` carries `llavero_conflicto` (the count), and the tray's aviso line leads to «Abrir llavero». Only for a listed root with its code accepted.

- **The plan** is `conflict_editor.plan_combinar(conflicto, llave, abierto)` → `CombinarPlan`, shown through `confirmar_plan()` and run under `working()` because `execute()` waits for a console. It refuses (`ResolucionImposible`) without the base under its own name, without copies, or without `keepassxc-cli.exe` next to `KeePassXC.exe` (`keepassxc.cli()`); with ours open it warns that KeePassXC will reload (S3) or merge its unsaved changes (S5).
- **`execute()`** re-checks size and mtime of every file, then per copy: `keepassxc.combinar(base, copia, llave)` (an indirection point) opens a **visible console** (`CREATE_NEW_CONSOLE`, the runtime's `python.exe`, since the window runs on `pythonw`) running `runsync.py --combinar-llavero BASE COPIA [--keyfile LLAVE]` → `keepassxc.combinar_aqui()` → `keepassxc-cli merge --same-credentials [--key-file …] <base> <copia>` (`orden_combinar()`, `ejecutar_cli()`; `--no-password --key-file` instead of the prompt in the key-file-only mode, above). The CLI asks the password; prdrive never sees it. On failure the console says so and waits for Enter. **On Linux** the console is a terminal emulator (`terminal()`, an indirection point: the first of `TERMINALES` on `PATH`, `x-terminal-emulator` first; none → `SIN_TERMINAL`, an `OSError` that says how to merge from KeePassXC's window). Terminals return at once or hide the exit code, so `--codigo FICHERO` makes the console write its pid at start and its code at the end (`apuntar_codigo()`), and `esperar_codigo()` waits for that file: no pid within `ESPERA_TERMINAL` (30 s), or the pid gone without a code (the terminal was closed), is -1. `cli()` is the drive's AppImage there, and `cli_lanzable()` turns it into the extracted `usr/bin/keepassxc-cli`; `combinar_aqui()` points `KPXC_CONFIG`/`KPXC_CONFIG_LOCAL` at `config/linux/`, or the CLI would create `~/.config/keepassxc` on the host (seen running the real one). Linux ARM64 uses the host's `keepassxc-cli` if it has one; Flathub's has none on `PATH`, so «Combinar» is refused with the window route. Exit 0 (also «not modified») → the copy moves to `.keychain/.prversions/<name>~%Y%m%d-%H%M%S.kdbx` (`en_versiones()`: rclone's own backup naming, so it stops travelling, stops being a conflict, and «Versiones…» lists it); the next pass deletes it on the remote, where the backup dir keeps it. That deletion trips bisync's `max-delete` (25 % of the previous listing, on either side): a keychain holds three or four files, so one copy is already 33 %, here and on every other device that sees it leave the remote. `sync.repetir_sin_freno()` handles it (it also repeats «all files were changed» with `--force`: above): when a keychain pass (not a resync) aborts with «too many deletes» and every «File was deleted» line of its log (`llavero._BORRADO`, rclone's `indent()` format) names a conflict copy of a base (`llavero.solo_copias_borradas()`, through `conflicts.leer_nombre()`), the pass runs once more with `max-delete = FRENO_SIN_COPIAS` (100); a base, `LEEME.txt` or a quoted name among them keeps the brake. Checked with rclone v1.75.1 in the cloud run (`2026-10-05-llavero-nube-resultados.md`). **An rclone bug it works around too**: after a conflict the remote wins, `modifyListing()` (`cmd/bisync/listing.go`, v1.75.1 and `master`) records the local loser's rename by removing the base's name from *both* listings, though the winner was just copied under it; the next pass sees the base «new on both sides», and if it changed here meanwhile (exactly what «Combinar» does) that is a second, spurious conflict whose copy brings nothing. So after every good keychain pass (not `--dry-run`) `sync.reapuntar_llavero()` checks `llavero.sin_listar()` (bases on the drive missing from the path1 listing, read with `listado_local()`) and runs one more pass at once, while both sides are equal: bisync says «Files are equal! Skipping» and lists it again. A failure there is only said. Non-zero → stop, that copy untouched, and the message gives the window route («Base de datos → Combinar desde base de datos…») with the copy's full path (`.keychain` is hidden). Copies merged before a failure stay merged and moved; repeating is harmless.
- **Where it is offered**: «Abrir llavero» (above) and «Reparación», whose conflict section gains a «Combinar» row when the device has the keychain, active only for a conflict on its base. «Quedarme con…» stay, with `PIERDE_LLAVERO` as a warning. Its findings never say «keychain» (`revision.nombre_visible()`). The console fallback of `--llavero` never merges.
- Checked against the real `keepassxc-cli` 2.7.6 when it is installed (`tests/test_llavero_combinar.py`): the built command merges an entry into the base, and a wrong password exits non-zero.

`tests/test_keepassxc.py` (a dict for HKCU, faked processes and launches), `tests/test_keepassxc_linux.py` (the Linux config, command-line ownership, extraction with a fake `--appimage-extract`, the host's KeePassXC, the zombie), the keychain block of `tests/test_tk_servicio.py` (the line, its button, the worst case in the size matrix), `tests/test_llavero_combinar.py`, `tests/test_llavero_activar.py`, `tests/test_tk_llavero.py`, `tests/test_install_llavero.py`, `tests/test_llavero_expulsar.py`, and the keychain blocks of `test_install_wizard.py`; the «Combinar» blocks of `test_tk_reparacion.py` and `test_tk_medidas.py`.

## Ejecting («Expulsar»)

`keepassxc.cerrar_llavero(config)` → `Cierre(listo, lineas)`, the spec's §10 steps 1–5, in two paths (the agent's is phase 3): the window's «Expulsar» (`tk_llavero.cerrar()`, before `cifrado.lanzar_expulsion()`) and `Expulsar PRDRIVE.bat` (`:llavero`, before `/dismount`), which runs `runsync.py --cerrar-llavero` with the device's **console** Python and waits for it. Callers ask «¿Cerrarlo?» first, if ours is open; then it blocks (window: under `working()`).

1. **KeePassXC** from the device (`procesos_de_la_unidad()`) gets `pedir_cierre()` = `taskkill /PID` **never `/F`** (`WM_CLOSE`: with unsaved changes KeePassXC asks), then `esperar_salida()` up to `ESPERA_CIERRE` (180 s). Still alive (a question unanswered, or minimise-on-close) → `Cierre(False, SIGUE_ABIERTO)` and nothing else happens: the drive is not free.
2. **The browser proxy** (`keepassxc-proxy.exe`, stateless, lives as long as the browser: K6, H-16) gets `terminar()` (`/F`).
3. **The watcher**: `parada_vigilante()` touched, then waited up to `ESPERA_VIGILANTE` (90 s). The watcher looks at the stop only **between passes**, and its pass (`runsync.pasada_llavero()` → `run_pair_quiet()`) has **no time limit**: on a slow remote (SFTP over a phone hotspot, a throttled Drive) a pass of a few small files can take over half a minute, and cutting it short only makes step 4 redo it. Past 90 s it is hung, and it holds the volume with the drive's `pythonw.exe` (and, in a pass, its rclone). Then `llavero.terminar_vigilante()` ends it **with its tree** (`llavero.matar_arbol()` → `store.matar_arbol()`: `taskkill /F /T` on Windows, i.e. `TerminateProcess`, never an `os.kill`, which on Windows terminates; `killpg(SIGKILL)` on POSIX, where `lanzar_vigilante()` made it a session leader), waits `ESPERA_MUERTE` (3 s, counted in `dormir()` steps like the other deadlines, so a test with a fake `dormir()` does not wait: dying is not instant) and, if it is gone, removes its `llavero.lock.json` and the stop file, which it can no longer remove. It says so in `state/daemon.log` (`llavero.apuntar_diario()`, which is `store.apuntar_diario()`, the one line-and-trim rule that `runsync.dlog()` uses too; `[llavero] vigilante terminado a la fuerza (pid N)…`) and says nothing to the person.
   - **Its bisync lock is removed too** (`llavero.quitar_candados_muertos()`, only after a termination that worked). A bisync killed mid-pass leaves its `.lck`, and rclone does not check that the pid in it is alive: with `--max-lock 2m` the next pass says `prior lock file found` until it expires, so step 4 would refuse for two minutes and the person would unplug with the save not uploaded (found by review; checked with rclone v1.75.2 by killing a real slow `bisync` with its process group: the immediate re-run refused, and with the lock removed it finished the interrupted transfer). The lock file says whose it is (`"PID"`, rclone's own); only a lock whose pid no longer exists is removed, a live one (another pass in progress) or one that cannot be read stays and expires by itself. The diary says which.
   - **Only if the pid is really the watcher** (`es_el_vigilante()`): a lock left by a watcher that died without cleaning up names a pid the system may have given to another program since, and `vigilante_vivo()` (pid alive, same host and boot) would call it alive. It is never the process that is ejecting nor its parent (`os.getpid()`, `os.getppid()`: ending them would cut the eject itself). Where the command line can be read (Linux, `store.orden_de()`) it must carry `--vigilar-llavero` (`VIGILAR`); where it cannot (Windows) the executable must be a Python (`INTERPRETES`: `python.exe`, `pythonw.exe`) running from the volume (`store.procesos_desde(model.DEVICE_ROOT)`), not an `rclone.exe` or anything else of the drive. Anything else is left alone and the diary says it could not be checked to be the watcher: a pid reused by another program, and also a watcher on a host Python (the light install) on Windows, whose image is not on the volume, so it holds it only through a child (this limit was not run on Windows). **Not checked: the process creation time against the lock's `started`**, which would also tell a reused pid that lands on another Python of the same drive (the service, another window); it needs a Windows-only `ctypes` call (`GetProcessTimes` on another process) that only the Windows CI job can exercise. A process that survives the termination is said too. Nothing of this blocks ejecting: what a hung watcher leaves unsent goes up in step 4, and if that cannot, the person is told (`SUBIRA`).
4. **Pending** (`llavero.pendiente()`) → `llavero.pasada(tope=TOPE_PASADA)` (60 s; past it the whole tree is killed, `matar_arbol()`, or a stray rclone would hold the volume: `SIN_TIEMPO`, 124). Good → silence. Otherwise one line: broken base, conflict copies («Abrir llavero» will offer to merge), or `SUBIRA` («se subirá la próxima vez», no network or no time). None of these blocks ejecting.
5. **The browser keys** back (`cerrar_navegador()`); a failure is a line, never a block.

- **Without VeraCrypt** the window now offers «Expulsar» whenever the keychain is on: it does the above and ends with «Ya puedes quitarla (Quitar hardware de forma segura)», closing the window (whose Python runs from the volume). Asking Windows for the real eject (`CM_Request_Device_EjectW`) is not done.
- **`--cerrar-llavero`** asks `[S/n]` in the `.bat` console (no answer, EOF → close: KeePassXC still asks about unsaved changes) and exits 1 only when KeePassXC stays open; the `.bat` then says so and does not dismount. Any unexpected error prints a line and exits 0: VeraCrypt will still say if something is open, and a bug here must not trap the drive.
- The `.bat` only does it when the drive has the keychain (`Llavero.bat` at its root) and a device Python exists; `expulsar-prdrive.sh` does the same on Linux (`llavero()`, with `llavero.sh` or `Llavero.bat`, the device's Python or the host's: `vestibule.md`); vestibule scripts are rewritten only by provisioning, so older drives get the hook with «Añadir plataformas…» (`vestibule.md`).
- **«Bloquear» an encrypted host root** closes it the same way. The window's (`tk.bloquear()`) runs `tk_llavero.cerrar()` before asking the agent; the agent's (`Agente._bloqueos()` → `_cerrar_llavero()`, also for the tray's «Bloquear») launches the root's `runsync.py --cerrar-llavero` with its own Python and no console before VeraCrypt (no one to answer: it closes, and KeePassXC asks about unsaved changes; `input()` failing with `RuntimeError` under `pythonw` counts as no answer). Exit 1, or longer than `agente.ESPERA_LLAVERO`, means KeePassXC is still open: no lock, a notice, and the root stays served. A root without the keychain locks as before.
- **Pulled out without ejecting**: KeePassXC dies with the drive and the base survives (atomic saves, K7), but the browser keys point at a dead letter. `keepassxc.de_la_unidad()` knows a key is ours and dead without any record: it names `…\<.prdrive>\keepassxc\…` and **that folder** is gone (not the JSON, which KeePassXC writes only once it starts, after «Abrir llavero» set the key). The agent sweeps them (`agente.limpiar_navegador()`, an indirection point: on Windows `cerrar_navegador(carpeta_app=APP_SUBDIR, muertas=True)`, since its own `APP_DIR` is not a `.prdrive`; on Linux `cerrar_navegador_linux(muertas=True)`, prdrive's manifests once no extracted KeePassXC is open) when it starts and whenever a root disconnects, back to an installed KeePassXC if there is one; `Agente._limpiar_navegador()` logs what it touched (keys or manifests) and never raises. Without the agent, the next «Abrir llavero» on that host rewrites them.
  - **On Linux KeePassXC does not die with the drive**: it runs extracted on the host, and would go on with the base in memory, and its passkeys, after the drive is gone. When a root disconnects, `_desconectar()` asks the KeePassXC of that root to close (`agente.cerrar_keepassxc_huerfano(raiz)`, an indirection point, over `keepassxc.cerrar_huerfano(app_dir)`: `llavero.pids_keepassxc()`, whose command lines still name the gone root, then `pedir_cierre()`: SIGTERM, so it asks about unsaved changes), and logs it. The browser waits for it to exit: while an extracted KeePassXC runs, `limpiar_navegador()` touches nothing, so `_desconectar()` leaves it in `navegador_tras_cierre` and `_tras_cierre()` sweeps the manifests on the first turn after it is gone (`agente.keepassxc_huerfano_abierto(raiz)`, an indirection point); a root that comes back first is dropped from it. Checked with the real AppImage: it exits in ~0.5 s, and sweeping right after the SIGTERM left both manifests behind. Without the agent, the keychain watcher does the same when it sees the drive gone (`vigilar_llavero()`, Linux only). On eject or lock it was already closed; on Windows there is nothing to do.
