# The keychain (`common/llavero.py`, `common/kdbx.py`, `common/keepassxc.py`, `common/registro.py`, `install/keepassxc_bin.py`, `install/llavero.py`, `ui/llavero_editor.py`, `ui/tk_llavero.py`)

Formerly: none (new with the keychain). Design and its reasons: `docs/superpowers/specs/2026-10-04-llavero-keepassxc-design.md`; real-hardware findings (K/B/PK/S/H-n codes): `docs/superpowers/pruebas/2026-10-04-keepassxc-portatil-resultados.md`.

A KeePassXC database (passkeys and passwords) travels in `.keychain/` at the volume root, with KeePassXC itself in `.prdrive/keepassxc/`, and syncs by itself against `keychain/` in the remote's catalogue folder. Windows only (x64, and ARM64 running the x64 build emulated); Linux is phase 2 of the spec.

## KeePassXC as a component

- **Pinned** in `pins.py` (`KEEPASSXC_VERSION`, `KEEPASSXC` = `{paquete: (zip, sha256)}`, `KEEPASSXC_PARA` maps each platform to a package: Windows ARM64 uses `windows-x64`, because the only ARM64 ZIP, 2.8.0-beta1, could not talk to the browser, H-7). The sum is written by hand after checking the PGP signature with KeePassXC's key (fingerprint in the docstring); no `.DIGEST` is read at run time (three formats, H-2).
- **`install/keepassxc_bin.py`** follows `veracrypt_bin`: the official ZIP in a per-version cache (`ensure_zip()`, a hand-placed ZIP is verified the same way and a bad one is reported, never downloaded over), every member path validated before the first write (`components.ruta_relativa_segura()`), the single top folder stripped, each written file re-read and re-hashed, the stamp (`PRDRIVE-KEEPASSXC`, version + package + per-file sha256 with relative `/` paths) written **last**, and the folder swapped like `traveler.sustituir()` after a free-space check.
- **Pending** (`components.keepassxc_pendiente()`): unlike rclone, a **missing** KeePassXC counts too, but only when the device has the keychain (`llavero_activo()`: `[keychain]` in its `sync_config.toml`) and only for the packages of the Windows platforms it carries (`paquetes_keepassxc()`). That is how enabling the keychain from «Ajustes» gets KeePassXC: the usual amber «Actualizar…».
- **The applier postpones it** while anything runs from its folder (`store.procesos_desde()`, moved from `install/components.py`, which re-exports it so its tests still patch it there): KeePassXC itself or `keepassxc-proxy.exe`, which lives as long as the browser is connected (K6, H-16).

## The pair, built in code

`[keychain]` in `sync_config.toml` (and the catalogue) makes `model.parse_config()` append `Pair(name="keychain", local=".keychain", remote=<catalog remote>, remote_path=<catalog folder>/keychain)`, bisync with `versions = true` and `LLAVERO_FLAGS` (`conflict-loser = num`, H-14: the loser stays beside it to be merged; `resync-mode = newer`, H-13). The TOML cannot change it: neither `[defaults.flags]` nor `[defaults]` filters reach it.

- **`Config.names` and `Config.del_usuario` leave it out**: the window, the console menu, the service's pair list and «Parejas» (`pair_editor.rows()`) never show it. `Config.pairs` keeps it, last, so `sync.py` with no names runs it, `sync.py keychain` runs it alone, `--list` marks it, and «Reparación», conflicts, versions and `pen_environment()` see it.
- **Its name is reserved** only while `[keychain]` is there (a user pair called `keychain` is a `ConfigError`). The base name must be a bare `*.kdbx`.
- **Filters, generated** (`Pair.reglas`, emitted right after `- .prversions/**` by `filters_content()`): `LLAVERO_REGLAS`, only the bases (`*.kdbx`, conflict copies included thanks to `suffix-keep-extension`) and `LEEME.txt`; never `QSaveFile` temporaries (H-11), `*.old.kdbx`, `.passkey` or plain-text exports (S6).
- **Root pairs** (`local = "."`) get `model.REGLA_SIN_LLAVERO` (`- /.keychain/**`) as their first rule while the keychain is on, so the base never travels by another road. In a bisync pair it precedes the pair's own `+` rules; in copy/sync it is an ordinary `--exclude`, which rclone always adds after the `--include`s (`fs/filter/filter.go`, `NewFilter`), so a root mirror with a broad `include` could still carry it. The agent's `IGNORAR_CAMBIOS` and `install/device.RUIDO` include `.keychain`.
- **Moving the catalogue** (`catalog_path`, `catalog_remote`) changes its `expected_prefix()`, so the defaults plan shelves its baseline like any other (`catalogue.md`); `resync-mode = newer` loses nothing.

## Before every pass (`llavero.preparar()`, from `sync.run_pair()`)

- **The fixed companion**, `LEEME.txt` (H-12: with a single file, a save would read as "every file changed" and bisync would stop). Created if missing with `store.crear_exclusivo()` and the exact bytes of `LEEME_TEXTO` (`\n` on every OS, or two devices would write different files and fight over it); never rewritten if someone changed it. The text never changes.
- **Every base must be whole** (`common/kdbx.py`, no key needed): signatures, the TLV header up to `EndOfHeader`, and for KDBX 4 the header SHA-256 plus the HMAC block chain ending exactly at EOF with a zero-size block. KDBX 3 cannot say where its encrypted body ends; with AES or Twofish (CBC) it must be a multiple of 16 bytes, which catches 15 of 16 random cuts. An unknown format is `None`, not broken. A broken base is looked at again after `ESPERA_ENTERA` (2 s; `llavero.dormir()` is the indirection point); if it is still broken the pass does not run and the pair records `sync.LLAVERO_ROTO` (2), retried on the next pass. Checked by hand against real bases (a KDBX 4.0 and 3.x from KeePassXC's test data, 3.1 from `keepassxc-cli` 2.7.6): no cut of the 4.0 passes, 1 in 16 of the 3.x.
- `.keychain/` is hidden (`store.hide()`) when `sync.py` creates it.

## It resyncs itself

Unlike every other pair, the keychain never waits for a `--resync` approval (`sync._bisync_preflight()`, `engine.md`): with no baseline (first pass, a shelved one after moving the catalogue) or changed filters it resyncs on its next pass, attended or not. `resync-mode = newer` keeps the newer base and the backup dir keeps the other side's in `.prversions/`. It is therefore never a «requiere resync» chip nor a `resync` finding.

## Who attends it, and when a pass is due

One thing at a time, in this order (the spec's §5b):

- **The root's service, if alive here** (`llavero.atiende_el_servicio()`: `model.daemon_lock()` held by a live pid of this host). Both write that file: runsync's service and the resident agent. An agent's record (`"agente": true`) counts only if its `pairs` list `keychain`: an agent from before the keychain (or one that read the config before it was turned on) holds the root without attending it, and the watcher stays. runsync's service is this device's own code, so it always does.
  - **The agent** treats `[keychain]` as a watched pair (`agente.leer_servicio()` appends `keychain` with `vigila=True` and `.keychain` as its folder, whatever the chosen pairs are): its own stat polling and `PoliticaCambios` (`agent-scheduling.md`), and the service interval for the remote.
    - **KeePassXC open** (`Agente._mirar_keepassxc()`, every `PoliticaCambios.sondeo`, only on roots it serves that carry the keychain; `agente.keepassxc_abierto()` is `llavero.keepassxc_abierto()` on the root's `.prdrive/`): the keychain pair gets its own interval, `min(the root's, REMOTO_ABIERTO)` (`pl.Pareja.intervalo`), also on a `sync`-mode root, where nothing else would pull or watch it.
    - **Opening and closing** reset its mark to «never tried», so a pass follows at once: on opening it brings the latest before the base is unlocked (with the agent serving, «Abrir llavero» runs no pass of its own); on closing it uploads the last save. A keychain pass already running defers the change to the next look (that pass may have started before). A root the agent stops serving (its window, a pause) is forgotten, not «closed».
  - **runsync's service** runs one keychain pass after each cycle and, while it waits for the next, `atender_llavero()` every `POLL_SECONDS`.
- **Otherwise, the keychain watcher**, `runsync.py --vigilar-llavero` (`vigilar_llavero()`), started detached by «Abrir llavero» (`llavero.lanzar_vigilante()`, an indirection point in `common/` so the window can call it: no-op if the service attends or a watcher lives). One at a time (`llavero.registro_vigilante()`, `state/llavero.lock.json`, taken with `store.tomar_registro()`). It leaves when the service takes the root, when the device goes, on `state/llavero.stop` (`llavero.parada_vigilante()`, for «Expulsar»; one left over from before it started is removed) and when KeePassXC closes (after `ARRANQUE_KEEPASSXC`, 30 s, if it never saw it), uploading whatever is pending first. cwd in the temp dir, so it never holds the volume.

**The rules are pure** (`llavero.Vigilancia`, the agent's `PoliticaCambios` values): a photo every `sondeo` (10 s) of each base's size, `mtime_ns` and KDBX seed (`llavero.huella()`; the seed tells apart two same-size saves in one exFAT clock tick); a change waits `calma` (20 s, each new save moves it) and at least `separacion` (120 s) since the last pass; with KeePassXC open (`keepassxc_abierto()`: only `KeePassXC.exe` running from the device counts, not the browser's proxy) the remote is pulled every `REMOTO_ABIERTO` (5 min). A failing pass doubles the separation up to `TOPE_REINTENTO` (30 min), so an offline keychain does not retry every two minutes. Whether KeePassXC is open is asked with the photo, not every turn: on Windows it walks every process.

**«Pending upload»** (`llavero.pendiente()`) needs no record of its own: a base differs (size, `mtime_ns`) from its line in bisync's `path1` listing of the last good pass (`listado_local()` parses rclone v1.75.1's `lineFormat`, nanoseconds and zone included). With no listing every base is pending. It also catches a save made **during** a pass (`Vigilancia.acaba_pasada(sin_subir=…)`), which the agent's generic watch absorbs.

## Opening it («Abrir llavero»)

The button of the main window's keychain line, `runsync.py --llavero` (what `Llavero.bat` runs; it does **not** stop the service) and the tray's «Abrir llavero» (`PIDE_LLAVERO` → `Agente._lanzar_llavero()`: that same `runsync.py --llavero` with the agent's windowed Python, cwd `equipo.DIR`, with the window's guards except an open window, which it does not mind; only for a listed root with its code accepted, only where `resumen()["abre_llavero"]`, i.e. Windows). Three layers:

- **`common/keepassxc.py`**, KeePassXC on this host: what is needed (`mirar_apertura()` → `Apertura`, touches nothing) and doing it (`abrir()`). Windows only: `paquete_del_equipo()` (an indirection point) is `windows-x64` on x64 and ARM64, `None` elsewhere (`SOLO_WINDOWS`).
- **`ui/llavero_editor.py`**, no Tk: the window's line (`linea()`: no line without `[keychain]`; amber without KeePassXC or after a failed pass; otherwise open / pending / up to date) and the flow (`abrir(config, avisar, esperar, elegir_llave, decir_sin_traer)`), the spec's §6 steps in order with the three questions passed in as functions.
- **`ui/tk_llavero.py`** gives it Tk dialogs (`avisar()`, `working()`, `elegir_llave()`; the first and last are indirection points). `ui.abrir_llavero()` hangs them off `root_oculto()`; if that root cannot be created, it falls back to the console and asks nothing. A failure halfway never re-runs the steps.

**The steps.** No `[keychain]`, no package, or no `KeePassXC.exe` → say so (the last: «Actualizar…» puts it). **Ours already open** (`llavero.keepassxc_abierto()`) → just launch with the base, which `SingleInstance` hands to the running one and brings to the front; no pass, no question, and its config is not touched (it rewrites it on exit). **Another KeePassXC on this host** (`otro_abierto()`: any `KeePassXC.exe` from `store.procesos()` not running from the device) → say so and stop: ours would hand it the base, with another config. **Bring the latest** (`llavero.pasada()`, `sync.py keychain` with no terminal) when the base is missing, or when the last good pass (`results.ultimas_buenas()`) is older than `DESDE_LA_ULTIMA` (2 min) and no service attends the root (it would collide with the service's own bisync lock). A failed pass still opens; the window says it in its line, standalone says it in a notice (`decir_sin_traer`). No base after the pass → say why and stop. **The key file**, if `[keychain] fichero_llave`: its path on this host (`state/keychain.json`, `{"equipos": {host: {"fichero_llave": path}}}`, `llavero.equipo()` = `prefs.HOST`) if still there, else a file dialog titled with `nombre_llave`, then recorded (`apuntar_llave()`). The file is never opened; cancelling opens without `--keyfile` and KeePassXC asks (`llavero_editor.llave_de_este_equipo()`, shared with «Combinar»). **Conflict copies of the base** (`conflicto_de_la_base()`, a fresh scan of `.keychain/`) → the merge plan through `confirmar` («Cancelar abre KeePassXC sin combinar»); it comes after the pass, which is what brings the copy, and after the key file, which merging needs (the spec listed it before both). Then `keepassxc.abrir()`, and the watcher.

**Config, line by line** (`ajustar_config()`, KeePassXC closed). Lives in `.prdrive/keepassxc/config/windows/`, outside the package folder that `keepassxc_bin` swaps whole, and is passed with `--config`/`--localconfig`. `editar_ini()` changes only the requested keys' lines (case-insensitive, like QSettings on Windows; `Group/Key` → `[Group]`, the rest is `[General]`), appends missing ones at the end of their section or in a new one, keeps every other byte and the file's line ending (`\r\n` for a new file), and reads/writes with `surrogateescape`. Every launch: `SIEMPRE` (`UseAtomicSaves`, H-11; `Browser/UpdateBinaryPath`; `GUI/CheckForUpdates=false`). Only when the file is created: `AL_CREAR` (`Browser/Enabled`, `RememberLastKeyFiles=false`, `UpdateCheckMessageShown`…) and `AL_CREAR_LOCAL` (`Security/QuickUnlock=false`, H-1). Both files always exist after it: `Config::init()` treats a `keepassxc_local.ini` without its `keepassxc.ini` as an old layout and moves it. **Recent paths** (`RECIENTES`, all `Local`) move from the previous root (`raiz.txt`) to this one (`mover_raiz()`: each list element starting with it, with `/` or QSettings' `\\`); a root QSettings would escape (non-ASCII, commas, quotes: `forma_ini()` → `None`) is not searched for.

**The browser** (`abrir_navegador()`, every launch with ours closed): the four `HKCU\Software\…\NativeMessagingHosts\org.keepassxc.keepassxc_browser` keys (`NAVEGADORES`: Chrome shared with Vivaldi and Brave, Mozilla with Tor, H-5; Edge; Chromium) get their default value (QSettings' «Default») pointed at `<exe>\config\org.keepassxc.keepassxc_browser_<name>.json`, where `.portable` puts the JSONs; KeePassXC's `updateBinaryPaths()` rewrites both at start (B2, B3, B5). `common/registro.py` wraps `winreg` (`leer`/`escribir`/`borrar`/`vacia`, HKCU only). **Undoing it** is `cerrar_navegador()` (wired into «Expulsar» later): only keys that are prdrive's (`de_la_unidad()`: inside this volume, or a `…\<app dir>\keepassxc\…` path that no longer exists) go back to an installed KeePassXC's JSON in `%LOCALAPPDATA%\KeePassXC` (any name sharing that key) or are deleted, and `NativeMessagingHosts` goes only if left empty. Never raises.

**Launch** (`orden()`, `entorno()`, `lanzar()`): `KeePassXC.exe --config … --localconfig … [--keyfile …] <base>`, `KPXC_INITIAL_DIR` = the volume root (exports land in sight, PK5), detached, cwd in the temp dir. `esperar_arranque()` watches it for `ESPERA_ARRANQUE` (1.5 s): `VC_FALTA` (`0xC0000135`, both signs) means no Visual C++ runtime (K3) and the notice gives Microsoft's installer (`REDISTRIBUIBLE`, x64 also on ARM64); another non-zero code is said with its value; 0 is a hand-off to a running instance.

## Turning it on and off («Ajustes → Llavero…»)

`tk_llavero.ajustes()` opens at once and reads the catalogue in the background (`segundo_plano`, the same `"catalogo"` read as «Parejas», `catalog.load()`); what it offers depends on the remote's `[keychain]` (`llavero_editor.tabla_remota()`), and every write needs that fresh read (`Catalog.editable`). The decisions are `LlaveroPlan`s in `ui/llavero_editor.py` (`EditPlan` shape, through `confirmar_plan()` and `working()`); `plan.activa` tells the caller to run the first pass.

- **`plan_activar(raw, cat, origen, pide, nombre_llave, llave)`.** `origen` is «Usar esta base…» (a `.kdbx` chosen by the person) or `None`, «Traer el del remoto». A base is checked with `kdbx.comprobar()` (broken → refused; KDBX 3 → warning that KeePassXC converts it to 4; unknown → warning) and its name normalised (`llavero.nombre_de_base()`: `.kdbx` lowercase, because the `+ *.kdbx` filter is case-sensitive; the model now refuses `.KDBX`). **The original is copied, never touched** (`llavero.poner_base()`: temp + re-read + `os.replace`). **If the remote already has a keychain, its base is the one**: the local `[keychain]` is the remote's, nothing is pushed, and a base of one's own goes in as `<base>.conflicto-dispositivo1.kdbx` (`llavero.copia_propia()`, rclone's own Path1 loser name) for «Abrir llavero» to merge; the same happens if `.keychain/<base>` already holds a different file. Otherwise the catalogue gets `[keychain]` first (`catalog.push()`; if that fails nothing local changes), then `.keychain/` (`preparar_carpeta()`: created, hidden, `LEEME.txt`), the copy, `[keychain]` in `sync_config.toml` (validated with `parse_config()` before confirming), `Llavero.bat` and the key file's path on this host. Warnings: a root bisync pair will ask for a resync (it gains `REGLA_SIN_LLAVERO`), and «this host cannot open it yet» (not Windows, or no `KeePassXC.exe`: the amber «Actualizar…» puts it, `components.pendientes()`).
- **`plan_pide_llave()`** writes `fichero_llave`/`nombre_llave` to the catalogue and here (prdrive cannot tell from the KDBX header); refused unless the remote's `[keychain]` is this base. «Dónde está el fichero llave…» only records the path on this host, no plan.
- **`plan_desactivar()`** removes `[keychain]` here, asks the watcher to stop and removes `Llavero.bat` (only if it is still ours, byte for byte). `.keychain/` and the remote stay, and other devices keep it. Warnings: KeePassXC open; a root pair would now carry `.keychain/`.
- **`Llavero.bat`** (`llavero.LANZADOR_BAT`, CRLF, ASCII) is `call "%~dp0runsync.bat" --llavero`: the same Python search as the window. Written on activation, not by the components updater.
- The «Crear una nueva con KeePassXC» exit of the spec is not there: a new base is made in KeePassXC and then given with «Usar esta base…».
- **The rule is one** (`llavero.decidir_alta()` → `Alta(tabla, destino, copia, subir, aviso_formato)`): the window's plan and the installer's both call it and only word it.

### In the installer (step «Llavero»)

`ui/tk_install._paso_llavero()` after «Parejas y configuración», optional («Sin llavero» keeps «Siguiente» on; `_ok_llavero`): «Usar una base propia» (with «La base usa un fichero llave» when the remote has none) or «Traer el del remoto» (only if the catalogue has `[keychain]`), and the key file's path on this host when the base asks for one. `install/llavero.pensar()` re-plans on every change and the step shows what will happen; «Poner el llavero» runs `aplicar()` under `working()`, **outside in**: KeePassXC for every Windows platform the device carries (`keepassxc_bin.instalar()`, the 78 MB download), then `[keychain]` into the catalogue (re-read first: if another device added one meanwhile it stops, since the base would be theirs; `catalog.push(ejecutar=…, donde_pedido=…, cachear=False)` runs through the wizard's rclone and leaves no cache in the installer's own `state/`), then the device: `.keychain/` (`preparar_carpeta(raiz)`), the copy, `[keychain]` in its `sync_config.toml`, `Llavero.bat`, and the key file's path in **its** `state/keychain.json` (`apuntar_llave(…, estado=)`). «Inicialización» then adds `keychain` to the names it resyncs. The «already a prdrive» panel has no «Añadir el llavero…»: an existing device does it from its window («Ajustes → Llavero…», plus the amber «Actualizar…» for KeePassXC), which needs no second connection.

## Merging conflict copies («Combinar»)

`conflict-loser = num` leaves the losing save beside the base as `personal.conflicto-remoto1.kdbx` (or `-dispositivo1`; the pair has `versions`, so `--suffix-keep-extension`, which `conflicts.esquema()` now knows). Choosing a version would lose the other's saves; merging keeps both (S4).

**The agent says so** (`Agente._copias_del_llavero()`): it reads what the root's `sync.py` records in `state/conflicts.json` after every pass (`conflicts.actualizar_pareja()`; JSON, not code: the agent has no model of the root), after each keychain pass and otherwise at most every `MIRAR_EMBLEMA` (a merge removes them with no agent pass). One notice per new copy per connection, saying nothing is lost and how to merge (`LLAVERO_EN_CONFLICTO` + `COMBINAR_AQUI`, or `COMBINAR_A_MANO` where prdrive cannot open it); none left forgets what was told, so a new conflict with the same name is told again. `resumen()` carries `llavero_conflicto` (the count), and the tray's aviso line leads to «Abrir llavero». Only for a listed root with its code accepted.

- **The plan** is `conflict_editor.plan_combinar(conflicto, llave, abierto)` → `CombinarPlan`, shown through `confirmar_plan()` and run under `working()` because `execute()` waits for a console. It refuses (`ResolucionImposible`) without the base under its own name, without copies, or without `keepassxc-cli.exe` next to `KeePassXC.exe` (`keepassxc.cli()`); with ours open it warns that KeePassXC will reload (S3) or merge its unsaved changes (S5).
- **`execute()`** re-checks size and mtime of every file, then per copy: `keepassxc.combinar(base, copia, llave)` (an indirection point) opens a **visible console** (`CREATE_NEW_CONSOLE`, the runtime's `python.exe`, since the window runs on `pythonw`) running `runsync.py --combinar-llavero BASE COPIA [--keyfile LLAVE]` → `keepassxc.combinar_aqui()` → `keepassxc-cli merge --same-credentials [--key-file …] <base> <copia>` (`orden_combinar()`, `ejecutar_cli()`). The CLI asks the password; prdrive never sees it. On failure the console says so and waits for Enter. Exit 0 (also «not modified») → the copy moves to `.keychain/.prversions/<name>~%Y%m%d-%H%M%S.kdbx` (`en_versiones()`: rclone's own backup naming, so it stops travelling, stops being a conflict, and «Versiones…» lists it); the next pass deletes it on the remote, where the backup dir keeps it. Non-zero → stop, that copy untouched, and the message gives the window route («Base de datos → Combinar desde base de datos…») with the copy's full path (`.keychain` is hidden). Copies merged before a failure stay merged and moved; repeating is harmless.
- **Where it is offered**: «Abrir llavero» (above) and «Reparación», whose conflict section gains a «Combinar» row when the device has the keychain, active only for a conflict on its base. «Quedarme con…» stay, with `PIERDE_LLAVERO` as a warning. Its findings never say «keychain» (`revision.nombre_visible()`). The console fallback of `--llavero` never merges.
- Checked against the real `keepassxc-cli` 2.7.6 when it is installed (`tests/test_llavero_combinar.py`): the built command merges an entry into the base, and a wrong password exits non-zero.

`tests/test_keepassxc.py` (a dict for HKCU, faked processes and launches) the keychain block of `tests/test_tk_servicio.py` (the line, its button, the worst case in the size matrix), `tests/test_llavero_combinar.py`, `tests/test_llavero_activar.py`, `tests/test_tk_llavero.py`, `tests/test_install_llavero.py`, `tests/test_llavero_expulsar.py`, and the keychain blocks of `test_install_wizard.py`; the «Combinar» blocks of `test_tk_reparacion.py` and `test_tk_medidas.py`.

## Ejecting («Expulsar»)

`keepassxc.cerrar_llavero(config)` → `Cierre(listo, lineas)`, the spec's §10 steps 1–5, in two paths (the agent's is phase 3): the window's «Expulsar» (`tk_llavero.cerrar()`, before `cifrado.lanzar_expulsion()`) and `Expulsar PRDRIVE.bat` (`:llavero`, before `/dismount`), which runs `runsync.py --cerrar-llavero` with the device's **console** Python and waits for it. Callers ask «¿Cerrarlo?» first, if ours is open; then it blocks (window: under `working()`).

1. **KeePassXC** from the device (`procesos_de_la_unidad()`) gets `pedir_cierre()` = `taskkill /PID` **never `/F`** (`WM_CLOSE`: with unsaved changes KeePassXC asks), then `esperar_salida()` up to `ESPERA_CIERRE` (180 s). Still alive (a question unanswered, or minimise-on-close) → `Cierre(False, SIGUE_ABIERTO)` and nothing else happens: the drive is not free.
2. **The browser proxy** (`keepassxc-proxy.exe`, stateless, lives as long as the browser: K6, H-16) gets `terminar()` (`/F`).
3. **The watcher**: `parada_vigilante()` touched, then waited up to `ESPERA_VIGILANTE` (it finishes a pass it is in).
4. **Pending** (`llavero.pendiente()`) → `llavero.pasada(tope=TOPE_PASADA)` (60 s; past it the whole tree is killed, `matar_arbol()`, or a stray rclone would hold the volume: `SIN_TIEMPO`, 124). Good → silence. Otherwise one line: broken base, conflict copies («Abrir llavero» will offer to merge), or `SUBIRA` («se subirá la próxima vez», no network or no time). None of these blocks ejecting.
5. **The browser keys** back (`cerrar_navegador()`); a failure is a line, never a block.

- **Without VeraCrypt** the window now offers «Expulsar» whenever the keychain is on: it does the above and ends with «Ya puedes quitarla (Quitar hardware de forma segura)», closing the window (whose Python runs from the volume). Asking Windows for the real eject (`CM_Request_Device_EjectW`) is not done.
- **`--cerrar-llavero`** asks `[S/n]` in the `.bat` console (no answer, EOF → close: KeePassXC still asks about unsaved changes) and exits 1 only when KeePassXC stays open; the `.bat` then says so and does not dismount. Any unexpected error prints a line and exits 0: VeraCrypt will still say if something is open, and a bug here must not trap the drive.
- The `.bat` only does it when the drive has the keychain (`Llavero.bat` at its root) and a device Python exists; vestibule scripts are rewritten only by provisioning, so older drives get the hook with «Añadir plataformas…» (`vestibule.md`).
- **Pulled out without ejecting**: KeePassXC dies with the drive and the base survives (atomic saves, K7), but the browser keys point at a dead letter. `keepassxc.de_la_unidad()` knows a key is ours and dead without any record: it names `…\<.prdrive>\keepassxc\…` and **that folder** is gone (not the JSON, which KeePassXC writes only once it starts, after «Abrir llavero» set the key). The agent sweeps them (`agente.limpiar_navegador()`, an indirection point, Windows only: `cerrar_navegador(carpeta_app=APP_SUBDIR, muertas=True)`, since its own `APP_DIR` is not a `.prdrive`) when it starts and whenever a root disconnects, back to an installed KeePassXC if there is one; `Agente._limpiar_navegador()` logs what it touched and never raises. Without the agent, the next «Abrir llavero» on that host rewrites them.
