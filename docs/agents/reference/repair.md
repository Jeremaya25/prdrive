# «Reparación» (`common/revision.py` + `common/frenos.py` + `ui/repair.py` + `ui/tk_repair.py`)

Formerly AGENTS.md «Reparación».

**One diagnosis, three layers.** `revision.revisar(config)` returns `Hallazgo`s (clave, título, detalle, pareja, gravedad, dato); `revision.informe(config)` returns the same thing as the text `sync.py --doctor` prints (all `doctor()` does now). It lives in `common/` because **`sync.py` does not import `ui/`**: a diagnosis on the window's side would be a second one and the two would drift. `ui/repair.py` answers "and what do I do about it" with plans in the `EditPlan` shape (`consequences`/`warnings`/`execute()`); `ui/tk_repair.py` only draws.

- **What has a button.** `prefijo` shelves the baseline (`bisync.shelve_baseline`); `lock` deletes the stray `.lck`s; `resync` and `fallo` are not disk plans (a pass through `lanzar`; opening the log); `freno` has three buttons under its text («Forzar sincronización…», «Ver qué se borraría», «Ver el log»: below).
  - **A missing local dir deliberately has none**: creating it is exactly what `_bisync_preflight()` refuses when a baseline exists, because an empty local side reads as "everything was deleted". The screen says so instead.
  - Nor does **`catalogo`**: the remote's catalogue folder holds both `remote.toml` and `pairs.toml` (a push raced the rename, `catalogue.md`). It is read from `state/catalog.json` (`catalog.duplicado()`), no network; the fix («apartar» the stray `pairs.toml`) is a remote operation and lives in «Ajustes → Catálogo del remoto».
  - Nor does **`espacio`**: a *dynamic* (sparse) VeraCrypt container with under `vestibulo.UMBRAL_LIBRE` (1 GiB) free on the physical drive. It grows as it is written, so when the drive fills the inner volume throws I/O errors mid-pass and rclone cannot say why; the fix is freeing space outside. `revisar(config, fisica=)` takes the physical root when the caller already looked it up (`None` = not in a container; the default `vestibulo.BUSCAR` looks it up itself), so the window's read finds it once (`ui.md`, «One read per refresh»).
- **`prefijo` accuses only what it can check** (#37). The expected prefix of a pair over an rclone `alias` is the one of the alias's *target* (`engine.md`, «Session prefix»), so a healthy alias pair has no finding. If the alias cannot be followed (`bisync.prefijo_comprobable()` is false: no `remote`, a cycle, a target missing from `rclone.conf`, a connection string) `revision._prefijo()` returns nothing, and `--doctor` says «no se puede comprobar» on the `prefijo esperado` line. Not a `NOTA` either: its chip reads «se arregla sola», and the same `clave` would bring back the «Apartar el baseline…» button.
- **A `resync` of a root pair that uploaded the program says where the copy is.** `revision._resync()` puts `(<remote folder>,)` in `dato` (a tuple: `Hallazgo` is frozen) and a sentence in the `detalle` when `revision.carpeta_programa_en_remoto()` finds it (`engine.md`); `()` otherwise. `repair.aviso_resync()` turns it into a warning before the resync («bórrala tú», `revision.aviso_carpeta_programa()`), because the code never deletes the remote copy and the new listing will no longer show it. The main window's prompt and `sync.py`'s say the same through the same two functions; «Reparación» is not the only way to a resync.
- **Deleting a lock asks who is syncing first.** `repair.sincronizacion_en_curso()` reads `model.daemon_lock()` and errs towards "yes, someone is": another host's record cannot be checked with `pid_alive`, and refusing to delete costs nothing while deleting under a live pass does.
- **A `fallo` says since when** (#20): `revision._fallos()` adds one sentence from the pass journal, «Falla desde el 12/09 · 0 de las últimas 14 bien.» («al menos desde» when every recorded pass failed: the streak may predate the journal). It goes in the `detalle`, so `--doctor` prints it too; with no journal, or one whose last line is not a failure, the finding reads as before.
- **A delete brake is its own finding, not a `fallo`** (#94). `common/frenos.py` recognises, in the log of the last failed pass, the aborts that `--force` / `--max-delete -1` skip, and it is the ONE place both `sync.py` (`KNOWN_ERRORS` takes `frenos.ENTRADAS`) and `revision._fallos()` read them. There are two brakes, **in two units** (`AGENTS.md`, «Safety invariants»): bisync's is a **percentage** of the previous listing (`Safety abort: too many deletes (>25%, 8 of 10) on Path1 "…"`, `excessDeletes()` in `cmd/bisync/deltas.go`; nothing was propagated when it stops) and a mirror's is a **count** (`Got fatal error on delete: --max-delete threshold reached`, `StatsInfo.DeleteFile()` in `fs/accounting/stats.go`: rclone deletes exactly up to the limit, exits 7, leaves the rest, which it counts in `failed to delete N files`, and what it already deleted stays deleted). bisync has a third abort skipped by the same `--force`, `Safety abort: all files were changed on PathN` (`cmd/bisync/operations.go`; the `CAMBIADOS` kind). `Path1` is `Mode.source` (the device) and `Path2` `Mode.dest`; for a mirror the side is its destination. A text speaks only its own unit (percentages for bisync, file counts for a mirror). `Freno` carries the figures, and any rclone did not give stay `None` (a log without `--verbose` has no `Deleted` lines; a changed sentence still gives the kind, from the final `Failed to bisync: …`). `frenos.detectar(texto, pair)` only looks for the brake of the pair's own mode, so a bisync log on a mirror (or on a `copy`) is nothing. The logs in `tests/_logs_frenos.py` are real, captured with the pinned rclone (v1.75.2) through `sync.run_pair()`.
  - **It replaces the pair's `fallo`, never adds to it**: `revision._fallos()` reads the log of each failed pair (`frenos.detectar_en()`: the last 4 MiB, which holds the abort and the `failed to delete N files` line; what needs the WHOLE log, how many files a mirror had already deleted, stays `None` and goes unsaid when the log is bigger than that) and builds a `freno` (AVISO, the figures and the side in the `detalle`, so `--doctor` prints them too, plus the «Falla desde…» sentence; `dato = (log, Freno)`, so «Ver el log» still reads `dato[0]`). With no log, an unreadable one, or a log that is not a brake, it is the `fallo` as before. A brake by size (`--max-delete-size threshold reached`, bytes) is **not** recognised and stays a `fallo`: forcing `max-delete` would not skip it, and the old bare `--max-delete` needle explained it as a count by substring. The keychain's pair is not in `Config.names`, so `results.fallos()` leaves it out, but `_fallos()` adds its last pass (`results.fallos_de([model.LLAVERO])`) and keeps it **only when it is a brake** (#115): `sync.repetir_sin_freno()` runs first (conflict copies; «all files were changed» once with `--force`), so a keychain brake that gets here is one that stayed after its repeat. `_hallazgo_freno()` words it apart: «El llavero: …», says what happened, that prdrive repeats it once by itself when it can (without saying it did: the repeat may not have run, or the simulation before it may have refused) and what to do (`frenos.salida_llavero()`: `python sync.py keychain --resync` for «all files were changed», «Combinar» for deletes), never the «Si es lo que querías, se puede forzar» of the other pairs, and no button but «Ver el log» (`puede_forzar()` and `puede_simular_forzado()` exclude it). A keychain failure that is not a brake (no network) has no finding: the window's keychain line says it and the pass retries by itself.
- **«Forzar sincronización…» skips the brake for ONE pass, after a plan** (#94). Not a disk plan: `repair.aviso_forzar(config, hallazgo)` returns a `RepairPlan` with nothing to `execute()` (like `aviso_resync()`) that goes through `tk_pairs.confirmar_plan()`, and confirming closes the screen and launches `args_forzar()` (`[pair, "--force"]`) through `lanzar`, with `devolver(True)`; cancelling does nothing. `sync.py` turns `--force` into what skips each mode's brake (`engine.md`). The plan says, with the figures, what will be copied or deleted and where; that if that side is unmounted, empty or the wrong folder the loss spreads; the mode's way out (bisync: check that side, or a `--resync`, which brings the missing files back from the other side; mirror: fix the origin and the next pass copies what is missing; a mirror keeps no versions, bisync says whether the pair does); that the next pass brakes again, with the cap rclone will really get (`orden.max_delete_efectivo()`: the last `--max-delete` it receives, however it is written; in bisync a negative one is its 50 % default, in a mirror it means no cap); and it recommends «Ver qué se borraría» (`repair.ETIQUETA_SIMULAR`).
  - **It refuses, and the case is not offered** (`ReparacionImposible`): a missing local folder (the `_local` finding's case: `_bisync_preflight()` aborts with rc 2 and a missing side reads as «everything was deleted»), bisync with no baseline (what is needed is a `--resync`), the keychain pair (`puede_forzar()` excludes `model.LLAVERO`: its bases are passwords, its way out is «Combinar»; the same rule, `frenos.se_puede_forzar()`, keeps `--force` off its command and refuses `sync.py keychain --force`, `engine.md`), a finding that is not a brake or carries no `Freno`. An empty local folder is a warning, not a refusal («parece desmontada»). Like every button it acts on `repair.vigente()`'s fresh finding.
  - **«Ver qué se borraría»** (`puede_simular_forzado()`: only where there are deletions, not for `CAMBIADOS`) launches the same pass with `--dry-run` (`args_forzar(simular=True)`) and **no confirmation**: it writes nothing. A good dry run prints only «OK» and its log is thrown away, so `sync.decir_lo_que_borraria()` reads the log (the WHOLE of it: the figure is what a person decides on, and a mirror whose source got unmounted can have 100 000 lines) before `dispose_log()` and prints the files it would delete (first 20, sorted, `frenos.borrarian()`; only when `--dry-run` and `--force` go together, so no other simulation changes). It counts rclone's `Skipped delete` and, with `versions = true`, `Skipped move into backup dir` (what is deleted goes to `.prversions/`: `DeleteFileWithBackupDir()`), and not the overwrites of such a pair (`Skipped move to <name>~<stamp>`, `Skipped copy`). When it finds none it says the log noted no deletion, never that none would happen: a false «nothing would be deleted» right before forcing is the worst answer it can give.
  - **No unattended path passes `--force`.** The service launches `sync.py NAME`, `--auto --once` only names, the agent `sync.py -- NAMES`, and the main window never builds it; `sync.py` itself refuses `--force` with no pair named, which is what `runsync.py --daemon --force` would otherwise reach. `tests/test_forzar_desatendido.py` pins each launcher's argv and scans the sources: only the modules in its `PERMITIDOS` name `--force`, and a new one has to be added there with its reason.
- **The first paint may be older than the click, so no button trusts it.** `tk_repair.construir(..., compartida=)` paints its list from the main window's shared read (`compartida.para(config).hallazgos`) when there is one that is still valid and whose `hallazgos` did not fail (`ui.md`, «One read per refresh»), else from `revision.revisar()`. Before `aplicar` and `resincronizar` make any plan, `repair.vigente(config, hallazgo)` re-runs `revisar()` and returns the finding with the same `(clave, pareja)` as it is *now*, or `None`: then the screen says «Esto ya no está: …», repaints, asks for no confirmation and touches nothing; the plan is made from the fresh finding, never from the one on screen. If `revisar()` itself fails, it says so and makes no plan. «Ver el log» only opens a file and does not ask. Every repaint after that (`repintar()`: after executing, after resolving a conflict) reads `revisar()` and never the shared read.
- **A plan checks again when it runs.** `RepairPlan.execute()` can come minutes after the plan was thought (the confirmation is modal): `plan_locks`'s `hacer()` calls `sincronizacion_en_curso()` again and raises `ReparacionImposible` if someone is syncing now; `plan_apartar`'s checks `pair_state(pair).has_baseline` again, so a baseline another screen shelved meanwhile is not shelved twice.
- **Nothing repairs itself**, on open or on click: every plan goes through `tk_pairs.confirmar_plan()`. After executing, the screen re-runs `revisar()` whole instead of crossing out the row it just fixed.
- **The conflicts are a section, not a window**: `tk_conflicts.seccion()` builds the tree into whatever frame it is given; there is no `open_dialog`, so the only way in is «Reparación». With the keychain it has a «Combinar» row under the buttons, active only for a conflict on its base (`conflict_editor.plan_combinar()`, `llavero.md`).
- **The keychain is never named by its pair**: titles go through `revision.nombre_visible()` («El llavero», not «keychain»), its conflicts read «El llavero: la base tiene copias de conflicto» and point at «Combinar», and the conflict list shows «(el llavero)» (`conflict_editor.nombre_pareja()`).
- **The main window says it in one line**: `revision.cuenta()` in the header chip plus one line with a «Reparación…» button, hidden while a pass runs (the rule that disabled the old per-fault blocks' buttons). The update/components block stays separate: an offer is not a fault, and counting them together made everything weigh the same.
