# Commands, verification and test conventions

Formerly AGENTS.md «Commands» (full list), its verification notes, and the registry of indirection points from «Conventions».

## Commands

```bash
python sync.py [pares...]      # every pair in sync_config.toml, or only these
python sync.py --list          # pairs + resolved endpoints (safe, read-only)
python sync.py --doctor        # bisync state: prefixes, filters, locks
python sync.py --dry-run       # simulate; MANDATORY before any *-mirror run
python sync.py --resync        # rebuild the bisync baseline
python sync.py -y/--yes        # auto-approve the resync question (cron/scripts)
python sync.py --keep-logs     # keep logs of successful runs too

python runsync.py              # UI (Tk, console fallback) + periodic service
python runsync.py --auto       # periodic service with the service's config, no UI
python runsync.py --auto --once  # one pass of the service's pairs, then exit
python runsync.py --llavero   # «Abrir llavero» without the window (what Llavero.bat runs)
python runsync.py --vigilar-llavero  # the keychain watcher (started by «Abrir llavero»)
python runsync.py --combinar-llavero BASE COPIA [--keyfile K] [--sin-contrasena]  # the «Combinar» console
python runsync.py --convertir-llavero BASE LLAVE [--actual K]  # the console that leaves a base key-file only
python runsync.py --cerrar-llavero   # what Expulsar PRDRIVE.bat runs before dismounting
python runsync.py --doctor     # any other args pass straight through to sync.py

python penwatch.py install|status|probe|uninstall   # the watcher, per machine/user
python agente.py run|status                         # the resident agent (host copy)
python agente.py atender ID | modo ID MODO | pasada ID [pareja…] | pausa | sigue | parar
python agente.py abrir [ID]                         # the window of the host root (the menu entry;
                                                    # starts a stopped agent, and with no root says how it is)
python agente.py desbloquear [ID] | bloquear [ID]   # open / close the encrypted host root
python agente.py ajuste pedir_al_iniciar sí|no      # or espera_unidad_nueva SEG
python agente.py actualizar                         # fetch the new release and put it in place
python agente.py actualizar ID                      # put that root on the agent's version (the tray's «Actualizar a la vX»)
python agente.py expulsar ID                         # release that removable drive (the tray's «Expulsar»)
python pregunta.py --nombre N --segundos S [--cambiada]  # the «¿Atender esta unidad?» window, what the agent
                                                    # launches (`agente.py pregunta` is the fallback if it is missing)

python prdrive-install.py          # install wizard for a NEW device (Tk only)
python prdrive-install.py --check  # rclone + connection + catalogue, then exit
python prdrive-install.py --probe  # what drives it sees, then exit
python prdrive-install.py --update E:\             # the device's code only
python prdrive-install.py --update-components E:\  # its rclone + runtime only
python prdrive-install.py --instalar-agente        # the resident agent on THIS host
python prdrive-install.py --desinstalar-agente     # and off again (no drive touched)
python prdrive-install.py --update-agente          # the installed agent (and open host roots) to this version
python prdrive-install.py --autoprueba RUTA        # CI: the built .exe's windowless self-test (JSON; hidden from --help)
python build_installer.py          # build the .exe (embeds the profile if any); refuses without the pinned PyInstaller and a Python with Tk 9
python -m ui.icons                 # repaint APP_DIR/runsync.ico (headless)

python tests/run_all.py -j N|auto  --display inherit|xvfb  --gui-jobs K  --timeout S  [files]  # all tests; or run one script directly
python tests/_runtime_ci.py clave|runtime PLAT DESTINO CACHE  # the CI's pinned runtime, Python 3.14.8 with Tk 9.0.4 (key / fetch)
python tests/_runtime_ci.py compilador windows-x64 DESTINO CACHE  # the same runtime unpruned, with pip: the .exe's builder
python tests/rendimiento/correr.py --pr DIR --base DIR --trabajo DIR [--python PY] [--rondas 7] [--capturas]  # the timing check (CI)
python tests/integracion/llavero_real.py --de-verdad  # the keychain end to end, for real (CI only)
python tests/maquina/correr.py --lista           # checklist rows with a cloud real-machine test (F9, F14…)
```

`runsync.py` with no args always **stops a previously started service** first.

## Verification

Verification is `tests/run_all.py` (each script in its own process), `--doctor` and `--dry-run`. Nothing to lint. `run_all.py` runs the files one at a time, in alphabetical order, unless `-j N|auto` runs N at once: each file gets its own `TMPDIR` and `HOME` (removed afterwards); `--display xvfb` gives each worker its own X server (1920x1080x24 per worker), and without Xvfb the display of the process is used; `--gui-jobs K` caps how many Tk files (`GUI`) run together (1 on a shared display, unlimited with `xvfb`); `GUI_NO` lists the files that import Tk without opening a window, each with its reason; `SERIE` runs after the pool, one at a time: `test_avisos_carpeta.py` (it watches the machine's mounts), `test_vestibulo.py` on Windows (a process name searched system-wide), and `test_superficie.py` and `test_tk_tabla.py` on a shared display (pixels and focus). `--timeout S` (600 s by default) kills a hung file with its whole process tree. Ctrl-C (or SIGTERM) stops the run: nothing else starts, the files still running are killed with their trees and waited for before the temporaries are removed (a second Ctrl-C repeats the kill and does not cut that wait), and it exits 130 with no summary. A name that is not a test file exits 2. A file whose worker's X server dies while it runs fails (`Xvfb murió durante el test`), and that worker takes no more files. A file that gets no result (the suite itself fails while running it, or its worker stops) counts as a failure, `sin resultado`; no file passes without one. `tests/test_run_all.py` checks these lists against the sources. The last line is the same as before: `FALLAN n de N: …` or `Los N ficheros de test pasan.`. **Tk 9 is the only Tk the windows are tested on** (owner's decision, 09/10/2026; `ui.md` «Which Tk»). CI (`.github/workflows/tests.yml`) runs `run_all.py` on every PR and push to `main` (except pushes that only touch `docs/superpowers/` or `docs/guia/`) in two kinds of job. Job `tests` (checks `tests (ubuntu-latest)` and `tests (windows-latest)`) runs the **whole suite** with the device's pinned runtime (`common/pins.py`: Python 3.14.8, Tk 9.0.4), as `run_all.py -j auto --display xvfb` on Linux and `-j auto --gui-jobs 1` on Windows (one desktop, so the windows take turns); it is the only place the windows and the SVG path run (`tests/test_iconos_svg.py` compares the SVG path with the Python painter by flipping `icons.USAR_SVG` on that Tk, which is also what keeps the painter covered; `ui.md` «Icons carry alpha»). Job `python-minimo` (check `Python 3.11 sin pantalla (ubuntu-latest)`) runs `run_all.py -j auto` on `setup-python` 3.11 with no display and no `python3-tk`, to hold the **Python floor** (3.11, for `tomllib`) of everything that is not a window. It exists because `sync.py`, `runsync.py --auto`, `penwatch.py`, `common/` and `install/` also run on a **host** Python, not the pinned one: the light install's `runsync.pyw`, `runsync.bat`/`.sh` falling back to the host's `pythonw`/`python3` when the device has no runtime for that machine, `penwatch.py` likewise (`penwatch.md`), `python sync.py` by hand, the installer run from a clone. Every Tk test skips itself there; it is Linux only because a Windows runner always has a desktop and python.org's 3.11 carries Tk 8.6, so a Windows 3.11 job would run all the windows again on the Tk that is no longer supported. `PRDRIVE_SIN_SVG=1` makes `ui/icons.py` use its Python painter on a Tk 9 too (`icons.USAR_SVG = False`, read at import): `PRDRIVE_SIN_SVG=1 xvfb-run -a <runtime>/bin/python3 tests/run_all.py` runs the whole suite through the painter, a local aid that no CI job runs (the painter is a Tk 8.6 leftover kept for devices still on the 3.13 runtime; `test_iconos_svg` already covers it by flipping the switch). `PRDRIVE_PERF=1` turns on the windows' own timings, written to `logs/perf.log` (`ui.md` «Timing on the device»); it is off in every test run, and the tests that check it set it themselves (`tests/_perf.py`). That runtime is fetched in a step before the suite (the suite never touches the network) by `tests/_runtime_ci.py`, which uses the installer's own `runtime_bin` (SHA-256 checked against the release's `SHA256SUMS`) and leaves the interpreter in `PRDRIVE_PYTHON`; Actions caches the archive under `runtime-<plat>-<key>`. Each job runs as an unprivileged user (a check that writes to `/` fails there), and no test may depend on what the real `%LOCALAPPDATA%` caches hold. The PR template still asks how it was checked. Tk tests skip themselves without a display **or without `tkinter`**, so an all-green run without Tk has tested no window.

**The installer build** (`.github/workflows/instalador.yml`, «Instalador»: PRs touching `build_installer.py`, `prdrive-install.py`, `install/**`, `common/pins.py`, `tests/_runtime_ci.py`, the action or the workflow; by hand) builds `dist/prdrive-install.exe` on `windows-latest` through the composite action `.github/actions/compilar-instalador`, exactly as the release does: the device's pinned runtime unpruned (`_runtime_ci.py compilador`), the pinned PyInstaller, `build_installer.py` (strict everywhere, not only here), then the gate, `--autoprueba` on the built `.exe` (3 minutes at most). It checks the action's `exe` output and uploads the `.exe` and `autoprueba.json` (artifacts `prdrive-install`, `autoprueba`). Locally only the Python half runs: `tests/test_build_installer.py` (the build checks refuse, with fake `PyInstaller` and `tkinter` modules, so the Tk 9 leg covers the Tk 8.6 refusal too) and `tests/test_autoprueba.py` (the self-test from the `.py`: exit 0 on the Tk 9 leg, 1 on the Tk 8.6 one; and `_autoprueba_superada()`, the gate that lets an `.exe` out, with synthetic reports that need no display, failing ones included); that PyInstaller bundles the pinned Tk 9 into a working `.exe` is only seen in an `Instalador` run (`provisioning.md` «The PyInstaller build»).

**The keychain for real** (`.github/workflows/llavero-real.yml`: PRs touching the keychain, and by hand) runs `tests/integracion/llavero_real.py` on `ubuntu-latest` (xvfb) and `windows-latest`. It is not a `test_*.py` (`run_all.py` never sees it) and refuses to run without `CI` or `--de-verdad`: it downloads the pinned rclone and KeePassXC, provisions a device in a temp dir with `install/deploy` and a `local` remote, and drives the device's own code one step per process (activate, «Abrir llavero», a save the watcher uploads, a real two-sided conflict merged by `plan_combinar()` with the password on stdin instead of a console, the deletion the delete brake must let through, `--cerrar-llavero`, then the key-file-only premises with the real CLI: `db-edit`, the `ls --no-password` probe, `merge --no-password`), checking what KeePassXC itself writes: the HKCU keys and the JSON it rewrites at start on Windows, the manifests on Linux, and a `change-public-keys` through the proxy they name. On Linux it points `HOME` and the XDG dirs at the temp dir. The cloud run that found the bugs it now guards: `docs/superpowers/pruebas/2026-10-05-llavero-nube-resultados.md`.

**Real-machine rows in the cloud** (`.github/workflows/maquina-real.yml`: a push to a non-`main` branch touching `tests/maquina/**` or the workflow, PRs touching what they test, and by hand with `inputs.pruebas` once the file is on `main`) run `tests/maquina/correr.py` on `ubuntu-latest` (as root) and `windows-latest` (as admin). One module per row of the real-hardware checklist (`fNN_*.py`: `CODIGO`, `SISTEMA`, `QUE`, `probar(p)`), checking only the OS boundary: real filesystems on virtual disks (loop, VHD via `diskpart`), the real tray window, VeraCrypt installed with `choco`, a network share of the machine itself, `max_user_watches`. The log ends with one `RESULTADO <code> <W|L> ok|parcial|fallo|saltada …` line per row; results go to `docs/superpowers/pruebas/maquina-real-resultados.md` and an `ok` row is marked `· nube: ok` in the checklist, not removed. How to run and read it cheaply: the `real-machine-tests` skill (`.claude/skills/`). F21 (`.pyc` between filesystems) cannot share the matrix, because its halves pass a tree between them: `pyc-linux` precompiles the program with the pinned runtime and uploads it as the `f21-arbol` artifact, and `pyc-windows` checks it on FAT32 and exFAT with the pinned Windows Python; in the matrix it reads `saltada`.

- The suite passes on Windows **and** Linux. A check about the other system's branch forces it (`IS_WIN`, and for a Linux mount point `Unidad.letra`) in any system, or prints `(saltado) …` when it cannot run there (Unix sockets, the Linux tray's `select()` on a pipe).
- `tests/_harness.py` points `equipo.DIR`, `XDG_DATA_HOME`/`XDG_CONFIG_HOME`/`XDG_CACHE_HOME` and `keepassxc.bases_navegador()` (the browsers' manifest folders, Firefox's under the home folder) at temp dirs for every test, so no test sees or deletes the runner's agent, menu entries, extracted KeePassXC or browser manifests, and turns `os.kill(pid, 0)` into a real question on Windows: there 0 is `CTRL_C_EVENT`, a Ctrl+C to the whole console, and forcing `IS_WIN = False` reaches it.
- **`tests/_vista.py` reads what a Tk screen shows**, for tests that compare two screens (an in-place update against the same screen drawn again): `a_la_vista(widget)` (the widget and every ancestor below its toplevel have a geometry manager; a `grid_remove`d frame hides its children), `visibles(raiz, clase, texto)` and `leer_vista(raiz)`, one tuple per visible widget, depth-first, in reading order (`grid` by row and column, `pack` in packing order, `place` by position; ties broken by class, text, style and image, never by creation order). It reads class, text, style without `Sobre<RRGGBB>.`, ttk state minus `ESTADOS_IGNORADOS` (`active`, `focus`, `hover`, `pressed`, `alternate`, `background`, `user1`–`user3`), image name, cell, `wraplength` and the value of the bound variable; not widget names, padding, child windows, or the root's own cell. It asserts nothing. `tests/test_tk_vista.py`.
- **A path the code under test will open is a `tmpdir()`, never a drive letter or a fixed absolute path.** The harness cannot redirect a path a test writes into the settings: `test_install_agente` registered a locked encrypted root at `P:\` (the letter the wizard proposes), and on a dev machine with a real prdrive mounted at P: `actualizar()` saw its control file and deployed the checkout's code onto it. A letter is fine only where a fake answers for it (`expulsar`, `veracrypt_command`, log lines). Likewise a check that depends on this host's CPU or OS picks its platform explicitly, or empties the cache it reads: on Windows ARM64 «the Linux of this CPU» is `linux-arm64`.
- **Pixels are read where they can be.** `tests/test_superficie.py` checks every rounded control's four corner pixels against its surface by capturing the window with ImageMagick's `import` (X11 only, 24-bit screen, `imagemagick` in the Linux CI steps); anywhere else it prints `(saltado) …` and the half that asks ttk (`style.lookup(style, "background", state)` for the live widget) still runs. The two-pixel-radius pieces (`FINOS`) come out blended with their border and are compared against the proportion measured on the paper.
- **A test that moves Tk with `update()` while a real worker thread runs calls `gc.collect()` first.** A `tkinter.Variable` left in a reference cycle by an earlier window, collected by the GC from the worker, calls Tk from that thread, and outside `mainloop()` `_tkinter` waits 1 s for it before raising «main thread is not in main loop» (printed as `Exception ignored in: Variable.__del__`): two of them made the QR pane's code arrive after `tests/test_tk_apartados_lectura.py`'s 2 s wait on Windows. Inside `mainloop()` (the real app) the call is handed to the Tk thread instead. The collection on a worker is rare, so a missing call shows up only now and then; to force it, wrap `threading.Thread.run` so every thread starts with `gc.collect()`, and every such `Variable` prints that line.
- Tk 9.0.4 (the pinned runtime) is the only Tk the suite opens windows on; the Tk 8.6 leg was dropped on 09/10/2026. See «The UI is tested on Tk 9» in `provisioning.md`.

## Timing check

`.github/workflows/rendimiento.yml` (PRs touching `ui/`, `common/`, `install/`, `runsync.py`, `sync.py`, `agente.py`, `pregunta.py`, `penwatch.py`, `prdrive-install.py`, `build_installer.py` or `tests/rendimiento/**`, and by hand) runs `tests/rendimiento/correr.py` on Windows x64 and Linux x64 with the pinned runtime (Windows ARM64 only by hand: tick «arm64»). A **draft** PR runs **3 rounds** (`RENDIMIENTO_RONDAS`: a quicker, rougher signal, so its verdict can fail on noise that a ready PR's 7 rounds would absorb); a ready PR takes **7**, and marking a draft ready runs the check again. A run by hand takes its `rondas` input (default 7). Not a `test_*.py`: `run_all.py` never collects it. Its pure part, the verdict, is tested by `tests/test_rendimiento_informe.py`.

- **How:** the PR tree and its base tree (two checkouts) are measured **in the same job, with the same interpreter and the same driver** (`driver.py`, from the PR tree: it knows how to reach each screen, the tree only supplies code). One round is one pass of each tree and the order alternates between rounds, so a drift of the machine hits both. Each pass is a cold process on a fresh copy of a sample device (5 or 50 pairs, `dispositivo.py`), with a fake `HOME` and a deadline (the whole process tree is killed). The one exception is what a device remembers once it has been opened (`correr.RECUERDOS`: the main window's remembered width and the heights of the bands above and below its list, the whole `state/ventana.json`): it is copied back to the template after each flow, so from the warm-up round on every measured pass opens a device that was opened before, as a real one is; a tree that does not write it (0.7.1) is unaffected. Flows (`PLAN`): «Parejas» and «Ajustes» with 5 pairs, with 50 and at 150 % (`tk scaling 2.0`), the main window (`principal`) with 5 and 50 pairs at 100 %, «Dispositivos» and the flags editor (`flota`, 5 pairs, 100 %), the wizard, the agent's question and the pass window with 10 000 lines. `suelo.py` times an empty Tk window to normalise. `--capturas` leaves one PNG per screen, which proves the machine paints.
- **What fails a PR** (`informe.py`): (1) a deterministic count above its ceiling in `presupuesto.toml` `[techo]`/`[techo.<system>]` (widgets per screen with 5 and 50 pairs; `widgets.main_leida` (`.p5`/`.p50`), the main window's widgets once the shared read has put the pairs in its list (`llega-instantanea`, the `principal` flow); `<<ThemeChanged>>` passes when opening screens, ttk styles created after the first widget, modules imported before the first paint, `escrituras.marcar`: the `store.write_json` calls to the device inside the click on a pair's checkbox, 1 in 0.7.1; `widgets.dispositivos` and `widgets.flags`, below); (2) a moment whose median is more than 25 % **and** 30 ms slower than the base's, with the best time also more than 30 ms slower (a noisy neighbour ruins medians, not minimums); (3) a moment or count the base reaches and the PR no longer does (the driver cannot find a button: update `driver.py` in the same PR). The time targets of the spec (`[meta_ms]`) and the count targets (`[meta]`) are only reported in the job summary.
- **Ceilings are a ratchet:** a PR that lowers a count lowers its ceiling in `presupuesto.toml` (the summary says when one can drop); raising one is said in the PR description. `[techo.windows]`/`[techo.linux]` replace `[techo]` per system, because the modules imported differ.
- **Once a window is open** (the driver measures these after the open, `[meta_ms]` carries the spec's targets for Windows x64):
  - `parejas`: `catalogo-llega`, `elegir-fila` (`lista.elegir(otra, avisar=False)` and its `update()`), `elegir-pareja` (`avisar=True`: the editor loads) and `reabrir-parejas` (close «Parejas», click «Parejas…» again). The catalogue `Event` is cleared before the reopening and released after recording it, so the remote's arrival (a repaint that took over a second on 0.7.1) never lands inside the measure.
  - `ajustes`: the four panes, `pane-otra-vez` (a pane already visited) and `volver-ajustes` (from the moment the patched `wait_window` destroys «Ajustes» until the main window is quiet again).
  - `principal`: `llega-instantanea`, `marcar` (with `escrituras.marcar`), `sincronizar-ventana` (click until the pass window is viewable) and `volver-pasada` (destroying the finished pass window until the main window is quiet). The checkbox is ticked (unticked first, untimed, if it was ticked) so the selection is never empty: with nothing ticked «Sincronizar ahora» does nothing and 0.7.1 writes no empty selection.
  - `flota` (opened from «Parejas», whose catalogue `Event` is held for the whole flow, so it paints from the local copy): «Dispositivos…» opens with the fleet not yet read (`open-dispositivos`, with `tema.abrir.dispositivos` and `estilos.dispositivos`); then the driver releases the notes, waits with `time.sleep` (never `update()`) for `dlg.sondeo._encargo.hecho` and times `dlg.sondeo._mirar()` plus the `update()` that paints the table and the card (`llega-flota`, whose widget count is `widgets.dispositivos`: the one that grows with devices); `elegir-dispositivo` is `dlg.tabla.elegir(otra)` and its `update()` (`[meta_ms]` 16, like `elegir-fila`); back in «Parejas» the driver clicks the editor's «Mostrar» («Avanzado») and «Editar flags…» (`open-flags`: `widgets.flags`, `tema.abrir.flags`, `estilos.flags`). A missing button, or an «Editar flags…» that is off (a read-only editor), is an error in `_notes`, not a missing moment without a cause. None of these counts carries `.p5`: the fleet and the pair are always the same.
  - **The sample fleet** (`driver.py`, `flota_de_muestra()`, built with the tree's own `fleet.Dispositivo`/`fleet.Equipo` and only the fields every version has) replaces `fleet.leer()`: 12 devices, from 0 to `MAX_EQUIPOS` equipos each; the second is this device's id; three fail with a `last_result` long enough to wrap at 440 design px; the last one has not been seen for ten days (it shows dimmed). The first (the most recent, the one the window selects on arrival) fails and has five equipos: the tallest card. Dates count back from now, so what is dimmed, what fails and how many widgets the card takes never change. The read waits on `ESTADO["flota"]`, which the flow clears before opening «Dispositivos…» and releases at the end; open by default, so no other flow can hang on it.
  - `wizard`: after `start-wizard` the driver clicks «Siguiente» on «¿Dónde?» (its default answer, «En una unidad», allows it) and times the first paint of «Dispositivo» (`paso-dispositivo`). The real `device.list_volumes()` of the machine runs: in the click on 0.7.1, in a thread once the wizard reads after painting. No count: its widgets are in the line's `detail`.
  - **No real pass ever runs:** the driver replaces `ui.tk.orden_sync` (the pass is `python -c pass`) and `ui.tk.preguntar_resync` (answers no), and wraps `store.write_json` to count the calls under the device. Both trees look those names up in `ui.tk` at call time.
  - **The shared read** (`root.instantanea`, `root.sondeo_instantanea`, set by the main window of the PR) is collected after the first paint and after `cancel_afters(root)`: sleep (never `update()`: pumping the loop would run the module preload in the PR only and bias «Parejas»/«Ajustes») until `root.instantanea.hecho`, then time `sondeo_instantanea._mirar()` plus `root.update()`. It is collected in the four flows that start from the main window (`parejas`, `ajustes`, `principal`, `flota`), so «Parejas», «Ajustes», «Dispositivos» and the clicks start from the same content a 0.7.1 window has from its first paint, and only `principal` records `llega-instantanea`. A tree without those attributes (0.7.1) skips it. That record also carries, to locate the cost (reported, never judged): `fases` (ms in `VistaPrincipal.aplicar()`, in the visor's `encajar()`, in all of `_mirar()` and in the `update()` that paints), `expose` and `configure` (`<Expose>`/`<Configure>` events per widget class during the timed span, counted through a binding on the `all` tag, restored afterwards) and `geometria` (widgets that moved, were resized or are new). They are in the run's `crudo.jsonl` artifact, not in the summary. The «Ajustes» pane moments (`pane-*`, `pane-otra-vez`) carry the same breakdown (`driver._trazar()`), with `fases` `clic` (the button's command, which builds or shows the pane), `update` (the paint) and the dialog's `encajar`; `llega-flota` too (`mirar`: applying the fleet notes, `update`), and so does `paso-dispositivo` (the wizard: `clic`, `update`). The warm-up round (ronda -1) runs with `BENCH_PERFIL=1`, so each moment of an action in the window (not the start-up ones: `start-*`, `apply-*`, `cold-parejas`) carries `detail.perfil` in `crudo.jsonl`: the 25 functions of most cumulative time while its timed span ran (`[function, file:line, calls, cumulative ms, own ms]`, from cProfile, the harness's own files left out). From Python 3.12 cProfile profiles the whole process, background threads included, and with a thread running its cumulative figures are approximate: a cumulative can pass the span (in a check run, `revisar` reads 159 ms in a 122 ms span of `paso-dispositivo` on the PR) or fall short of the time really spent. The table locates the cost, it does not add it up. The measured rounds never carry it, and the medians ignore the warm-up; `informe.cuentas()` does read the warm-up, merged with the measured rounds, so a count that a profile had changed would show there as a second value.
  - **Every step works on both trees:** a moment only the PR has reads «nuevo» in the summary, never a failure; one the base reaches and the PR does not fails (update `driver.py` in the same PR).
- **Never a required check:** it is path-filtered and the machine varies from one run to another.
- **`--env CLAVE=VALOR`** (repeatable) adds a variable to the environment of every child the check starts. With `--env PRDRIVE_PERF=1` each pass also leaves in `--salida` the device's `perf.log` and the host's, as `perf-<árbol>-<flujo>-<pares>[-150]-<ronda>.log` (round `-1` is the warm-up): the moments the driver times and the window's own marks, for the same pass. `--env` is not a CI input; a local run passes it by hand.
- The wizard flow, the agent flow and the main-window flows drive real buttons by their labels («Parejas…», «Ajustes…», «Sincronizar ahora», the sidebar's «Reparación», «Nombre e icono», «Actualizaciones», «Configuración»), the fleet's and the flags editor's buttons («Dispositivos…», «Mostrar», «Editar flags…»), the wizard's «Siguiente», the checkboxes by class (`ttk.Checkbutton`, the topmost visible one) and the pass window as a `Toplevel` child of the root whose title ends in «— OK»: a PR that renames or replaces one updates `driver.py`.
## Indirection points

Everything that touches the network, a real device or the desktop is a **module-level indirection point so every test can replace it**. Keep new ones in that shape. A module imported inside a function (`ui/__init__.py`, `ui/tk.py`, `common/update.py`, `runsync.py`: `ui.md`) is patched on the module itself (`update.fetch = …`, `llavero.pasada = …`), never through the importer's namespace; the names tests do replace through another module's namespace (`runsync.ui`, `runsync.prioridad`, `runsync.model`, `ui.tk.pair_status_notes`, `ui.tk.abrir`, `uitk.mostrar`…) stay imported at module level. Registry:

- **Network and downloads**: `catalog.run()` (`fleet` and `remote_picker` go through it; it has an optional `apuntar` that no caller passes, so a stub takes just `args`; `tests/_rclone_falso.py` is a POSIX `sh` script standing in for the rclone binary, `catalog._binary = lambda: falso`, which echoes or sleeps by `$PRDRIVE_FALSO_MODO`), `update.fetch()`, `rclone_bin.fetch()`, `runtime_bin.fetch()` (also the Tk-with-Xft package; `runtime_bin.cache_dir()` too), `veracrypt_bin.fetch()`/`ensure_veracrypt()`, `keepassxc_bin.fetch()`, `descarga.esperar()`.
