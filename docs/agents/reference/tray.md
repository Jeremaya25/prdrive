# The tray (`ui/bandeja.py`, `ui/bandeja_windows.py`, `ui/bandeja_linux.py`) and the global shortcuts (`ui/atajos.py`, `ui/atajos_linux.py`, `ui/tk_atajos.py`)

Formerly AGENTS.md «The tray (phase 4: Windows; phase 6: Linux)». Core of the agent: `agent.md`; the window's side of the conversation: `agent-window.md`.

Same split as the rest of `ui/`: **`ui/bandeja.py` decides, `ui/bandeja_windows.py` and `ui/bandeja_linux.py` draw**, and none imports tkinter (`tests/test_install_agente.py` checks it).

## What it shows and asks (`ui/bandeja.py`, pure)

- **`bandeja.vista(resumen)` is pure**: from `Agente.resumen()` (what goes to `estado.json`: `equipo` = each host root with its state, `pedir_al_iniciar`, and per drive `en_lista`/`ahora_no`/`preguntando`/`error`/`fallando`) it returns the icon, the tooltip and the menu tree. Every `Entrada` carries **mailbox-shaped requests** (`equipo.PIDE_*`); the agent takes them through `Agente.pedir()` → a `queue.SimpleQueue` drained in `_buzon()` together with the file mailbox, so there is one handler for both. Requests the tray adds:
  - `PIDE_ABRIR`: the window of a root. `_lanzar_ventana()` checks only the UI lock (our own service lock is expected and runsync pauses it); a locked encrypted root is unlocked first with `abrir=True` and its window opens on connect.
  - `PIDE_EXPLORAR`: its folder in the file manager. `agente.explorar()` (indirection point) over `orden_explorar()`: `explorer.exe <folder>` on Windows, never `os.startfile()` and its Shell verbs on a drive root; `xdg-open` on Linux. Same guard as `PIDE_ABRIR` in `Agente._abrir(…, explorador=True)`; a locked encrypted root is unlocked first with `Desbloqueo.explorar` and its folder opens on connect, no window.
  - Both, for a **listed drive that is locked**, unlock it first too (the tray itself sends neither for one today; the shortcuts below do): locked with BitLocker (`_bloqueada_bitlocker()`), Windows' prompt through `_desbloquear_bitlocker()`, which returns whether a prompt is up (one already open counts, no second one); a VeraCrypt drive whose closed vestibule the walk has made stable (`_cerrada_veracrypt()`: in `vestibulos`, not connected nor in `vistas`, not mode `nada`), VeraCrypt through `_abrir_vestibulo()` → `abrir_contenedor()`, even with its «Pedir la contraseña al conectarla» off (the person asked), but not again within `GRACIA_ABRIR` of the last time the agent asked it for that drive (`vestibulos_pedidos`, written by the plug-in open in `_vestibulos()` too), because `open_container()` returns no process to follow; with nothing to open it with, a notice points to the drive's own «Abrir PRDRIVE» / `abrir-prdrive.sh`. With the prompt up, `_abrir_al_abrirse()` records an `AlAbrirse` (`al_abrirse`: window and/or folder, renewed on every request) that `_conectar()` honours like `Desbloqueo.abrir`/`.explorar`, after the fingerprint (a drive whose code changed is asked about and opens nothing) and never a second window in mode `ui`; it is dropped after `ESPERA_ABRIR` (`_seguir_desbloqueos()`, and checked again at connect), so a drive unlocked much later does not open by itself.
  - `PIDE_DESPERTAR`: back from suspend: re-read battery/network, probe every offline remote now, burst the walk. Windows sends it twice, so a second one within `DESPERTAR_DOBLE` is not logged again.
- **Tooltip**: «prdrive · sincronizado hace 5 min» = `resumen()["ultima_pasada"]` (`Agente.ultima_buena`, set on `OK` only) put into words by `bandeja.hace()`. `vista(resumen, ahora)` takes the clock, and `_escribir_estado()` compares the **vista**, not the summary, because the «hace» changes on its own.
- **No grey status header in the menu.** At the top, only when something is wrong, go up to `MAX_AVISOS` lines (`bandeja._avisos()`, one list shared with `avisos()`). Each is **clickable and leads to its fix**: a failing pair, a pair that needs `--resync` (`saltadas`, «… necesita --resync», fixed in «Reparación») or a drive's config error → «· Abrir…» its window; an offline remote → «· Probar ahora» (`PIDE_SONDEAR`: its probe now, nothing else re-read); a ghost → «· Bloquear»; a keychain with conflict copies (`llavero_conflicto`) → «· Combinar…» (`PIDE_LLAVERO`, where the keychain opens) or «· Abrir…» its window, whose «Reparación» shows them. What has no fix from here (a missing root) stays greyed out.
- **Icon priority** (`bandeja.estado()`): pause > a pass in flight > avisos (failing pairs, a root's `error`, offline remotes, a missing root, a ghost) > held by battery/metered (pause icon) > a root paused from its window (pause icon and its name, #64) > an encrypted root locked (not an aviso: it is the normal state) > a listed drive locked with BitLocker (the same lock badge, «<name> bloqueada») > bien. The five `.ico` are `icons.capas_bandeja()` (the brand plus a corner badge whose **colour** is what reads at 16 px), painted by `copiar_codigo()` and, if missing, by the agent on start (`write_bandeja(solo_si_faltan=True)`), never copied.
- **A device is named by `common/nombres.py`** (`agent.md`, «The name shown for a drive»): `bandeja.vista()` only draws the `nombre` that `resumen()` gives it, for a connected drive, a drive locked with BitLocker (`bandeja._bitlocker()`) and a root of this host. With no name of its own it is the volume's label or «prdrive · <4 of the id>», with the host behind it only if two read the same.
- **Never «Configurar» nor «Abrir en explorador» for a drive that is not in the list**, even asked by hand: the first runs its code before the yes, and the folder follows the same rule. Its submenu reads «… (sin atender)» and holds only «Atender…».
- «Cerrar el agente» is `PIDE_PARAR`: the next logon starts it again. There is no other way to close a tray icon.
- **A medium that comes back without the letter changing** (#128). `IOCTL_STORAGE_LOAD_MEDIA` on a device that stayed (the case that left the agent ~2 minutes without seeing it, `RECORRIDO_RESPALDO`) does not arise with a pendrive any more: «Expulsar» retires the device, so putting it back is a new device and arrives as always (`DBT_DEVICEARRIVAL` → `montajes()`). A card reader or any device whose letter stays still has no notice Windows is known to send, and then the backup walk finds it. The tray never filtered on `DBTF_MEDIA`: `_mensaje()` reads no flags, so any `DBT_DEVICEARRIVAL` (a volume with its letters, `DBTF_MEDIA` or not) is a mount change (`tests/test_bandeja_windows.py` pins it). What is not known is whether Windows sends one for a medium that returns: row X10 of the pending list.
- **Walks with a tray**: `cmd_run()` bursts on `WM_DEVICECHANGE` and falls back to `RECORRIDO_RESPALDO` (30 s), or to 5 s while a listed drive locked with BitLocker is in sight (`Agente.cada_recorrido()`, `agent.md`); without one (`poner_bandeja()` → None, an indirection point) it keeps penwatch's 5 s. On Linux the walk is mountinfo's either way; the tray changes nothing there.

## One submenu per device (#68)

The host roots first, then the connected drives, each an `Entrada` with `hijos` and its `emblema`, and inside (never repeating the name): «Configurar» (`PIDE_ABRIR`, first, the submenu's `defecto`), «Abrir en explorador» (`PIDE_EXPLORAR`), «Abrir llavero» (`PIDE_LLAVERO`, icon `I_LLAVERO`; only when the drive carries the keychain, `resumen()` `llavero`, read like the emblem at most every `MIRAR_EMBLEMA`, and `abre_llavero`, Windows and Linux (`agente.ABRE_LLAVERO`); greyed with Configurar, and absent on a locked root, whose `[keychain]` cannot be read; with the tray's «Pausar», battery or power saving holding passes, the agent also queues an urgent keychain pass so it opens with the latest, `Agente._traer_al_abrir()`; `llavero.md`), «Sincronizar ahora» (that device only, live when `atendida`) and, for an encrypted root, «Bloquear»/«Desbloquear…» and the `pedir_al_iniciar` checkbox; «Expulsar» for a drive the agent says is `expulsable` (below), «Actualizar a la vX» when the agent says `actualizable` (`bandeja._poner_al_dia()`: «Actualizando a la vX…» greyed while it runs, with Configurar/Abrir greyed; the greyed «Actualízala para que la atienda» for a «por actualizar» device it cannot update, i.e. an unlisted one; `agent-window.md`); last, after a separator, a greyed «Versión X» (`bandeja._version()`, from the drive's `version` in `resumen()`: `Agente._version_de()` reads its `VERSION` on connect and then at most every `MIRAR_EMBLEMA`, so an update from its window shows without replugging; nothing when unknown, so a locked root has none). A locked root's «Configurar…»/«Abrir en explorador…» unlock first (the ellipsis says a password comes).

- **«Expulsar» (`PIDE_EXPULSAR`) is only for a *compatible* volume.** The agent decides (`resumen()["expulsable"]`, `Agente._expulsable()`): a drive in the list with its code accepted, not a host root (a folder), not updating or locking, whose volume `expulsar.compatible()` accepts (`agent.md`). `bandeja._expulsar()` puts it after the update line, behind a separator and before the version, and **leaves it out** for every other device, not greyed: an unlisted drive keeps only «Atender…», an encrypted one is closed with «Bloquear»/«Expulsar PRDRIVE» (`vestibule.md`). While it runs (`expulsando`) it reads a greyed «Expulsando…», and Configurar/Abrir are greyed too. Its icon is `I_EXPULSAR` (`icons.GLIFOS["expulsar"]`; Linux theme name `media-eject`). On Windows it retires the DEVICE (`CM_Request_Device_EjectW`, `agent.md`), so the letter leaves Explorer and the notice says «Ya puedes quitarla»; a veto says why (the program, service or device Windows names).

- **A listed drive locked with BitLocker** (`resumen()["bitlocker"]`, `bandeja._bitlocker()`; how the agent knows: `agent.md`) gets its own submenu after the connected drives: «<name> (bloqueada)», always with `bandeja.MARCA` (nothing of a locked device is read), and one entry. That entry is «Desbloquear…» (`PIDE_DESBLOQUEAR` with its id, the submenu's `defecto`, so a double click on the submenu picks it on Windows), or the greyed «Desbloqueando: la contraseña la pide Windows» while Windows' prompt is open. It is not an aviso and has no line at the top of the menu.

The rule: what is about ONE device goes in ITS submenu; what is about the whole agent stays outside («Pausar»/«Reanudar», «Atajos de teclado…» (below), «Actualizar» or, while no newer version is known, «Buscar actualizaciones» (`PIDE_BUSCAR_VERSION`, `agent-window.md`), «Cerrar el agente», and «Sincronizar todo ahora» only with two or more `atendida` devices: with one it would repeat its own). The menu's last line, after a separator, is the agent's own version, greyed («Agente X», `bandeja._version_del_agente()`, from `resumen()["version"]`). Abnormal states go in the label, in parentheses (`ESTADO_DE_RAIZ`: «bloqueada», «no responde», «no está en su sitio»…; a drive «sin atender», «código cambiado»; root or drive «por actualizar», `POR_ACTUALIZAR` (older than `VERSION_MINIMA`, or an update left it `a_medias`), whose Configurar/Abrir/Sincronizar are greyed because `Agente._abrir()` refuses it; root or drive «en pausa», `EN_PAUSA`, when its window paused it, #64). What cannot be done is greyed, so a root's submenu keeps its shape.

- **«Pedir la contraseña al conectarla» is per drive, inside ITS submenu** (#123; `bandeja._pedir_al_conectar()`, after the update line and a separator, before «Expulsar» and the version). It is the `Unidad.pedir_al_conectar` of that drive and is asked with `PIDE_AJUSTE_UNIDAD` (`id`, `clave`, `valor`: the opposite of what the box shows). The tray draws what the agent says: the entry is there only when the drive's row carries a non-empty `cifrado` and a boolean `pedir_al_conectar` (`agent.md`), so a normal drive, a drive that is not served (unlisted, «código cambiado», «por actualizar») and a summary from before the setting have none. The locked BitLocker submenu gets it too, after «Desbloquear…» (which stays the `defecto`). A VeraCrypt drive that is closed has no submenu, so its box is changed with it open.
- **`pedir_al_iniciar` stays global** (one key in `agente.json`, one `PIDE_AJUSTE`; the window's checkbox is unchanged). It is the encrypted host root's; the per-drive one above is a different setting. Several encrypted host roots can exist (`PIDE_RAIZ` adds one per wizard run; `raiz_para_abrir()` already handles more than one), so with exactly one it goes in that root's submenu, where it reads as its own and is; with two or more it goes outside, worded «Pedir la contraseña de cada raíz cifrada al iniciar sesión».
- **The device icon (`bandeja.Emblema`) is decided by the agent, as data.** `Agente._emblema(con)` → `volumen.emblema(donde, APP_SUBDIR)` reads the `autorun.inf` where «Nombre e icono…» writes it: the connection's root (`con.raiz`), which for a drive in a container or an encrypted host root is the mounted volume and returns `{"marca": clave}`, `{"ico": path}` or `{}`; `resumen()` carries it per drive as `emblema`. Only for a LISTED root with its code accepted and a valid version, connected (so unlocked); read on connect and then at most every `MIRAR_EMBLEMA` (60 s), so an icon changed from the window shows within a minute without reading the drive every turn. `bandeja._emblema()` checks `en_lista` again: an unlisted, changed, old or locked device always gets `bandeja.MARCA`. `clave_de(icono, app=)` exists because the agent's `APP_DIR` is its own folder, not `.prdrive`.
- **Parsing policy.** A brand colour (`icono-<clave>.ico`, the key is in the name) is never read: the tray paints the brand in `icons.CAMPOS[clave]` (`icons.pixeles_marca()`/`png_marca()`). A user's `icono-propio-<hash>.ico` is passed by path, only where prdrive would put it (so it cannot leave the root) and under `icons.MAX_ICO` (4 MiB, the same cap `volumen.leer_ico()` applies).
  - Windows lets Windows parse it (`LoadImageW(LR_LOADFROMFILE)` → `DrawIconEx` into the menu DIB, `alfa_desde_mascara()` for icons without alpha): what Explorer already does with that `icon=` on every plug-in, so no new exposure.
  - Linux reads it with `icons.png_de_ico()`, strictly bounded (`MAX_IMAGENES_ICO`, every image inside the file, square, ≤ 256 px): a PNG entry goes as-is after its signature and IHDR; a 32-bit DIB entry is decoded (alpha, or its AND mask) and re-encoded with `icons._png()`; 8/24 bits are not understood.
  - VeraCrypt's exe, an `OTRO` icon or anything that fails → the brand. Never raises out of the menu. Cached by path, size and mtime (the name already changes with the drawing) in a bounded cache (`bandeja.CacheAcotada`, `TOPE_CACHE` entries, the oldest out): every save of «Nombre e icono…» is a new key.
- **Click on the submenu itself.** Windows: the submenu's default item is what a **double click** on the submenu item picks («Default Menu Items» in *About Menus*), so `SetMenuDefaultItem` on «Configurar» (bold) makes a double click on the device open its window, and `TrackPopupMenu` returns its id; a single click opens the submenu as everywhere in Windows (making it act would need a menu hook and break the normal way to open it). Linux: dbusmenu has no default entry and the known hosts send no `clicked` for a `children-display = submenu` node (Qt's importer, GNOME AppIndicator's `PopupSubMenuMenuItem`); acting on one would open the window on the click that opens the submenu, so `Menu.pulsada()` ignores it and «Configurar» is the path. `Vista.defecto()` (Linux `Activate`) is the first device's «Configurar».

## Menu icons

`Entrada.icono` is a `bandeja.I_*` key, the name of a glyph in `icons.GLIFOS`: what the entry means, not how it is drawn.

- **Windows draws its own menu** (the «Rediseño prdrive» board «Bandeja del sistema»): every item is `MFT_OWNERDRAW` (set with `SetMenuItemInfoW` after `AppendMenuW`, so the text stays for screen readers and keyboard), `itemData` is its index in `Dibujo.filas`, and the tray window hands `WM_MEASUREITEM`/`WM_DRAWITEM` to `Api.medir()`/`Api.pintar()`. What a row looks like is pure and tested without Windows: `aspecto(oscuro, ppp)` (the tokens: surface, accent-soft for the row under the pointer or with its submenu open, ink, disabled, ink-3 for the chevron, line-soft; 34 px rows, 16 margins, 12 gap, a 20 px icon column, 13.5 px Noto Sans, scaled by `LOGPIXELSY`) and `pintura(entrada, estado)` (default bold, a checked entry shows the `ok` glyph, a disabled one is grey and never highlighted, no icon → text at the margin). The theme is read **at every opening** (`theme.sistema_oscuro()`: the agent lives for days); the font is the bundled one when `theme.cargar_fuentes()` loaded it into the process (Api calls `theme.nitidez()`), else Segoe UI. `SetMenuInfo(MIM_BACKGROUND | MIM_APPLYTOSUBMENUS)` paints the menu's margins in the surface colour. `pintar()` ends with `ExcludeClipRect` of the whole row, because Windows draws its submenu arrow afterwards on the same DC and it would land on the chevron (`icons.GLIFOS["derecha"]`). Text is measured with `DrawTextW(DT_CALCRECT)`, the call that draws it. Glyphs and emblems go through `GdiAlphaBlend` from premultiplied DIBs, cached per process (`_glifo()`, `_emblema()`). If fonts or brush cannot be made (`_preparar()` raises), the menu is Windows' own with the glyphs as `hbmpItem` below. The frame (border, corners, shadow) stays Windows'.
- Without the owner-drawn menu, Windows paints that glyph as the item's `hbmpItem` (`icons.pixeles_menu()`): a 32-bit top-down DIB with premultiplied alpha, at `SM_CXSMICON`, in the menu's text colour (`GetSysColor`). The bitmaps are created per menu and deleted after `DestroyMenu`.
- Linux sends the desktop theme's name (`bandeja_linux.ICONOS_DEL_TEMA`, `icon-name`), so it follows the theme's colour and dark mode. `tests/test_bandeja_linux.py` checks every key has a theme name.
- A device submenu carries an `Entrada.emblema` instead (a colour icon, not a glyph): Windows paints it into the same DIB (`bandeja_windows.pixeles_emblema()`, cached in `Api._pixeles`); Linux sends `icon-data`, the PNG bytes dbusmenu takes (`bandeja_linux.png_emblema()`, `TAMANO_EMBLEMA` = 32 px).

## Windows (`bandeja_windows.Bandeja`)

Runs its own thread with its window and message loop. The agent talks to it only via `PostMessageW` (`poner()`, `globo()`, `cerrar()`); it talks back via `pedir()` and `montajes()` (→ `Vigia.despertar()`, which on Linux writes a pipe polled beside mountinfo). Everything Win32 is in `Api`; `tests/test_bandeja_windows.py` drives the rest with a fake one and a real queue-based loop. Not to weaken:

- **A hidden top-level window, not a message-only one** (the spec said message-only): those get no broadcasts, and `WM_DEVICECHANGE` for volumes (VeraCrypt's `BroadcastDeviceChange()`) and `TaskbarCreated` are broadcasts.
- **Device events of a handle** (`DBT_DEVTYP_HANDLE`: the directory handle of a watched pair, which `common/avisos_carpeta.py` registers on this window) go to `Bandeja.dispositivo` (the engine's `dispositivo()`, set by `agente.poner_avisos_carpeta()`) BEFORE the window answers: with `DBT_DEVICEQUERYREMOVE` Windows waits for that answer and the handle must be closed by then. `Api.aviso_de(lparam)` reads the `DEV_BROADCAST_HDR` and returns `(handle, guid, letters)`: of a `DEV_BROADCAST_HANDLE`, its handle and its `dbch_eventguid` (`guid_de()`, the text form in lower case), which is how a `DBT_CUSTOMEVENT` says that someone asks for the volume, dismounts it or mounts it again; of a `DEV_BROADCAST_VOLUME`, the letters of `dbcv_unitmask`, and then `DBT_DEVICEREMOVEPENDING`/`…REMOVECOMPLETE` go to `Bandeja.volumen` (the engine's `volumen()`: VeraCrypt's dismount broadcast), if someone listens. A failing engine never blocks the removal. Detail: `agent-scheduling.md`.
- **`arrancar()` succeeds with the window, not the icon**: at logon the taskbar may not exist yet, `NIM_ADD` fails, and `TaskbarCreated` adds it later (also after an Explorer restart).
- The menu is `TrackPopupMenu(TPM_RETURNCMD)` after `SetForegroundWindow`, with a `WM_NULL` after it, or it does not close when clicking away; `&` in names is doubled (`texto_menu()`).
- Notices hang off the tray icon (`NIM_MODIFY` + `NIF_INFO`) through `avisos.GLOBO`; without it, `avisos` falls back to its temporary icon.
- **The session and power events** (#178: the agent locking a root by itself; what it does with them: `agent.md`). All through `Api` (`registrar_sesion()`/`soltar_sesion()` over `wtsapi32`, `temporizador()`/`parar_temporizador()` over `SetTimer`/`KillTimer`), driven by the fake one in `tests/test_bandeja_windows.py`:
  - **Registered on creation**: `_oir_sesion()` calls `WTSRegisterSessionNotification(hwnd, NOTIFY_FOR_THIS_SESSION)` right after the window exists. At logon the session service may not be ready, so a failure arms a window timer (`ID_TEMPORIZADOR_SESION`, every `CADA_REINTENTO_SESION` ms) for up to `REINTENTOS_SESION` attempts; a `WM_TIMER` already queued after success or the last attempt does nothing. `Bandeja.oye_sesion` says whether it worked (the agent reads it with `getattr`, so the Linux tray, which has none, offers no session box). `WM_DESTROY` kills the timer and unregisters (`WTSUnRegisterSessionNotification`).
  - `WM_WTSSESSION_CHANGE` with `WTS_SESSION_LOCK`/`WTS_SESSION_UNLOCK` → `pedir({"pide": PIDE_SESION, "evento": "bloqueo"/"desbloqueo"})` (`EVENTOS_WTS`); other session changes (console connect, remote, fast user switching) ask nothing.
  - `WM_POWERBROADCAST` with `PBT_APMSUSPEND` → `evento: "suspension"` and returns `None` (Windows' TRUE) at once: Windows gives about 2 s and the agent never stretches them. The resume ones still send `PIDE_DESPERTAR`.
  - `WM_QUERYENDSESSION` returns `None` (TRUE): nothing vetoes or delays a logoff or shutdown.
  - `WM_ENDSESSION` with a non-zero `wParam` calls `Bandeja.fin_de_sesion` (the agent's `lanzar_al_salir()`, set by `poner_bandeja()`) inside a `try`, like `dispositivo`, and returns 0: after that answer the process may die, so no agent turn is waited for.

## Linux (`ui/bandeja_linux.py`, phase 6)

Draws the same `bandeja.Vista` on the session bus, with its own thread and connection (the agent talks to it via `poner()`/`cerrar()`, which write a pipe the thread selects on). Cite the *StatusNotifierItem* and *dbusmenu* specifications like the D-Bus one. Not to weaken:

- **Name, path, register**: `org.kde.StatusNotifierItem-<pid>-1` owns `/StatusNotifierItem` (interface `org.kde.StatusNotifierItem`), registered with `RegisterStatusNotifierItem` on `org.kde.StatusNotifierWatcher`; the menu is `com.canonical.dbusmenu` v3 at `/MenuBar`, which the item's `Menu` property names. The icon is `IconPixmap`, `a(iiay)` **ARGB32 in network byte order, not premultiplied** (`icons.pixmap_bandeja()`, 16–64 px, painted lazily and cached); changes are `NewIcon`/`NewToolTip`/`NewStatus`, and `NeedsAttention` with avisos. `ItemIsMenu` so the left click opens the menu too; `Activate` (for hosts that call it anyway) does the `defecto` entry (the first device's «Configurar»).
- **dbusmenu ids are renumbered on every change** (`bl.Menu.poner()`, only when the entries actually differ) and `LayoutUpdated` is emitted; the previous numbering is kept, so a click from a menu that was open means what it said. `_` in labels is doubled (dbusmenu mnemonic). There is no default entry, so no bold and no double click on a device submenu; clicking a submenu node does nothing.
- **No watcher is not «no tray forever»**: `arrancar()` succeeds with the session bus, `puesta` is False until a watcher with a host exists, and `NameOwnerChanged`/`StatusNotifierHostRegistered` register it when one appears or restarts (Linux's `TaskbarCreated`). `Agente.con_bandeja()` (not `bandeja is not None`) decides whether a notice may say «from the tray icon».
- **The fallback is the menu entry**: on Linux `install/agente.quiere_menu()` puts the «prdrive» `.desktop` even without a host root, and `agente.py abrir` starts a stopped agent (`arrancar_agente()`), opens the root's window, or with no root sends `bandeja.aviso_de_estado()` as a notification. «Verificación» has a «Bandeja» row (`tk_equipo.escritorio()`, one bus connection for it and the notifications row) naming the GNOME extension when there is no watcher.
- **Resume from suspend** is `PrepareForSleep(false)` from logind on the **system** bus, heard in the tray thread → `PIDE_DESPERTAR`; no system bus, no resume signal, nothing else lost.
- `tests/test_bandeja_linux.py` drives it all over `tests/_bus_falso.py`.

## Global keyboard shortcuts (#109)

The «Agent brief» of #109 is the spec. Five actions can carry a shortcut the user records: «Sincronizar ahora», «Abrir su carpeta», «Pausar o reanudar», «Abrir su ventana» and «Abrir el llavero» (`equipo.ACCIONES_DE_ATAJO`; a new one goes **last**, because the Windows hotkey id is `PRIMER_ATAJO` + its position, and the portal's id is the action's name, so appending moves no saved shortcut and asks no portal confirmation again). They are global (any window in front) and **none exists by default**: `agente.json` gets an `atajos` key (`equipo.Ajustes.atajos`, action → combination in its inner form `ctrl+alt+s`, checked only for shape by `equipo.FORMA_ATAJO` when read, and against `atajos.validar()` before it is put, `Agente._atajos_guardados()`) only when one is saved, so hosts in use do not change, and with none the agent connects to nothing to put them.

- **The pure half is `ui/atajos.py`**, like `ui/bandeja.py`: parsing and printing a combination (`leer()`, `normal()`, `texto()`: «Ctrl+Alt+S», «Mayús», «Win» or «Súper»), what each system needs (`windows()`: `RegisterHotKey`'s modifiers with `MOD_NOREPEAT` and the virtual key; `x11()`: the mask and keysym; `portal()`: the freedesktop «shortcuts» trigger, `CTRL+ALT+s`), what is valid (`problema(c, windows)`: a key in `TECLAS`, i.e. a letter, a digit, F1–F24 or a few named keys, with Ctrl, Alt or the logo key, since without one of them the key would stop typing in every other program; on Windows also not Ctrl+Alt with a letter, a digit or the space unless the logo key is in it, `ALTGR`: Windows reports AltGr as Ctrl+Alt, so `RegisterHotKey(MOD_CONTROL|MOD_ALT, '2')` would swallow «@» on a Spanish layout, and Shift does not help since AltGr+Shift types on some layouts, «Ą» in Polish; on X11 AltGr is `ISO_Level3_Shift` and on Wayland the desktop decides; `validar()` applies it to a save and to `agente.json`), the target (`objetivo()`), what a press does (`pulsado()`), the recording window's model (`Teclas`, `Edicion`), its conversation with the agent (`guardar()`, `respuesta()`, `tras_guardar()` over `leer_estado()`/`pedir()`, `agent-window.md`) and what the agent reports (`resumen_de()`).
- **A pressed shortcut is a request like the tray's.** Every engine calls `pulsado(accion)`, which `agente.poner_atajos()` turns into `Agente.pedir({"pide": "atajo", "accion": …})` (Windows: the tray's own `pedir`). `Agente._atajo()` asks `atajos.pulsado()` for the requests and runs them through `_atender_peticion()`: `PIDE_PASADA` for «Sincronizar ahora», `PIDE_EXPLORAR`, `PIDE_ABRIR`, `PIDE_LLAVERO` for the keychain (the tray's «Abrir llavero», so `_lanzar_llavero()`'s guards and `runsync.py --llavero`, which also brings an already open KeePassXC to the front; `llavero.md`), and for the pause the drive's own (`PIDE_PAUSAR_RAIZ`/`PIDE_REANUDAR`, the window's «Pausar», kept in `agente.json`); with the tray's global pause on and the drive not paused, `PIDE_SIGUE`, as the window's «Reanudar todo». No new action logic. `agente.py atajo ACCION` leaves the same request in `agente.pide`, so a desktop's own shortcut settings can run it where none of the three mechanisms exists.
- **Which drive: the last used** (`atajos.objetivo()`): of the connected rows that are `en_lista`, host roots included, the one with the latest `Agente.usadas` time, else the last connected (`Conexion.desde`), and with one, that one. **The keychain's chooses only among the rows that carry it** (`objetivo(…, llavero=True)`, `resumen()` `llavero`): using a drive without one last must not leave the keychain of another drive plugged in beside it unopened. A root counts as used (`Agente._usada()`) when a tray request names it (`_buzon()`, the in-process queue only; «Sincronizar todo ahora» carries `todas` and does not count), when its window asks something through `state/servicio.pide`, when the agent opens its window (`_lanzar_ventana()`), when `_contrato()` first sees its `ui.lock.json` alive (`Conexion.ventana`: a window opened by its own launcher), and when a shortcut acts on it. Memory only.
  - **«Abrir su carpeta» and «Abrir su ventana» also choose among locked devices** (`atajos.ABREN_BLOQUEADA`, `candidatas(…, bloqueadas=True)`), appended after the connected rows with `bloqueada` set: an encrypted host root in `atajos.RAIZ_BLOQUEADA` (`resumen()["equipo"]`: locked, or VeraCrypt already asking), a listed drive locked with BitLocker (`resumen()["bitlocker"]`) and a listed VeraCrypt drive with its container closed (`resumen()["vestibulos"]`: `id`, `nombre`, `raiz`, from `_cerrada_veracrypt()`). They send the same `PIDE_EXPLORAR`/`PIDE_ABRIR` as for an open drive and `_abrir()` unlocks first (above); no notice, since the password window is what is seen (unless it cannot be shown: then the agent's own notice says why). The others (sync, pause, keychain) never pick a locked one. For «last connected», a locked drive counts from when the walk first saw it plugged in and locked (`Agente.bloqueadas_desde`); an encrypted host root has no such time; on a tie a connected row wins. A locked device in sight counts as used too (`_usada()` → `_bloqueada()`), so pressing again after closing the password window goes back to it. The diary names it «… (bloqueada)».
- **What is seen**: «Sincronizar ahora» and the pause have no visible effect, so they notify (`avisar()`, `common/avisos.py`) with the drive's name («PEN: sincronizando», «PEN: en pausa», «PEN: reanudada»); the folder, the window and the keychain do not. No drive at hand, or a drive that is not served (with its `motivo`), says so and asks nothing.
  - **The keychain** (`atajos._llavero()`) notifies what would otherwise look like a broken shortcut: no drive with a keychain at hand, a host that does not open keychains (`resumen()["abre_llavero"]`), and a chosen drive that is `actualizando` or `expulsando` (`Agente._abrir()` only writes the diary then); those ask nothing. With passes held back (pause, battery, power saving) it says nothing either: its `PIDE_LLAVERO` gets the urgent pass that brings the latest, as the tray's does (`Agente._traer_al_abrir()`, `llavero.md`), and a drive paused from its own window is not attended, so `--llavero` brings the latest itself.
- **Engines** (`Agente.atajos_motor`, created the first time it is needed by `poner_atajos()` through `Agente.poner_motor`: with saved shortcuts or when the window opens). If it cannot be created, `atajos_motivo` says why (in the diary when the reason changes) and `_motor_de_atajos()` tries again later, from `REINTENTO_ATAJOS` (30 s) doubling up to `REINTENTO_ATAJOS_MAX` (15 min, `atajos_reintento`/`atajos_fallos`): at login the session bus, the portal (D-Bus-activated, its backend waiting on the compositor) or the tray can take longer than one attempt waits (`ESPERA_ARRANQUE`, 5 s). Opening the window tries at once; no desktop (`SIN_ESCRITORIO`) is never retried, since the agent's environment does not change. Each has `poner(combos)` (asynchronous: the answer comes back as `(combos, rechazados)` in `Agente.atajos_hechos`, waking the `Vigia`), `cerrar()`, `nombre` and `suspende`. `atajos.mecanismo()` picks one:
  - **Windows: `RegisterHotKey` in the tray thread** (`agente.MotorDeBandeja` over `Bandeja.poner_atajos()`). The hotkeys belong to the tray window, whose thread already runs the message loop: the agent posts `WM_ATAJOS`, the thread unregisters the old ones, registers the new ones (ids from `PRIMER_ATAJO`) and answers through `Bandeja.atajos_puestos`; `WM_HOTKEY` with a known id is `pedir({"pide": "atajo", …})`; `WM_DESTROY` unregisters them. `ERROR_HOTKEY_ALREADY_REGISTERED` (1409) is «otro programa (o el propio sistema) ya la usa». No tray, no shortcuts (`SIN_BANDEJA`).
  - **X11: `XGrabKey`** (`atajos_linux.X11`, its own thread and `Display`, ctypes over `libX11.so.6`). Each combination is grabbed on the root window four times, with and without CapsLock and NumLock (`BLOQUEOS_X11`); a `BadAccess` from any of them (caught by a process-wide error handler that routes errors per `Display`, `_ERRORES`) releases the others and rejects it. `XkbSetDetectableAutoRepeat` plus a set of keys still down make a held key act once. `XSetIOErrorExitHandler` (libX11 1.7) keeps the process alive when the server goes: the thread ends. **Known gap**: if the server goes exactly while keys are being looked up during a change of shortcuts, libX11 can fetch the keyboard map and crash on the reply that never comes (seen once against a killed Xvfb); `X11._poner()` narrows that with an `XSync` first (`Xlib.vivo()`), and nothing is looked up while only waiting.
  - **Wayland: the portal** `org.freedesktop.portal.GlobalShortcuts` (`atajos_linux.Portal`, its own session-bus connection with `common/dbus.py`). It checks the interface's `version`, registers as `prdrive` (`org.freedesktop.host.portal.Registry`, the menu entry's `.desktop`; missing on older portals), then `CreateSession` and `BindShortcuts` (each action an id, its combination the `preferred_trigger`), each answered by a `Request`'s `Response` signal; `Activated` with our session and an action id is the press. Changing them closes the session and opens another. A request that arrives while a `Response` is awaited is not queued behind it (the confirmation dialog may stay open, or the portal restart, and the answer never come): `Portal._abandonar()` closes the waiting `Request` (`Request.Close`, which removes its dialog and stops its `Response`) and the agent is not answered for it: it asks again only when what must be in place changes or a save is under test, and by then it has either been answered or given up on that request (`ESPERA_ATAJOS`). A non-zero response (1: cancelled) or an id missing from the answer rejects it. No portal (`Get` fails): no shortcuts, and the window says why (`SIN_PORTAL`). XWayland grabs are not global, so a Wayland session never uses `XGrabKey`.
- **Reconciling** (`Agente._atajos()`, every turn): what must be in place (`_atajos_deseados()`) is a save being tested (`atajos_prueba`), else nothing while the recording window is open and the engine `suspende` (so the combination pressed reaches the window instead of firing; the portal does not suspend, since putting them back would ask for confirmation again, and presses that arrive while the window is open are ignored), else the saved ones that `atajos.validar()` accepts (a hand-edited or other-version `agente.json` can hold Shift+letter, Ctrl+Alt+letter on Windows, or one combination on two actions: those are never put, are notified once and show their reason in `resumen()["atajos"]`, so the window and `status` say it). One request in flight at a time, asked again only when what must be in place differs from the last one asked **or a save is under test** (`atajos_prueba`: a «Guardar» equal to the last request is put again, since otherwise it would never get its answer; with the portal that may show its dialog again, K5, accepted because it answers a person's «Guardar»). No answer within `ESPERA_ATAJOS` (180 s: the portal waits for the user) counts as «el sistema no ha contestado» (the error shows and is notified once), but the request is **not asked again** (`Portal._abandonar()` would close, every 180 s, the dialog the person is looking at): it stays marked as expired (`atajos_vencida`), and an answer for exactly the last request that arrives later (the person confirms at login) is accepted and rewrites the errors, so the shortcuts that work stop being reported as broken; an answer for anything else is dropped. A saved shortcut the system refuses at start stays saved and is notified once per agent (`atajos_avisados`); its reason goes to `resumen()["atajos"]`. A save that nobody decided (`atajos.SIN_DECIDIR`: cancelled in the portal's dialog, or no answer; it always covers every combination) changes nothing: `agente.json` keeps the previous set and the next turn puts it back (with the portal that is a new `BindShortcuts`, which may show its dialog again: unverified, K5).
- **The tray entry** «Atajos de teclado…» (`bandeja._atajos()`, glyph `teclado`, theme name `preferences-desktop-keyboard`) is in the agent-wide block after «Pausar»/«Reanudar» and asks `PIDE_GRABAR_ATAJOS`; while the window is open it reads «Atajos de teclado: la ventana está abierta», greyed. A summary without `atajos` (none today: the tray is the agent's) has no entry. `agente.py atajos` asks the same.
- **The recording window** (`ui/tk_atajos.py`, launched by the agent as `pregunta.py --atajos`, `agente.orden_atajos()`, one at a time, `Agente.ventana_atajos`): the window ↔ agent conversation is in `agent-window.md`. It only draws `atajos.Edicion`; keys are read on the root's `<KeyPress>`/`<KeyRelease>` (`atajos.Teclas`: modifiers by their own key events plus the event `state`, whose Alt bit is `0x20000` on Windows; on Windows the key comes from the virtual key in `keycode`). The combination column reserves room for its longest text (`atajos.MAS_LARGA`, «Pulsa la combinación…») and any change calls `Visor.crecer()`: the window is not resizable and must not grow a scrollbar. With `--motivo` it only says why there are none.
