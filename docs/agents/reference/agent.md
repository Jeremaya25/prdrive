# The resident agent (`agente.py`, `install/agente.py`)

Formerly AGENTS.md «The resident agent» (core). Planner, network probes and `watch = true`: `agent-scheduling.md`. Host root: `host-root.md`. Tray: `tray.md`. Window ↔ agent: `agent-window.md`.

The six phases of `docs/superpowers/specs/2026-09-25-instalacion-en-el-equipo-design.md` (read it before touching this). The agent attends the prdrive drives plugged into the host and, optionally, **the host root**, plain or in a VeraCrypt container; with no root it is the **«solo agente»** install. It has a tray (Windows, Linux) and the window of a root talks to it.

**Nothing of this has run on a real machine.** What needs checking there, phase by phase, is the living list in `docs/superpowers/pruebas/2026-09-25-equipo-pendiente-en-real.md`: add to it whatever you build that only a real host can prove.

## Files and ownership

- **Lives outside every root**, in `equipo.DIR` (`%LOCALAPPDATA%\prdrive\`, `~/.local/share/prdrive/`): `agente/<version>/` (agente.py, pregunta.py, penwatch.py, common/, ui/; never install/), `runtime/<stamp_id>/` (its own python-build-standalone, extracted by `runtime_bin.extract()`), `rclone/<pinned version>/` (its own rclone), `veracrypt/<pinned version>/` (only with an encrypted host root and no VeraCrypt installed), `agente.json` (WHAT: drives, modes, `espera_unidad_nueva`, moderation), `instalacion.json` (WHERE: code, python), `agente.lock.json`, `agente.pide`, `estado.json`, `agente.log`. **No secret there.** `tests/_harness.py` points `equipo.DIR` at a temp dir for every test.
- **One writer per file.** `agente.json` is written by `install/agente.py` the first time only; afterwards **only the agent** writes it, and everybody else (wizard re-run, CLI, window) appends a JSON line to the mailbox `agente.pide` (`equipo.pedir()`); the agent consumes it by renaming it first (`equipo.recoger()`). `instalacion.json` is the installer's. A root has its own mailbox, `state/servicio.pide` (`agent-window.md`), same shape.
- **Pairs and interval stay the drive's**: `leer_servicio()` reads the raw TOML (not `model.parse_config()`: the drive may be another version; only `model.comprobar_seguridad()` is applied, see «Not covered» below) and applies `prefs.elegir()`, the pure core of `startup_defaults()`: one rule, not two.

## The contract with a drive

- **The agent never runs a drive's code before «Atender».** A drive whose id is not in `agente.json` gets a notification + a countdown window (`pregunta.py` → `ui/tk_agente.py`, exit code 0/1/2: 0 is the only yes); the deadline is `planificador.Pregunta`, not the window's. No answer / late answer / no display = «Ahora no» for THIS connection only (re-armed when the root disappears). Only its control file and `state/fleet.json` are read. `tests/test_unidad_nueva.py` asserts no launched process carries its paths.
- **It is the drive's service through the drive's own files** (spec section 3), so old drives work. It writes `daemon.lock.json` (`"agente": true`); obeys `daemon.stop` after the pair in flight (releases, deletes the stop, **pauses** instead of exiting); stays paused while a live `ui.lock.json` of this host exists and for `GRACIA` seconds after (so a service started from the window has time to write its lock); **steps aside** while another live pid of this host holds the lock. A stale lock (dead pid / other host) is overwritten.
  - `runsync.stop_previous_daemon()` returns `None` and says nothing when the lock is the agent's: pausing for the window is what the «Cambiar…» button of the agent's line already describes, and callers print or show a message only when there is one. `tests/test_agente_contrato.py` drives the real `stop_previous_daemon()` against it.
  - **Releasing survives Windows**: runsync reads the lock every 0.1 s while it waits (`STOP_WAIT_STEP`), and Windows will not delete a file someone has open (WinError 32). `_soltar()` stops serving at once (`con.lock = None`, what the planner looks at) and retries the delete on the next turns (`Conexion.soltando`); an undeleted lock with the agent's pid would keep runsync waiting until it gave up.
- **Every pass is the root's own `sync.py`**, a child with the agent's Python (`pythonw` on Windows), `stdin=DEVNULL` (a pair needing `--resync` is skipped), cwd `equipo.DIR`. One pass at a time on the whole host. Nothing stays open in a drive between passes, with ONE exception accepted on 06/10/2026: on Windows, the directory handle of each `watch = true` pair heard with `ReadDirectoryChangesW`. It is registered for `DBT_DEVICEQUERYREMOVE` on the tray window and closed at once when the system asks for the drive, and before «Expulsar» and «Bloquear»; with no tray, nothing is left open (the pairs walk), and VeraCrypt volumes always walk (Windows gives no removal notice for them; seen in the cloud, F18). A Linux inotify watch holds nothing open (unmounting works; the kernel drops it). Detail: `agent-scheduling.md`. A drive unplugged mid-pass records nothing.
  - **Low priority** (`common/prioridad.py`), passes and probes alike: nobody is watching them. Windows: `BELOW_NORMAL_PRIORITY_CLASS` in the `creationflags` (`_opciones_hijo(baja=True)`), which rclone inherits from `sync.py` (`CreateProcess`). POSIX: `Popen` cannot ask for it, so `agente.bajar_prioridad(pid)` sets `nice` 10 and I/O class best-effort 7 right after the launch; `sync.py` takes over 0.1 s to start its rclone, which inherits both. Done from outside on purpose: an older drive's `sync.py` knows nothing of it. It never raises a priority (a higher `nice`, the idle I/O class stay) and never fails a pass. Only CPU on Windows: I/O and memory priority have no documented API for another process.
- **«Expulsar» a drive (`PIDE_EXPULSAR`, `agente.py expulsar ID`, the tray's entry).** The agent releases the drive and `common/expulsar.py` unmounts it, so the cable can come out. It never forces.
  - **Compatible** (`expulsar.compatible()`, cached per connection for `MIRAR_EMBLEMA`): a volume the system mounts straight from a removable device. Linux: `/proc/self/mounts` → `/dev/…` → sysfs (`/sys/class/block`), the disk is `removable = 1` or its path goes through `usbN`, and `udisksctl` exists. Windows: a letter that is not `%SystemDrive%` whose `IOCTL_STORAGE_QUERY_PROPERTY` says USB, SD or MMC bus, or `RemovableMedia`; the bus and not `GetDriveType` because a pendrive declaring itself `Fixed` is the norm. A VeraCrypt volume (`/dev/mapper`, a virtual bus), an internal disk and a host root are not compatible.
  - **Order, like «Bloquear»** (`Agente._expulsiones()`): wait for the pair in flight, for a folder photo (`ESPERA_VENTANA` at most) and for the root's window (it runs from the drive; past `ESPERA_VENTANA` it says so and gives up); then `_soltar()` and `hilo(expulsar.expulsar)`. `_contrato()`, `_raices()` and `_actualizable()` leave the drive alone while it is in `Agente.expulsiones`, and it stays there `GRACIA_EXPULSION` after a good result so the lock is not retaken while the system removes it.
  - **Linux**: `udisksctl unmount -b <partition>` then, best effort, `power-off -b <disk>`; a busy target is told in words, never forced. **Windows**: open `\\.\E:`, `FSCTL_LOCK_VOLUME` (4 tries, half a second apart; if it never locks nothing else is done), `FSCTL_DISMOUNT_VOLUME`, `IOCTL_STORAGE_MEDIA_REMOVAL` (allow) and `IOCTL_STORAGE_EJECT_MEDIA`; if only the last fails the volume is already dismounted and counts as good. **Unverified on a real Windows**: `docs/superpowers/pruebas/2026-09-25-equipo-pendiente-en-real.md`, «Expulsar».
  - The notice «<name>: ya puedes quitarla» or «no la expulso» (with the reason) comes from the result on the next turn, also when the drive is already gone.
- **Detection** reuses `penwatch.candidate_roots()` (still the one drive walk). Linux wakes on `POLLPRI` of `/proc/self/mountinfo` and bursts; Windows bursts on the tray window's `WM_DEVICECHANGE` (both then fall back to a 30 s walk); without a tray it polls every `penwatch.POLL_SECONDS` like penwatch. Two sightings before a drive counts. VeraCrypt vestibules of LISTED drives are opened once per connection (`penwatch.open_container(root, cwd=…)`), never for others; a disconnection is recorded as «already asked» until a walk shows no vestibule («Expulsar» must not bring the password up again).

## Notifications and D-Bus

- **Notifications only when a pair STARTS failing** (`planificador.empieza_a_fallar`), STARTS being skipped for needing `--resync` (`Agente.saltadas`: the planner counts a skipped pass as done, so without this the pair stops syncing unseen; cleared by an `OK` or `FALLO`, kept through `RED`, carried as `saltadas` per drive in `resumen()` for the tray), or a remote goes offline: `common/avisos.py` (D-Bus `Notify`; Windows `Shell_NotifyIconW` NIF_INFO on a temporary message-only window, **unverified on real Windows**). No Tk in the agent process: `tests/test_install_agente.py` checks `tkinter` isn't in `sys.modules` after importing it.
- **`common/dbus.py`** cites the *D-Bus Specification* like `ui/qr.py` cites ISO/IEC 18004: keep the citations. It has the calling half (address, EXTERNAL, marshalling, calls, properties, `AddMatch`) and, for the Linux tray, the answering half: `pedir_nombre()`, `exportar(ruta, Interfaz…)` (methods with their in/out signatures, read-only properties), `emitir()`, `atender()`, and `Peer`/`Introspectable`/`Properties` answered for every exported path. A call that arrives while `llamar()` waits is answered then and there when something is exported (a watcher may ask before it replies); a handler's exception is a `Failed` error for the caller, never a crash. `tests/test_dbus.py` pins the canonical `Hello` bytes; `tests/_bus_falso.py` is a bus that also calls the client, as a tray host does.

## Installing (`install/agente.py`)

Code and runtime each in a per-version dir, swapped with `os.replace`, old ones pruned. It imports penwatch's `device_id`/`mode` and **uninstalls penwatch** (and says so). It registers with `penwatch.register_task()` (the task XML is `penwatch.task_xml()` with the command as a parameter) or an XDG autostart (`penwatch.autostart_desktop()`, `Exec=` quoted per the Desktop Entry spec), **not** systemd: notifications, the question and VeraCrypt's password need the graphical session. Uninstalling removes `equipo.DIR` and never touches a drive.

- **Dependency rules**: the agent imports penwatch, never the reverse; penwatch imports nothing of the project (`tests/test_install_agente.py` walks its AST). `agente.py` is in `build_installer.DATOS_FICHEROS` but NOT in `deploy.DEPLOY_FILES`: it goes to hosts, not devices.
- The wizard's final step offers «Que lo atienda el agente de este equipo» instead of installing penwatch. The wizard's route and the host root: `host-root.md`.
- Updating the agent itself («Actualizar»): `agent-window.md`.

## Hardened after the #54 review (`tests/test_agente_endurecido.py`)

- **Pair names** go through `model.problema_nombre()` in `_build_pair`: no leading `-`, no `/` `\\` `:` or control characters, not `.`/`..` (the name is an argv entry and a folder in `state/` and `filters/`). The agent reads the raw TOML, so `leer_servicio()` drops such names itself, and every pass is `sync.py -- <pareja>`.
- **One agent per host**: `equipo.tomar_lock()` creates `agente.lock.json` with O_EXCL (`store.crear_exclusivo()`) and removes a dead record only by compare-and-delete (`store.retirar_si_sigue()`, the `.romper` rule of `runsync._retirar_ui()`).
- **Writes into a root never follow links out of it**: `agente.en_la_raiz()` resolves the path and the root before the agent writes `daemon.log` (also `O_NOFOLLOW`; capped like runsync's by `store.recortar_diario()`: past `store.DIARIO_TOPE` it keeps the last `store.DIARIO_QUEDAN` lines; it reads only the last `DIARIO_TOPE` bytes, so a huge `daemon.log` on a crafted drive costs no memory, and it opens with `O_NONBLOCK` so a FIFO of that name cannot hang it) or `daemon.lock.json`; `store.write_text()` unlinks a stale `.tmp` and creates it with O_EXCL, which does not follow a link.
- **The host root and its pairs are checked resolved too**: `raiz_equipo._dentro()` is true if either the written or the resolved paths are contained; `revisar_local()` refuses a `local` that a link takes out of the root or into `equipo.DIR`.
- **«Actualizar» skips a ghost**: `install/agente.actualizar_raices()` treats an encrypted root whose `.hc` is free (`vestibulo.retenido() is False`) as locked, like the agent.
- **One service per root**: the agent (`Agente._tomar()`) and runsync's service (`runsync.tomar_lock()`) both take `daemon.lock.json` with `store.tomar_registro()` (O_EXCL + compare-and-delete), never check-then-write. Both write the boot time (`arranque`) and judge liveness with `store.vivo_en_este_arranque()` (`service.md`, «A lock record names its boot»).
  - runsync's service finding the agent's lock touches `daemon.stop` and waits (`ESPERA_AGENTE`) for it to let go; the launcher's `stop_previous_daemon()` no longer deletes the **agent's** lock on timeout.
  - The agent leaves a `daemon.stop` alone while another live service holds the lock (it is for that one), re-checks the lock is its own right before each pass, and a fresh connection clears a lock with its own pid left by the previous one. A runsync service steps down when a live record of someone else appears.
  - What remains: a drive with an older runsync still writes without looking, overlapping at most the pair in flight.
- **Stopping the agent waits for its pass.** Each pass runs in its own session/process group and is recorded in `equipo.pasada_json()` (pid, drive, pair, and the boot time, `store.arranque_del_sistema()`, so a pid from another boot is ignored). `install/agente.parar_agente(avance)` waits for the agent AND that pass up to `ESPERA_PASADA` (10 min), saying so (`avance(fracción, texto)`; the wizard shows it under the bar, the CLI prints it once per text), then kills the agent first (so it cannot see the pass end, count a failure and delete the record) and the pass with its rclone (`matar_arbol()`: `killpg`, `taskkill /T`). A new agent launches nothing while the previous one's pass is alive (`Agente.heredada`).
- **A cut pass leaves bisync's `.lck`**, which expires by itself two minutes later (`--max-lock 2m`); before that, the next pass of that pair fails with «prior lock file found» and notifies a failure that is not one (H-15).
  - `parar_agente()` records the cut in `pasada.json` (`equipo.apuntar_corte()`: `cortada`, plus `raiz` from the record).
  - The next agent reads it at start (`Agente.cortada`, `equipo.pasada_cortada()`) and `_raices()` leaves out **that pair only** for `equipo.ESPERA_TRAS_CORTE` (150 s). Nothing deletes the lock: rclone's own expiry decides.
  - A pair whose own flags raise `max-lock` can still fail once, as before.
- **The id is not a credential.** «Atender» records `agente.huella(raiz)` in `equipo.Unidad.codigo`: sha256 of everything in `.prdrive/` except what changes with use (`state/`, `logs/`, `filters/`, `keys/`, `runtime/`, `bin/`, `sync_config.toml`, the control file, `.ico`, `__pycache__`); a few MB, milliseconds.
  - Another hash on connect = `Conexion.cambiada`: not served, no window; the tray offers «… (código cambiado)» · «Atender con su código nuevo…», and `pregunta.py … --cambiada` asks again (the yes keeps the mode). An empty `codigo` (listed by the wizard or `atender ID` unplugged) is recorded on the first connection.
  - Children get `PYTHONPYCACHEPREFIX` in `equipo.DIR`, so a drive's `__pycache__` is never read. Every update of a drive therefore asks once.
  - **What the agent refuses to serve** in `sync_config.toml`: `leer_servicio()` runs the raw TOML through `model.comprobar_seguridad(crudo, es_equipo(app), carpeta_programa=APP_SUBDIR)` before serving a root (`engine.md`) and turns its `ConfigError` into the `ValueError` that says why the root is not served, so drives whose own code predates that gate are covered too (`orden_sonda()` hands each pair's `remote` to a `rclone lsd` on this host). It refuses: the flags the script owns (`--config`, `--workdir`, `--resync`…), flags that run a program (`*-command`, `*-ssh`, `rc`…), flags that write arbitrary host files (`--cpuprofile`, `--memprofile`), unsafe remote names (connection strings, a one-letter name that rclone reads as a Windows drive), an `include`/`exclude` entry with a line break, and a `local` outside the root (`..`, drive letters, `:` and dots-and-spaces tricks, the program's and the keychain's folders).
  - **The config is read again right before every pass** (`Agente._lanzar()`, `tarea.tipo == pl.PASADA`; `leer_config()`, the same read-and-check `leer_servicio()` starts with). The agent re-reads a drive's `sync_config.toml` only when its mtime changes, and a drive with older code (whose own `sync.py` checks nothing) could be edited keeping the mtime, so the next pass would run an unchecked config. If it no longer passes, or cannot be read, nothing is launched: `Agente._sin_servicio()` leaves the root unserved (`servicio = None`, `motivo = «sin servicio: …»`, a diary line `no lanzo <pair>: …`) and the next turn reads it whole. There is no per-tick read, and a probe (`SONDA`) uses the `remote` already checked when the root was loaded. A root unserved because `comprobar_seguridad()` refused its config is notified once as «<name>: config rechazado» (`ConfigRechazada`, a `ValueError`); the other reasons (unreadable, not TOML, no pairs) keep «nada que sincronizar».
  - **Not covered**: backend-option redirects (`--sftp-host`, `--*-url`, `--*-endpoint`) that could send credentials elsewhere; `--temp-dir`/`--cache-dir`; the `--*-from` filter files, which on a non-bisync root pair can beat the program-folder `--exclude`; and the travelling VeraCrypt the vestibule of a listed drive opens.
- **The agent never runs a drive's rclone.** `install/agente.poner_rclone()` puts the pinned rclone (`conseguir_rclone()` → `rclone_bin.pinned_rclone()`: cache, hand-placed official zip or download, never the PATH) in `equipo.dir_rclone()/<pins.RCLONE_VERSION>/`; `instalacion.json` records it, `podar()` prunes old ones, `instalado_prep()` needs it.
  - The agent passes it to every child in `model.RCLONE_DEL_AGENTE` (`PRDRIVE_RCLONE`; a missing path when it has none, so the child fails instead of falling back), and `model.rclone_path()` returns that and only that when set (`sync.py`, `catalog.run()` and the window it opens all go through it). The probe runs `agente.rclone_propio()` directly. With no rclone of its own the agent launches nothing from any root (`SIN_RCLONE`, said once).
  - **Drives older than `agente.VERSION_MINIMA` (0.5.0)** would ignore the variable, so they are not served, not asked about, not opened (`Conexion.vieja`, `version_vieja()`: their `VERSION` is inside the accepted fingerprint), and notified once per connection; the tray shows «… (por actualizar)». A listed one is offered «Actualizar a la vX» there (the agent puts its own version on it, `agent-window.md`); an unlisted one keeps «Actualízala para que la atienda» greyed out.
  - A drive synced by the agent and by its own window uses two rclones; with both on the same prdrive version they are the same pin.
