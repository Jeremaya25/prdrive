# The resident agent (`agente.py`, `install/agente.py`, `common/presencia.py`)

Formerly AGENTS.md «The resident agent» (core). Planner, network probes and `watch = true`: `agent-scheduling.md`. Host root: `host-root.md`. Tray: `tray.md`. Window ↔ agent: `agent-window.md`.

The six phases of `docs/superpowers/specs/2026-09-25-instalacion-en-el-equipo-design.md` (read it before touching this). The agent attends the prdrive drives plugged into the host and, optionally, **the host root**, plain or in a VeraCrypt container; with no root it is the **«solo agente»** install. It has a tray (Windows, Linux) and the window of a root talks to it.

**Nothing of this has run on a real machine.** What needs checking there, phase by phase, is the living list in `docs/superpowers/pruebas/2026-09-25-equipo-pendiente-en-real.md`: add to it whatever you build that only a real host can prove.

## Files and ownership

- **Lives outside every root**, in `equipo.DIR` (`%LOCALAPPDATA%\prdrive\`, `~/.local/share/prdrive/`): `agente/<version>/` (agente.py, pregunta.py, penwatch.py, common/, ui/; never install/), `runtime/<stamp_id>/` (its own python-build-standalone, extracted by `runtime_bin.extract()`), `rclone/<pinned version>/` (its own rclone), `veracrypt/<pinned version>/` (only with an encrypted host root and no VeraCrypt installed), `agente.json` (WHAT: drives, modes, `espera_unidad_nueva`, moderation, and per drive the Windows volume where it was last attended with BitLocker and its «Pedir la contraseña al conectarla», `Unidad.pedir_al_conectar`; the global keyboard shortcuts, `atajos`, only when some are saved: `tray.md`), `instalacion.json` (WHERE: code, python), `agente.lock.json`, `agente.pide`, `estado.json`, `agente.log`, `consumo.json` (what the agent spends per drive and day, last 14 days: passes, passes that found nothing to do, processes, seconds, bytes of bisync workdir rewritten on the drive; `common/consumo.py`, written once per finished pass from the pair's report, `common/parte.py`, never on the drive; `agente.py status` prints today's line under each connected drive; `tests/test_agente_consumo.py`), and `llavero-navegador.json` (which `HKCU\…\NativeMessagingHosts` keys prdrive created for the keychain's browser, so that closing deletes only those: written by whoever opens or closes the keychain on this host, the drive's window or this agent's sweep of a drive that left; `common/keepassxc.py`, `llavero.md`). **No secret there.** `tests/_harness.py` points `equipo.DIR` at a temp dir for every test.
- **One writer per file.** `agente.json` is written by `install/agente.py` the first time only; afterwards **only the agent** writes it, and everybody else (wizard re-run, CLI, window) appends a JSON line to the mailbox `agente.pide` (`equipo.pedir()`); the agent consumes it by renaming it first (`equipo.recoger()`); what keeps a request from being lost between the two is in `agent-window.md`, «A request and the agent's take in the same instant». `instalacion.json` is the installer's. A root has its own mailbox, `state/servicio.pide` (`agent-window.md`), same shape.
- **Pairs and interval stay the drive's**: `leer_servicio()` reads the raw TOML (not `model.parse_config()`: the drive may be another version; only `model.comprobar_seguridad()` is applied, see «Not covered» below) and applies `prefs.elegir()`, the pure core of `startup_defaults()`: one rule, not two.

## The contract with a drive

- **The agent never runs a drive's code before «Atender».** A drive whose id is not in `agente.json` gets a notification + a countdown window (`pregunta.py` → `ui/tk_agente.py`, exit code 0/1/2: 0 is the only yes); the deadline is `planificador.Pregunta`, not the window's. No answer / late answer / no display = «Ahora no» for THIS connection only (re-armed when the root disappears). Only its control file and `state/fleet.json` are read. `tests/test_unidad_nueva.py` asserts no launched process carries its paths.
- **It is the drive's service through the drive's own files** (spec section 3), so old drives work. It writes `daemon.lock.json` (`"agente": true`); obeys `daemon.stop` after the pair in flight (releases, deletes the stop, **pauses** instead of exiting); stays paused while a live `ui.lock.json` of this host exists and for `GRACIA` seconds after (so a service started from the window has time to write its lock); **steps aside** while another live pid of this host holds the lock. A stale lock (dead pid / other host) is overwritten.
  - `runsync.stop_previous_daemon()` returns `None` and says nothing when the lock is the agent's: pausing for the window is what the «Cambiar…» button of the agent's line already describes, and callers print or show a message only when there is one. `tests/test_agente_contrato.py` drives the real `stop_previous_daemon()` against it.
  - **Releasing survives Windows**: runsync reads the lock every 0.1 s while it waits (`STOP_WAIT_STEP`), and Windows will not delete a file someone has open (WinError 32). `_soltar()` stops serving at once (`con.lock = None`, what the planner looks at) and retries the delete on the next turns (`Conexion.soltando`); an undeleted lock with the agent's pid would keep runsync waiting until it gave up.
- **Every pass is the root's own `sync.py`**, a child with the agent's Python (`pythonw` on Windows), `stdin=DEVNULL` (a pair needing `--resync` is skipped), cwd `equipo.DIR`. One pass at a time on the whole host. Nothing stays open in a drive between passes, with ONE exception accepted on 06/10/2026: on Windows, the directory handle of each `watch = true` pair heard with `ReadDirectoryChangesW`. It is registered for `DBT_DEVICEQUERYREMOVE` on the tray window and closed at once when the system asks for the drive, and before «Expulsar» and «Bloquear»; with no tray, nothing is left open (the pairs walk), and on a VeraCrypt volume, which gives no removal notice to a handle, it is closed when VeraCrypt broadcasts the dismount of its letter (`avisos_veracrypt`, on by default; off, those pairs walk). A Linux inotify watch holds nothing open (unmounting works; the kernel drops it). Detail: `agent-scheduling.md`. A drive unplugged mid-pass records nothing.
  - **Low priority** (`common/prioridad.py`), passes and probes alike: nobody is watching them. Windows: `BELOW_NORMAL_PRIORITY_CLASS` in the `creationflags` (`_opciones_hijo(baja=True)`), which rclone inherits from `sync.py` (`CreateProcess`). POSIX: `Popen` cannot ask for it, so `agente.bajar_prioridad(pid)` sets `nice` 10 and I/O class best-effort 7 right after the launch; `sync.py` takes over 0.1 s to start its rclone, which inherits both. Done from outside on purpose: an older drive's `sync.py` knows nothing of it. It never raises a priority (a higher `nice`, the idle I/O class stay) and never fails a pass. Only CPU on Windows: I/O and memory priority have no documented API for another process.
- **«Expulsar» a drive (`PIDE_EXPULSAR`, `agente.py expulsar ID`, the tray's entry).** The agent releases the drive and `common/expulsar.py` unmounts it, so the cable can come out. It never forces.
  - **Compatible** (`expulsar.compatible()`, cached per connection for `MIRAR_EMBLEMA`): a volume the system mounts straight from a removable device. Linux: `/proc/self/mounts` → `/dev/…` → sysfs (`/sys/class/block`), the disk is `removable = 1` or its path goes through `usbN`, and `udisksctl` exists. Windows: a letter that is not `%SystemDrive%` whose `IOCTL_STORAGE_QUERY_PROPERTY` says USB, SD or MMC bus, or `RemovableMedia`; the bus and not `GetDriveType` because a pendrive declaring itself `Fixed` is the norm. A VeraCrypt volume (`/dev/mapper`, a virtual bus), an internal disk and a host root are not compatible.
  - **Order, like «Bloquear»** (`Agente._expulsiones()`): wait for the pair in flight, for a folder photo (`ESPERA_VENTANA` at most) and for the root's window (it runs from the drive; past `ESPERA_VENTANA` it says so and gives up); then `_soltar()` and `hilo(expulsar.expulsar)`. `_contrato()`, `_raices()` and `_actualizable()` leave the drive alone while it is in `Agente.expulsiones`, and it stays there `GRACIA_EXPULSION` after a good result so the lock is not retaken while the system removes it.
  - **What is pending goes up first** (`Agente._por_subir()`, `Expulsion.subir`/`sin_subir`; `tests/test_agente_expulsar.py`). Asking to eject queues, as urgent passes, the pairs of the drive that may hold something not synced: all of the service's in mode `daemon`, minus the ones known not to (they hear the system's notices and no change is pending; passed, or started, less than `RECIEN_PASADA` = 30 s ago) and the ones that would upload nothing (skipped, their remote offline). None if the agent is moderating (pause, battery, power saving, metered): ejecting does not override what the person asked. While `subir` is not empty the drive is served as usual (`_contrato()` does not release it) but the planner only sees those pairs (`_raices()`). A pass that cannot even be launched is named too. It waits `ESPERA_SUBIR` (120 s) at most, only `ESPERA_TURNO` (20 s) when the single queue is held by another root's pass, and not at all once the agent no longer serves the drive (its window opened); the pair in flight is never cut. What did not get its pass, or failed it, is named in the notice: «Ya puedes quitarla. Se ha quedado sin sincronizar: docs.» Without this a drive left with whatever changed since its last pass, which with a stretched interval (`agent-scheduling.md`) can be many minutes.
  - **Linux**: `udisksctl unmount -b <partition>` then, best effort, `power-off -b <disk>`; a busy target is told in words, never forced.
  - **Windows** (#128): open `\\.\E:`, `FSCTL_LOCK_VOLUME` (4 tries, half a second apart; if it never locks nothing else is done), `FSCTL_DISMOUNT_VOLUME`, `IOCTL_STORAGE_MEDIA_REMOVAL` (allow); then **retire the DEVICE** like «Quitar hardware de forma segura», with `CM_Request_Device_EjectW` (`cfgmgr32` by `ctypes`), which is what makes the drive letter go from Explorer. `IOCTL_STORAGE_EJECT_MEDIA` alone took the medium out but left the device and its letter until the stick was pulled.
    - **What is retired** (`_dispositivo_a_retirar()`, looked up BEFORE locking): only a volume `_bus_windows()` calls removable (the criterion of `compatible()`: USB, SD or MMC bus, or `RemovableMedia`), so a virtual disk hanging from a tree with something removable is never retired. `_cadena_windows()` walks volume → `IOCTL_STORAGE_GET_DEVICE_NUMBER` → the disk interface with that number (`CM_Get_Device_Interface_ListW`) → its device (`DEVPKEY_Device_InstanceId`) → `CM_Get_Parent` up to `PROFUNDIDAD_MAXIMA`; `_elegir_nodo()` takes the first PARENT of the disk that declares `CM_DEVCAP_REMOVABLE` (for a pendrive, the «USB Mass Storage Device» Windows lists in the safe-removal dialog), and the disk itself only if no parent is (a card reader).
    - **The request is made with the volume handle already closed** (an open one would veto it), and the device is found again by its instance id (`_retirar_dispositivo()`). A veto (`CR_REMOVE_VETOED`) is told with its cause (`PNP_VETOS`, one sentence per `PNP_VETO_TYPE`, with the program, service or device Windows names); the volume is already dismounted then, as with the other failures. With no device to retire (a virtual disk, a chain that cannot be read) it ejects the medium with the same locked, dismounted handle. If Windows cannot even take the request (any other `CONFIGRET`), `_expulsar_medio()` opens the volume again and repeats `_soltar()` (lock with its retries, dismount, allow removal: the helper both passes share) before `IOCTL_STORAGE_EJECT_MEDIA`, because opening it remounts the file system and in that gap Explorer or the indexer may have it open (#156). If the volume can no longer be opened (the device is gone, `CR_NO_SUCH_DEVNODE`) that counts as good; if it opens but the second lock or dismount fails nothing is ejected and the result is not `ok`: it carries the `CONFIGRET` and points to «Quitar hardware de forma segura», never «ya puedes quitarla». Only the eject itself failing after a successful second lock and dismount counts as good (the volume is dismounted).
    - Every OS call is a module-level function tests replace: `_cadena_windows()`, `_retirar_dispositivo()`, `_bus_windows()`; `tests/test_expulsar.py` drives the decision with doubles of the chain, the bus and the veto. **Unverified on a real USB stick**: `docs/superpowers/pruebas/2026-09-25-equipo-pendiente-en-real.md`, «Expulsar» X7–X10; the chain and the request's prototypes are run on a virtual disk by the cloud row F29 (`tests/maquina/f29_retirar_dispositivo_windows.py`).
  - The notice «<name>: ya puedes quitarla» or «no la expulso» (with the reason) comes from the result on the next turn, also when the drive is already gone.
- **A VeraCrypt volume's name and icon for Explorer** (Windows): `_conectar()` calls `explorador.poner(raiz, APP_SUBDIR)` for a listed drive with its code accepted (Explorer does not read that volume's `autorun.inf`; it reads per-letter HKCU keys), and `_desconectar()` calls `explorador.quitar(raiz, uid)`, which removes only that drive's marked keys (`drive-name-icon.md`). Both no-ops for anything that is not a VeraCrypt letter; neither raises. The connections live in memory, so a volume closed while the agent was not running leaves its keys behind: `Agente._limpiar_letras()` runs `explorador.limpiar(APP_SUBDIR)` at the first turn (beside `_limpiar_navegador("al arrancar")`) and in `_recorrer()` when a letter not seen by the previous walk appears in `candidate_roots` (`Agente.letras_vistas`; never every turn), logs the letters it cleans in the diary and never raises (#157; `tests/test_agente_veracrypt.py`).
- **Pairs of a root that are due together go in ONE `sync.py`** (`Agente._acompanan()`, `Pasada.otras`, `LOTE` = 8; entrega 4 of the same roadmap; `tests/test_agente_lote.py`). Each `sync.py` is a Python that starts (0.26 s of CPU of the 0.65 an unchanged pass costs), so four pairs with one interval were four starts in a row. When the planner hands a pass, the agent asks it again, with what is already chosen removed, what would come next for that root **now**: the same rules apply (moderation, offline remote, backoff), urgent ones included, and whatever is not due yet is not dragged along. `sync.py -- a b c` runs them in order and the result of each comes from its own report (`common/parte.py`) and its own slice of the output (`parte.trozos()`: up to its report line; the final «Hecho. …» belongs to none), so a network failure or a «Saltada» lands on the pair that said it; a pair with no report counts as a failure with the process's code and what came after the last report (`parte.resto()`) if the process ended badly (it died before reaching it), and as fine if the process ended with 0 (`sync.py` exits 1 when any pair fails). The output of a batch is read up to `SALIDA_DE_LOTE` (16 MB), not the 64 KB tail of a single pass: a pair that moves a lot fills it with progress lines and the first pair's report sits far above. **Only once that root's `sync.py` has written a report** (`Conexion.con_partes`, learnt from the first single pass of the connection): an older `sync.py` writes none, and with several pairs in one process nobody would know which failed. The keychain always goes alone. `pasada.json` carries `parejas` (a cut batch keeps all of them waiting for the lock to expire, `_raices()`), `estado.json` shows them joined, and `consumo` counts one process for the batch.
- **A quiet agent waits; a quiet drive is barely touched** (entrega 3 of `docs/superpowers/specs/2026-10-11-watch-y-energia-hoja-de-ruta-design.md`; `tests/test_agente_reposo.py`; ceilings `consumo.*` in `tests/rendimiento/presupuesto.toml`).
  - **The loop's wait is `cuanto_esperar(agente, decision)`**, not a fixed `TICK`. Still `TICK` (2 s) while there is anything to watch closely (`Agente.en_reposo()` is false): a pass or any child, **any drive in sight** (its contract lives in its `state/` files), a mount burst, something half done, a tray request. With nothing of that, **and only if the mailbox tells** (`Agente.oye_buzon`), up to `REPOSO` (30 s) or the next backup walk if sooner: everything else that can happen (a mount, the tray, the network, a request) wakes the `Vigia`. Measured: 1 800 turns an hour → 120.
  - **The agent hears its own mailbox** (`common/avisos_buzon.py`, `poner_buzon()`): the system says when anyone writes `agente.pide`, instead of the agent trying to rename it every 2 s. Linux: an inotify descriptor on `equipo.DIR` that the `Vigia` polls (`Vigia.oir_buzon()`; only the mailbox's name ends the wait). Windows: a thread on a synchronous `ReadDirectoryChangesW` of `equipo.DIR` (non-recursive, host disk: nothing to eject) that calls `vigia.despertar()`. It needs nothing from whoever asks, so a window of an older version still gets its answer at once. If it cannot be set up, `oye_buzon` stays false and the loop is the 2 s one, as before. The rename attempt on every turn stays as the safety net.
  - **One directory read per drive and turn** (`mirar_estado()`, `Conexion.vista`). Each turn used to do nine separate operations on an attended drive (does `daemon.stop` exist, read the lock twice, read the window's lock, try to rename the root's mailbox, two dates, the control file): 273 a minute, so a USB stick never rested. Now `vuelta()` lists `state/` once per connection and everything reads from that: whether the drive is still there (a failed listing disconnects it, as `presente()` did), whether there is a stop, a mailbox (`_buzones_de_raices()` only calls `recoger()` if it is listed), and the date and size of `daemon.lock.json`, `ui.lock.json` and `ui_prefs.json`. `Agente._registro()` re-reads a JSON only when that signature changes or after `RELEER_REGISTROS` (20 s: with the 2 s date resolution of FAT and exFAT a same-size rewrite can go unseen until then); the pid inside is still checked alive on every turn, on the host. `sync_config.toml` (outside `state/`) is stat'ed every `MIRAR_CONFIG` (20 s). **What decides is never read from memory**: `_lanzar()` and `_soltar()` read the lock for real (`_lock_es_nuestro()` without `de_memoria`), `_tomar()` creates it with `O_EXCL`, and `Conexion.vista` is cleared at the end of the turn, so anything outside a turn reads the disk. Measured, two quiet hours: 30 048 file operations on the drive → 5 035.
  - **Battery and network are not read with no drive in sight** (`_leer_entorno()`): there is no pass to moderate, and on Windows the metered-network question is a COM call that wakes other processes. They are read at once when a drive arrives.
  - **The metered network is asked when Windows says the network changed** (`MIRAR_RED_MEDIDA`, 30 min; `Agente._avisa_el_coste()`): `NotifyNetworkConnectivityHintChange`, which `red.py` already hears, also fires when the connection's cost changes, so a `PIDE_CAMBIO_DE_RED` (and its burst settling) makes the next turn read the whole environment, and between notices the COM question is only a backup every half hour instead of every `MIRAR_ENTORNO` (60 s). Battery and power saving keep their minute. Without a network source, and on Linux (toggling «metered» in NetworkManager brings no `StateChanged`), it is asked every minute as before.
  - **The keychain look asks a cheap question first** (`agente.hay_keepassxc()`, an indirection point; `store.foto_de_procesos()`): on Windows, knowing whether a drive's KeePassXC is open meant opening every process of the host every `sondeo` (10 s) for each root with a keychain. Now one Toolhelp snapshot (names only, no process opened) per look says whether anything is called `KeePassXC.exe`; only then is each root asked whose it is. If the snapshot cannot be taken, and on Linux, the full look is done as before.
  - Not done from that entrega: a finished child waking the loop. It polls every `TICK` while a pass runs, and with a drive in sight the wait is `TICK` anyway, so on its own it saves nothing: it belongs with lengthening the wait while a drive is served, which needs the drive's `state/` to tell of its changes.
- **The name shown for a drive** (#128; `common/nombres.py`, the ONE place; `agente.nombre_de()` for a connected drive, `agente.nombre_guardado()` for one that is not in sight). The tray, the notices and the diary all read `Conexion.nombre` or those two. Without a name of its own: the volume's label if it carries one (`nombres.etiqueta_de()`: `GetVolumeInformationW` on Windows, `/dev/disk/by-label` on Linux; a blank label and the `PRDRIVE` label prdrive itself writes count as none), else «prdrive · <first 4 of the id>». Only if two drives still read the same does the host that provisioned it go behind in brackets (`nombres.distinguir()`), and the first 8 of the id if not even that. Which of two drives that share a label carries the suffix is whichever connects second (`Agente._nombres_de_otras()` compares with the names the others have right now), so it can swap between sessions; the two are never equal at the same time. It used to be the host's network name, which two drives provisioned from the same computer share.
  - **An own name is never touched.** `state/fleet.json` holds the host name that the installer stored at provisioning as if it were a name, so nothing in the file says which is which: the stored name is the host's (and replaced) when it equals one of the hosts the drive has published from (`publicado.equipos`, `nombres.es_del_equipo()`), and an own name otherwise. A drive named after that computer deliberately is told apart by its root's `autorun.inf`: only «Nombre e icono» writes `label=` there, and with the same text it writes into `fleet.json`, so a stored name equal to the `label=` (case-insensitive) is the person's even when it is also a host's (`nombres.elegir(rotulo=)`, `autorun.leer()` in `nombre_de()`, host roots included). Seen on the owner's encrypted host root (18/10/2026): named «PERETATIL» on a host «Peretatil», it showed «prdrive · 1838». A `label=` that differs from the stored name says nothing, and alone it names nothing. **The name the agent remembers (`Unidad.nombre`) never goes into that decision** (#155): the agent computed it, nobody typed it, so feeding it to `nombres.elegir()` as `guardado` would make the first default an own name for good (while `fleet.json` has no `nombre`, i.e. the fleet note was never published: a label that changes stayed the old one, what 0.7.4 stored never got the default above, a drive whose twin was removed kept the id suffix, and two drives remembered with the same host name read the same). `nombre_de()` decides from `fleet.json` and the label alone and `_conectar()` recomputes it on every connection, rewriting `Unidad.nombre` as a copy to show. That copy is only for a drive that is not in sight (`nombre_guardado()`) and for what the others are called (`Agente._nombres_de_otras()`). A default name defers to an own one, not the other way round. Nothing here changes what is published to the remote (the fleet note keeps the host name) or `fleet.nombre()`.
  - **Not covered**: the window's own lists (`ui/tk_equipo.py`, `agente.py status`) keep reading `Unidad.nombre` with their own fallback.
- **Detection** reuses `penwatch.candidate_roots()` (still the one drive walk). Linux wakes on `POLLPRI` of `/proc/self/mountinfo` and bursts; Windows bursts on the tray window's `WM_DEVICECHANGE` (both then fall back to a `RECORRIDO_RESPALDO` walk, 120 s; it was 30 s, and on a host with no drive that walk was half of what the agent spent); without a tray it polls every `penwatch.POLL_SECONDS` like penwatch. On Windows a drive letter that appears or goes (`letras_de_unidad()`, `GetLogicalDrives`, microseconds, no disk touched; checked in `toca_recorrer()` on every turn) starts a burst like a mount notice, tray or no tray. Two sightings before a drive counts. VeraCrypt vestibules of LISTED drives are opened once per connection (`penwatch.open_container(root, cwd=…)`), never for others, **unless that drive's «Pedir la contraseña al conectarla» is off** (`Unidad.pide_al_conectar()`, below): then `_vestibulos()` records the connection as handled in `Agente.vestibulos` like any other, says so once in the diary («no se abre sola») and asks VeraCrypt nothing; a disconnection is recorded as «already asked» until a walk shows no vestibule («Expulsar» must not bring the password up again).
- **A listed drive plugged in but locked with BitLocker** (Windows; spec `docs/superpowers/specs/2026-10-10-agente-bitlocker-bloqueada-design.md`). A locked volume shows nothing of what it holds, so the agent recognises it by the name Windows gives the volume (`\\?\Volume{GUID}\`: it comes from the mount manager, so it reads the same while locked and needs no elevation; `bitlocker.volumen_de()`, which never raises).
  - **Remembered** in `equipo.Unidad.volumen` by `Agente._apuntar_volumen()`, every time a listed drive is connected with its code accepted (`_conectar()`, and the yes of `_atender()`): stored while the volume carries BitLocker (`BitLockerStatus.present`), cleared when it does not, left alone when Windows does not answer. A root with no volume name (a folder a volume is mounted on, anything off Windows) is not even asked its state: `cifrada.bitlocker_de()` answers for the letter in the path, which there is another volume. One volume names one drive: storing it clears it from any other entry. Never for a host root, nor for an unlisted, `cambiada` or `vieja` drive. So a drive is not recognised locked until this host has attended it once unlocked, nor after Windows gives its volume another name (a stick with no serial number in another port).
  - **Seen** by `_mirar_bitlocker()` at the end of every walk: the candidate roots that gave neither a control file nor a vestibule, or answered with `OSError`, are matched by volume name against the remembered ones of listed drives that are not connected and not in mode `nada`. A match counts only if `cifrada.bitlocker_de()` says `locked`; any other state, or none, shows nothing. Nothing is read from or run on the drive, so one sighting is enough. `Agente.bitlocker` (id → root) goes to `resumen()["bitlocker"]` (`id`, `nombre`, `raiz`, `desbloqueando`), `estado.json`, `agente.py status` and one diary line per connection. With no remembered volume (always, off Windows) no root is asked anything.
  - **The walk runs every `RECORRIDO_WINDOWS` (5 s) while one is in sight**, tray or not (`Agente.cada_recorrido()`): it is not known whether Windows broadcasts anything when a volume is unlocked. Each walk leaves the time of the next one in `Agente.proximo_recorrido`, from what it has just seen, and the loop asks `toca_recorrer()`; so the walk that first sees a locked drive already shortens the wait.
  - **«Desbloquear…»** is `PIDE_DESBLOQUEAR` with the drive's id (`agente.py desbloquear ID`); with any other id, or none, the request is still the encrypted host root's (`_es_de_bitlocker()`). `agente.desbloquear_bitlocker()` (an indirection point) launches `bitlocker.orden_desbloquear()`: `%SystemRoot%\System32\bdeunlock.exe E:\`, what Explorer's `unlock-bde` verb runs. The agent never sees the password, never elevates and **never prompts on its own**. One prompt per drive while its process lives (`desbloqueos_bitlocker`), then a `RAFAGA` of walks; if it cannot be launched, a notice says to unlock it from Explorer. Unlocked is when the walk reads the control file, and from there it is the normal path: two sightings, the fingerprint, the mode.
  - **«Pedir la contraseña al conectarla»** (#123, `Unidad.pedir_al_conectar: bool | None`, in `agente.json`; `None` is «as always according to the type»: VeraCrypt yes, BitLocker no, so no host changes unless someone asks; `Unidad.pide_al_conectar(cifrado)` is the ONE rule for the effective value). It is a setting of THIS host for ONE listed drive, not of the drive and not global (`pedir_al_iniciar` stays the encrypted host root's). A host root never carries it (`desde_dict()` drops it).
    - **VeraCrypt**: see «Detection» above; off means no `abrir_contenedor()`, nothing else. The tray has no entry for a closed vestibule drive (`resumen()["unidades"]` is the connected ones), so with it off the way to open one is the drive's own «Abrir PRDRIVE»; the setting is changed with the drive open.
    - **BitLocker**: `Agente._pedir_bitlocker()`, called by `_recorrer()` right after `_mirar_bitlocker()`, asks Windows' prompt through `_desbloquear_bitlocker()` for a locked drive in sight whose effective value is true. **ONE decision per connection**, with the value of the first walk that sees it locked (also at logon: the agent starts with nothing seen), whether the window comes out or not: `Agente.bitlocker_tratadas`. So a cancelled prompt is not insisted on, switching it on with the drive already seen locked applies from the next connection, and a failed launch notifies once (as the manual one) instead of every 5 s. The mark is dropped only when the drive's volume is no longer in sight at all, locked or not (`bitlocker_presentes`, plus the connected ones): a drive that was connected and comes back locked with the cable in (an «Expulsar» that leaves it locked, a manual re-lock) is the same connection (`_desconectar()` marks it), so it must not bring the prompt back up. The «Desbloquear…» request is the person's and always goes through. It is a system window and not a notice: it does not look at moderation (`moderacion.py`) or at the agent's pause.
    - **Where it is asked**: `PIDE_AJUSTE_UNIDAD` (`id`, `clave`, `valor`; `Agente._ajuste_de_unidad()`), the per-drive twin of `PIDE_AJUSTE`: only `equipo.AJUSTES_DE_UNIDAD`, only a listed drive that is not a host root, `valor` a boolean or `None` (back to «as always»); anything else is refused in the diary and changes nothing. It goes to `agente.pide`, not to a root's mailbox (it is not in `PIDE_SERVICIO`).
    - **What the UI is told** (`resumen()`): per connected drive `cifrado` (`equipo.CIFRADO_VERACRYPT` when its vestibule marker is in the last walk, open or not (`Agente.con_vestibulo`); `CIFRADO_BITLOCKER` when `volumen` is noted; empty otherwise) and `pedir_al_conectar` (the effective value); per `bitlocker` entry, `pedir_al_conectar`. The tray and the window offer the setting only where `cifrado` is set and the value is a boolean (`tray.md`, `agent-window.md`); `agente.py status` prints it for a drive whose setting was touched and for a connected encrypted one.
  - **Unverified on a real Windows**: the section «Una unidad bloqueada con BitLocker» of the pending list (rows B7–B9 for the prompt coming up by itself, whether it takes the foreground when the agent launches it, and what Windows leaves in sight after «Expulsar»).

## Notifications and D-Bus

- **Notifications only when a pair STARTS failing** (`planificador.empieza_a_fallar`), STARTS being skipped for needing `--resync` (`Agente.saltadas`: the planner counts a skipped pass as done, so without this the pair stops syncing unseen; cleared by an `OK` or `FALLO`, kept through `RED`, carried as `saltadas` per drive in `resumen()` for the tray), or a remote goes offline: `common/avisos.py` (D-Bus `Notify`; Windows `Shell_NotifyIconW` NIF_INFO on a temporary message-only window, **unverified on real Windows**). No Tk in the agent process: `tests/test_install_agente.py` checks `tkinter` isn't in `sys.modules` after importing it.
- **`common/dbus.py`** cites the *D-Bus Specification* like `ui/qr.py` cites ISO/IEC 18004: keep the citations. It has the calling half (address, EXTERNAL, marshalling, calls, properties, `AddMatch`) and, for the Linux tray, the answering half: `pedir_nombre()`, `exportar(ruta, Interfaz…)` (methods with their in/out signatures, read-only properties), `emitir()`, `atender()`, and `Peer`/`Introspectable`/`Properties` answered for every exported path. A call that arrives while `llamar()` waits is answered then and there when something is exported (a watcher may ask before it replies); a handler's exception is a `Failed` error for the caller, never a crash. `tests/test_dbus.py` pins the canonical `Hello` bytes; `tests/_bus_falso.py` is a bus that also calls the client, as a tray host does.

## Installing (`install/agente.py`)

Code and runtime each in a per-version dir, swapped with `os.replace`, old ones pruned. It imports penwatch's `device_id`/`mode` and **uninstalls penwatch** (and says so). It registers through `common/presencia.py` (next section): on Windows the HKCU `Run` value and the «Aplicaciones instaladas» entry, on Linux an XDG autostart (`penwatch.autostart_desktop()`, `Exec=` quoted per the Desktop Entry spec), **not** systemd: notifications, the question and VeraCrypt's password need the graphical session. `arrancar()` launches the agent itself (`presencia.arrancar()`), no longer `schtasks /Run`. Uninstalling never touches a drive or a host root.

- **Dependency rules**: the agent imports penwatch, never the reverse; penwatch imports nothing of the project (`tests/test_install_agente.py` walks its AST). `agente.py` is in `build_installer.DATOS_FICHEROS` but NOT in `deploy.DEPLOY_FILES`: it goes to hosts, not devices.
- The wizard's final step offers «Que lo atienda el agente de este equipo» instead of installing penwatch. The wizard's route and the host root: `host-root.md`.
- Updating the agent itself («Actualizar»): `agent-window.md`.

## What it leaves outside `equipo.DIR`, and uninstalling (`common/presencia.py`)

The owner's rule: **discreet and clean**. Outside its folder the agent leaves only what starting and removing it need, all per user (HKCU, the home folder), never admin, and uninstalling leaves no trace of it. `presencia.py` travels with the agent (in `common/`), because Windows' «Desinstalar» runs without `install/`; `install/agente.py` calls it for registering, starting, stopping (`parar_agente()`, moved here) and `--desinstalar-agente`.

- **Starting at logon, Windows**: the value `prdrive` of `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (`registrar_arranque()`, a `list2cmdline` line: pythonw + `agente.py run`). Not a scheduled task: the task of earlier versions (`TAREA_VIEJA`, `schtasks /Delete /TN prdrive`) is deleted on every register, so «Actualizar» migrates a device by itself. Windows lists it in Settings → Apps → Startup and Task Manager's «Aplicaciones de arranque»; switching it off there writes `...\Explorer\StartupApproved\Run\prdrive`, which registering never touches (the person's choice survives updates) and uninstalling deletes. Lost with the task, on purpose: its restart-on-failure (3 × 1 min) and priority 7; a crash waits for the next logon or the menu entry. **Linux**: the XDG autostart, as before.
- **«Aplicaciones instaladas»** (`registrar_ficha()`, Windows only): `HKCU\...\Uninstall\prdrive` with `DisplayName`, `DisplayVersion`, `DisplayIcon` (the code's `runsync.ico`), `InstallLocation` (`equipo.DIR`), `InstallDate` (kept from the first install), `EstimatedSize` (KiB of `equipo.DIR`), `NoModify`/`NoRepair`, `UninstallString` = pythonw `agente.py desinstalar`, `QuietUninstallString` = the same with `--si`. No `Publisher`. Rewritten on every install/update (the code dir changes with the version).
- **Starting now** (`presencia.arrancar()`): `Popen` detached (`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` / new session), `cwd = equipo.DIR`, with `entorno_limpio()`: never `PRDRIVE_RCLONE`/`PYTHONPYCACHEPREFIX` (what the old agent gives its children: «Actualizar» starts the new agent from one of them), and from a PyInstaller `.exe` never `TCL_LIBRARY`/`TK_LIBRARY`/`TCLLIBPATH`/`PYTHONHOME`/`PYTHONPATH`/`_PYI_*`/`_MEI*` (they point into the wizard's temp dir, gone when it closes).
- **`agente.py desinstalar [--si]`** (`cmd_desinstalar()`): `chdir` to the temp dir, `presencia.plan_desinstalar()` (consequences + warnings, nothing touched), then `ui/tk_desinstalar.py` (confirm → `working()` → report; `SIN_VENTANA` without Tk or display) or the console (`desinstalar_por_consola()`: asks only on a tty; with `--si`, never, and silent without stdout). The last thing, in a `finally`, is `presencia.rematar()`.
- **`presencia.desinstalar()`**, in order: `parar_agente(quien="El agente")`; `esperar_ajenos()` (`ESPERA_AJENOS`): anything else still running from `equipo.DIR` (`store.procesos_desde()`, minus this pid; usually the host root's window, which runs on the agent's Python) raises `DesinstalacionError` **before anything is removed**; `raices_que_quedan()` (read before `agente.json` goes); Windows: `limpiar_letras()` = `explorador.limpiar(APP_SUBDIR, todas=True)` (also the letters of an open VeraCrypt volume: nobody will remove them later); `limpiar_navegador()` (the keychain's dead browser keys/manifests, the same function `agente.limpiar_navegador()` now delegates to); `quitar_registros()` (Run, StartupApproved, old task, the Uninstall key; Linux: autostart); `quitar_menu()`; `borrar_cache()` (Linux `~/.cache/prdrive/`: exFAT rclone copies, the extracted KeePassXC; kept, and said, while something runs from it); `borrar_carpeta()`. Never a drive or a host root: `raices_que_quedan()` says where each stays (an encrypted one is not closed either, `host-root.md`).
- **The folder from inside itself**: when `components.corre_desde(equipo.DIR)` (Windows' «Desinstalar» runs on the agent's own pythonw) `borrar_carpeta()` only notes it (`_PENDIENTE`) and writes `HKCU\...\RunOnce\prdrive` = `cmd /d /c rmdir /s /q "<dir>"` as a safety net; `rematar()` then, as the process's last act, runs `rmtree` on Linux or `lanzar_suelto(orden_borrado())` on Windows: a hidden `cmd /d /s /c` (CREATE_NO_WINDOW, not DETACHED_PROCESS, so `ping`/`reg` open no console; breakaway from the job if allowed) that retries `rmdir` `REINTENTOS_BORRADO` (60) times a second apart and, once the folder is gone, deletes its RunOnce. If something stays locked (VeraCrypt's driver until reboot), RunOnce removes the rest at the next logon and Windows deletes the entry as it runs it (a brief console flash then, the rare case). A path with `%` is never put in a `cmd` line (it would expand). Run from elsewhere (`--desinstalar-agente`), the folder goes at once, and RunOnce only for what stays locked.
- **What Windows itself keeps** about any program that ran (MUICache, the tray's icon history, notification settings keyed by the executable) is the OS's, not ours, and is not touched.
- **Tests**: `tests/test_presencia.py` (both branches with `_harness.REGISTRO`, the in-memory `HKCU` of `tests/_registro_falso.py` that `_harness` puts in `common/registro.py` for every test, plus `presencia.ejecutar`/`lanzar`/`lanzar_suelto` stubbed there), `tests/test_tk_desinstalar.py` (the window), `tests/test_install_agente.py` (`registrar()` writes both values).
- **Unverified on a real machine**: section «Arranque y desinstalación sin rastro» (U1–U7, plus A1 and A14) of `docs/superpowers/pruebas/2026-09-25-equipo-pendiente-en-real.md`; above all, the name Windows gives the `Run` entry in «Aplicaciones de arranque» (the value's or the executable's, «Python»).

## Hardened after the #54 review (`tests/test_agente_endurecido.py`)

- **Pair names** go through `model.problema_nombre()` in `_build_pair`: no leading `-`, no `/` `\\` `:` or control characters, not `.`/`..` (the name is an argv entry and a folder in `state/` and `filters/`). The agent reads the raw TOML, so `leer_servicio()` drops such names itself, and every pass is `sync.py -- <pareja>`.
- **One agent per host**: `equipo.tomar_lock()` creates `agente.lock.json` with O_EXCL (`store.crear_exclusivo()`) and removes a dead record only by compare-and-delete (`store.retirar_si_sigue()`, the `.romper` rule of `runsync._retirar_ui()`).
- **Writes into a root never follow links out of it**: `agente.en_la_raiz()` resolves the path and the root before the agent writes `daemon.log` (also `O_NOFOLLOW`; capped like runsync's by `store.recortar_diario()`: past `store.DIARIO_TOPE` it keeps the last `store.DIARIO_QUEDAN` lines; it reads only the last `DIARIO_TOPE` bytes, so a huge `daemon.log` on a crafted drive costs no memory, and it opens with `O_NONBLOCK` so a FIFO of that name cannot hang it) or `daemon.lock.json`; `store.write_text()` unlinks a stale `.tmp` and creates it with O_EXCL, which does not follow a link.
- **The host root and its pairs are checked resolved too**: `raiz_equipo._dentro()` is true if either the written or the resolved paths are contained; `revisar_local()` refuses a `local` that a link takes out of the root or into `equipo.DIR`.
- **«Actualizar» skips a ghost**: `install/agente.actualizar_raices()` treats an encrypted root whose `.hc` is free (`vestibulo.retenido() is False`) as locked, like the agent.
- **One service per root**: the agent (`Agente._tomar()`) and runsync's service (`runsync.tomar_lock()`) both take `daemon.lock.json` with `store.tomar_registro()` (O_EXCL + compare-and-delete), never check-then-write. Both write the boot time (`arranque`) and judge liveness with `store.vivo_en_este_arranque()` (`service.md`, «A lock record names its boot»). The agent's record also carries the `pairs` and `interval_min` it serves, and while it holds the root those follow the config: `Agente._al_dia_el_lock()`, called on each turn that serves the root with its own lock, compares them with what it last wrote and rewrites the record only when one changed (`con.lock` changes only once the write has succeeded). A failed write is retried every `RELEER_REGISTROS`, not only at the next pass.
  - runsync's service finding the agent's lock touches `daemon.stop` and waits (`ESPERA_AGENTE`) for it to let go; the launcher's `stop_previous_daemon()` no longer deletes the **agent's** lock on timeout.
  - The agent leaves a `daemon.stop` alone while another live service holds the lock (it is for that one), re-checks the lock is its own right before each pass, and a fresh connection clears a lock with its own pid left by the previous one. A runsync service steps down when a live record of someone else appears.
  - What remains: a drive with an older runsync still writes without looking, overlapping at most the pair in flight.
- **Stopping the agent waits for its pass.** Each pass runs in its own session/process group and is recorded in `equipo.pasada_json()` (pid, drive, pair, and the boot time, `store.arranque_del_sistema()`, so a pid from another boot is ignored). `install/agente.parar_agente(avance)` waits for the agent AND that pass up to `ESPERA_PASADA` (10 min), saying so (`avance(fracción, texto)`; the wizard shows it under the bar, the CLI prints it once per text), then kills the agent first (so it cannot see the pass end, count a failure and delete the record) and the pass with its rclone (`matar_arbol()`: `killpg`, `taskkill /T`). A new agent launches nothing while the previous one's pass is alive (`Agente.heredada`).
- **A cut pass leaves bisync's `.lck`**, which expires by itself two minutes later (`--max-lock 2m`); before that, the next pass of that pair fails with «prior lock file found» and notifies a failure that is not one (H-15).
  - `parar_agente()` records the cut in `pasada.json` (`equipo.apuntar_corte()`: `cortada`, plus `raiz` from the record).
  - The next agent reads it at start (`Agente.cortada`, `equipo.pasada_cortada()`) and `_raices()` leaves out **that pair only** for `equipo.ESPERA_TRAS_CORTE` (150 s). Nothing deletes the lock: rclone's own expiry decides.
  - A pair whose own flags raise `max-lock` can still fail once, as before.
- **The id is not a credential.** «Atender» records `agente.huella(raiz)` in `equipo.Unidad.codigo`: sha256 of everything in `.prdrive/` except what changes with use (`state/`, `logs/`, `filters/`, `keys/`, `runtime/`, `bin/`, `keepassxc/`, `sync_config.toml`, the control file, `.ico`, `__pycache__`); a few MB, milliseconds.
  - **Why `keepassxc/` is out**: reading KeePassXC (78 MB, 131 files) costs 8–9 s on a pen drive, and its configuration and browser JSONs change with use (and with the drive letter): in the fingerprint, activating the keychain, using KeePassXC or opening it on another host would each make the drive ask «su código ha cambiado». Only the **top-level** folder is skipped (`HUELLA_SIN_CARPETAS` applies at `.prdrive/`, like `bin/`). What the agent still runs from there is checked, not fingerprinted: every launch or registration compares the executable with a SHA-256 in `common/pins.py` (`llavero.md` «Checked before it is launched or registered»), and `pins.py` and `keepassxc.py` are in the fingerprint. The DLLs beside the executables are the accepted gap.
  - The question window's title says which case it is (`tk_agente.titulo_ventana()`: «prdrive — unidad nueva» or «prdrive — código cambiado»; `--cambiada` already reaches `pregunta.py`).
  - Another hash on connect = `Conexion.cambiada`: not served, no window; the tray offers «… (código cambiado)» · «Atender con su código nuevo…», and `pregunta.py … --cambiada` asks again (the yes keeps the mode). An empty `codigo` (listed by the wizard or `atender ID` unplugged) is recorded on the first connection.
  - Children get `PYTHONPYCACHEPREFIX` in `equipo.DIR`, so a drive's `__pycache__` is never read. Every update of a drive therefore asks once.
  - `install/agente.preparar()` warms that cache for the agent's own code, right after `poner_runtime()` (`calentar_codigo()` → `deploy.precompilar(codigo, python, prefijo=equipo.DIR/"pycache")`, best effort): the prefix applies to **every** `.pyc` of the child, the stdlib's too. A drive's code is warmed at its first use. The agent's code fingerprint already leaves `__pycache__` out.
  - **What the agent refuses to serve** in `sync_config.toml`: `leer_servicio()` runs the raw TOML through `model.comprobar_seguridad(crudo, es_equipo(app), carpeta_programa=APP_SUBDIR)` before serving a root (`engine.md`) and turns its `ConfigError` into the `ValueError` that says why the root is not served, so drives whose own code predates that gate are covered too (`orden_sonda()` hands each pair's `remote` to a `rclone lsd` on this host). It refuses: the flags the script owns (`--config`, `--workdir`, `--resync`…), flags that run a program (`*-command`, `*-ssh`, `rc`…), flags that write arbitrary host files (`--cpuprofile`, `--memprofile`), unsafe remote names (connection strings, a one-letter name that rclone reads as a Windows drive), an `include`/`exclude` entry with a line break, and a `local` outside the root (`..`, drive letters, `:` and dots-and-spaces tricks, the program's and the keychain's folders).
  - **The config is read again right before every pass** (`Agente._lanzar()`, `tarea.tipo == pl.PASADA`; `leer_config()`, the same read-and-check `leer_servicio()` starts with). The agent re-reads a drive's `sync_config.toml` only when its mtime changes, and a drive with older code (whose own `sync.py` checks nothing) could be edited keeping the mtime, so the next pass would run an unchecked config. If it no longer passes, or cannot be read, nothing is launched: `Agente._sin_servicio()` leaves the root unserved (`servicio = None`, `motivo = «sin servicio: …»`, a diary line `no lanzo <pair>: …`) and the next turn reads it whole. There is no per-tick read, and a probe (`SONDA`) uses the `remote` already checked when the root was loaded. A root unserved because `comprobar_seguridad()` refused its config is notified once as «<name>: config rechazado» (`ConfigRechazada`, a `ValueError`); the other reasons (unreadable, not TOML, no pairs) keep «nada que sincronizar».
  - **Not covered**: backend-option redirects (`--sftp-host`, `--*-url`, `--*-endpoint`) that could send credentials elsewhere; `--temp-dir`/`--cache-dir`; the `--*-from` filter files, which on a non-bisync root pair can beat the program-folder `--exclude`; and the travelling VeraCrypt the vestibule of a listed drive opens.
- **The agent never runs a drive's rclone.** `install/agente.poner_rclone()` puts the pinned rclone (`conseguir_rclone()` → `rclone_bin.pinned_rclone()`: cache, hand-placed official zip or download, never the PATH) in `equipo.dir_rclone()/<pins.RCLONE_VERSION>/`; `instalacion.json` records it, `podar()` prunes old ones, `instalado_prep()` needs it.
  - The agent passes it to every child in `model.RCLONE_DEL_AGENTE` (`PRDRIVE_RCLONE`; a missing path when it has none, so the child fails instead of falling back), and `model.rclone_path()` returns that and only that when set (`sync.py`, `catalog.run()` and the window it opens all go through it). The probe runs `agente.rclone_propio()` directly. With no rclone of its own the agent launches nothing from any root (`SIN_RCLONE`, said once).
  - **Drives older than `agente.VERSION_MINIMA` (0.5.0)** would ignore the variable, so they are not served, not asked about, not opened (`Conexion.vieja`, `version_vieja()`: their `VERSION` is inside the accepted fingerprint), and notified once per connection; the tray shows «… (por actualizar)». A listed one is offered «Actualizar a la vX» there (the agent puts its own version on it, `agent-window.md`); an unlisted one keeps «Actualízala para que la atienda» greyed out.
  - A drive synced by the agent and by its own window uses two rclones; with both on the same prdrive version they are the same pin.
