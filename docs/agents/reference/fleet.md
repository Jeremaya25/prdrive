# The fleet registry (`common/fleet.py` + `ui/tk_fleet.py`)

Formerly AGENTS.md «The fleet registry». The catalogue it sits beside: `catalogue.md`; where a device is named: `drive-name-icon.md`.

`<catalog dir>/devices/<device id>.toml`: one small TOML per device (`id`, `nombre`, `version`, `plataformas`, `last_seen`, `last_result`, `entiende`, and optionally `equipos`, `equipos_visto`, `ultima_buena`, `tipo`, `cifrado`), the id being the `id=` of `.prdrive/PRDRIVE`. **Each device rewrites only its own**, so there is nothing two devices can clobber and therefore no `catalog.push()` ceremony (that protects a file governing deletions; this is a presence note).

- `fleet.olvidar(quien, raw)` is the **one** exception: it deletes a note instead of writing one, so a dead device does not sit in the list forever. It destroys nothing (the owner republishes next time it is plugged in), so it takes an `askokcancel`, not `confirmar_plan()`. **A device cannot forget itself**: that guard is in `fleet`, not the window, because it is a property of the operation. Unlike `publicar()`/`leer()` it returns the reason it failed.
- `nombre` lives in `state/fleet.json` on the device, not only in the note: it must survive with no network, and reading a hostname would rename the device on every machine it is plugged into. `deploy` writes it at provisioning and calls `fleet.recordar()` so the first pass doesn't repeat it. **After that it changes in one place only**, «Ajustes» → «Nombre e icono» (`drive-name-icon.md`): «Dispositivos…» shows the name and cannot edit it, so `tk_fleet` has no `pedir_nombre()` and `open_dialog()` returns nothing. A rename publishes on the next real pass, not at once: `guardar_nombre()` leaves `publicado` untouched and `hace_falta_publicar()` compares the name.
- **`entiende`** is what this code can read and an older version cannot (`fleet.ENTIENDE`, today just `remote.toml`): it lets another device ask before doing something that would leave an older one behind («Renombrar el catálogo…», `catalogue.md`). A list, not a version threshold, so the answer does not depend on which release each thing shipped in; a note without it reads as `()`. It is part of `_sin_fecha()`, so a device publishes once after updating.
- **Published after every real pass, good or bad** (`sync.py main()`, never for `--dry-run`): a fleet where everyone says 'ok' cannot show which device has been failing for weeks. `hace_falta_publicar()` throttles it, because the daemon runs one `sync.py` per pair per cycle.
- `publicar()` and `leer()` **never raise**; a note is not the sync, and `parse()` tolerates a half-written or future-version one. Staleness is `DIAS_OBSOLETO = 7`; an unreadable date counts as stale.
- **«Dispositivos…» opens at once and reads in the background (#66).** There is no local copy of the notes, so `refrescar()` shows the chip «leyendo la flota…» and `tk.Indicador` (`tk_fleet.LEYENDO`), keeps what the table had (nothing, on opening: not even `SIN_NOTA`, which is not known yet), switches «Quitar de la lista…» and «Releer» off (`repasar()` keeps quitar off while `dlg.sondeo.esperando`), and hands `fleet.leer()` to `segundo_plano`; `pintar()` paints what arrives. `olvidar()` goes through `working()`, then the list is re-read the same way.

## Where it has been, and since when it fails (#17)

Everything is computed at publish time, with **no new write on the device**:

- **`equipos`/`equipos_visto`** are two *parallel* string lists (latest first, no repeats, at most `MAX_EQUIPOS = 5`), not a list of tables: `config_file.dumps_table()` writes only scalars and string arrays, and teaching it inline tables would touch the serializer behind `sync_config.toml` and the catalogue.
  - `nota_de()` inherits the list from `publicado` in that device's `state/fleet.json` (`<app_dir>/state/` when given an `app_dir`) **only if its `id` matches** (a «Reinstalar desde cero» is another device), puts `equipo_actual()` in front with the pass's `store.stamp()`, and leaves the list alone when the hostname is empty.
  - `parse()` pairs the lists by position: a non-string name is dropped with its date, a missing date is `""`, and it cuts to `MAX_EQUIPOS` on read. `_tabla()` is the one dict both `dumps()` and `recordar()` write, so the throttle compares against what was published.
- **The hostname is published as is, always, and the window says so** in its header. Whoever can read `devices/` holds the remote's key and every synced file; a machine's network name is far less. `equipos` means «where it could publish from»: a failed publish records nothing, and the retry happens by itself on the next pass because the host still differs from the last note's.
- **`ultima_buena`** comes from `results.Fallo.buena` (the pair's `_buena()`), read in the **same** `results.fallos()` call as `last_result`: `fleet.estado(config)` returns both, so they cannot contradict each other. It is the **oldest** `buena` among the failing pairs, or `SIN_BUENA` (`"ninguna"`) when any has none. «None that is recorded», not «never»: a pair that never succeeded and a record older than the `buena` key look the same.
- **`_sin_fecha()`** adds only the current host (`equipos[0]`) and `ultima_buena`: same machine → the 6 h rhythm is unchanged; another machine → published on the first pass; `ultima_buena` only moves with `last_result`. A `publicado` from before these keys publishes once after updating.
- **The table's «Último equipo» column** is the host the device last published from: `Dispositivo.ultimo_equipo` = `equipos[0]` (the list is latest-first; the same value `_sin_fecha()` compares), shown by `tk_fleet.ultimo_equipo()` with `SIN_DATO` («—») for a note that predates the list. Only the most recent one: the full list with dates is the card's «Equipos», so the two do not repeat each other. A column = one `COLUMNAS` entry + one cell in `tk_fleet.fila()`. The table is a `tk.Tabla` (drawn on one canvas, `ui.md`: one widget whatever the fleet's size, so the window's count depends only on the card's dates; not a `Treeview`): «Este» is an icon, «Última pasada» a chip (`ultima_pasada()`: an `ok` note reads «bien», green; a failure is amber, its row tinted; a device stale for a week is plain grey text). The card under it carries the «Ficha» label, and its «Estado» also says «bien». Tests pick rows with `dlg.tabla.elegir()` and read `dlg.tabla.filas`.
- **The card** (`tk_fleet.ficha()`, pure, no Tk) sits under the table, in the same window (a fourth-level modal was the alternative). The table leaves «Versión» and «Para» to it. **It is a fixed set of labels, filled in place** (`tk_fleet.Ficha`, `dlg.ficha`): the name and id, the four section captions and their lines (`LINEAS_FICHA`: one, one, two for «Estado» and `MAX_EQUIPOS` for «Equipos») are made the first time a fleet has a device to show (`Ficha._construir()`, from `reservar()` or `poner()`), so a window opened on an empty fleet makes none of them. Choosing a row only `configure()`s and re-grids them (`Ficha.poner()`), so it creates and destroys no widget.
  - **The rows flow**: a one-line «Estado» lets «Equipos» move up a row, a two-line one (the «Última pasada buena» hint) pushes it down. A label with nothing to say (the second «Estado» line, an unused date) is `grid_remove`d **and emptied**, so it neither shows nor counts as on screen for `tests/_vista`; the unused «Equipos» lines are `" "` labels, as before, so the section keeps its height. Date labels are made when a fleet needs more than exist (as many as the most dates one device of the fleet shows) and never destroyed, so the window's widget count depends on the fleet's most dates, not on how many devices it has.
  - **Its space is reserved for the largest card in the fleet, measured on the labels** (`Ficha.reservar()`): the `Visor` fits once, on opening, and without that, picking a longer card grew the content and brought up a scrollbar that was not there. `reservar()` fills the labels with each device in turn and reads their `winfo_reqwidth()/winfo_reqheight()` (a label's is right after `configure()`, with no idle pass, on Tk 8.6 and 9; a frame's is not), then adds up what `grid` would: each row the largest of its labels plus their gaps, each column the same (the first with the gutter's `minsize`), the two-column name adding what does not fit to the last, plus the card's padding. The result is the `minsize` of the card's row and column in the window's grid. **No card is painted per device and no `update_idletasks()` is made to measure.** `tests/test_tk_flota_vista.py` pins each device's sum against `grid`'s own at three scalings (a name that spans two columns included) and, at 100 %, each device's card against the old painted one, label by label; `tests/test_tk_medidas.py` walks the whole list to hold that the window never grows when another row is chosen.
  - **Gaps:** the card's 8 and 2 px line gaps are `theme.E2` and `icons.px(…, 2)`: the same at 100 % and scaled on denser screens. Not `theme.medida(2)`: it rounds to 2 pt, which is 3 px at 100 %.
  - **The rest of the window changes in place too:** the card sits in the window's grid with no frame of its own, the chip is replaced only when its `(text, type, icon)` changes, and the empty-fleet sentence (`SIN_NOTA`, `marco` row 2) is made the first time the fleet is empty. Three frames stay on purpose, because folding them is not pixel-identical: `cabecera()` and `donde` (the title and sentence beside the chip and folder would share rows with them, and at 200 % on Tk 9 the chip block is taller than the title block, so the title moved 3 px up and the sentence 3 px down), and `acciones` and `cierre` (one footer frame would size its columns across both rows, and a long note made the window 11 px wider: 800 → 811 at 100 %).
