# Provisioning a device and the build (`prdrive-install.py` + `install/` + `ui/tk_install.py` + `ui/lecturas_asistente.py`)

Formerly AGENTS.md «Provisioning a device» (general part), «The PyInstaller build».
VeraCrypt → `veracrypt.md`; the vestibule → `vestibule.md`; updating an installed device → `updating.md`; the agent's install → `agent.md`.

## The steps

The order is load-bearing: you cannot read the catalogue before knowing the remote, pick pairs before knowing where the device goes, or initialise them before the `sync.py` that does so exists.

```
1 Dispositivo     which volume + the "already a prdrive" shortcut
2 Cifrado         VeraCrypt / BitLocker / none  → fixes state.device_root
3 Conexión        form, or import a remote from the user's rclone.conf
4 Comprobaciones  rclone + connect + read the catalogue
5 Instalación     full/light + platform list; copy .prdrive/, hide it, rclone +
                  runtime per platform, launchers, rclone.conf + keys
6 Parejas         pick from the catalogue, write sync_config.toml, make dirs,
                  publish the device's note in the fleet registry
7 Llavero         optional: none, a base of one's own, or the remote's
                  (KeePassXC + [keychain] + .keychain/, `llavero.md`)
8 Inicialización  --resync of the bisync pairs (and the keychain's first pass)
9 Verificación
```

(The list starts with «¿Dónde?», unit or this host, which the step titles count too.)

Each step disables «Siguiente» until its condition is met. **No console fallback** (unlike `runsync.py`): this happens once in a device's life. Step 5 copies a folder of its own and touches nothing else, so it needs no `--dry-run` ceremony and runs straight through `ui.tk.working()`. With VeraCrypt `.prdrive/` lives *inside* the container, so the volume looks empty until mounted: detection re-runs at the end of `_paso_cifrado`.

**Window sizing: one re-fit per step, and no walking.** A step change (`Wizard.ir()` → `repintar()`) draws the step with `Wizard._pintando` set, so the `revisar()` calls its own drawing makes (the list that lands in mid-draw, the «ya es un prdrive» panel chosen with it) only switch «Siguiente»; `repintar()` re-fits the `Visor` once, when the step is complete. A panel that appears later, outside a step change, still re-fits on its own. The window is centred **once**, when it opens (`run_wizard()`). After that it grows in place: `Wizard.reencajar()` does not call `centrar()`, and `Wizard._al_cambiar_tamano()` moves it only when its bottom or right edge would leave the usable screen (`ui.tk.pantalla_util()`), by the least that brings it back, keeping the top-left (`_sitio_en_pantalla()`). That move is requested on idle, after Tk has applied the new size: asked from inside the `<Configure>` of the size change it is lost on X11 without a window manager (measured), and `winfo_reqheight()` still holds the old size until the next idle pass, so `reencajar()` cannot decide it.
**Why:** on Windows every move or resize of a toplevel repaints every widget, each of them a native window. Pressing «Siguiente» on «¿Dónde?» showed «Dispositivo» in 450 ms there (63 ms on Linux), measured on Windows CI with the timing check's warm-up profile: `revisar()` → `reencajar()` ran three times per step change, each run that changed the size called `centrar()` (168 ms, nearly all of it `update_idletasks()`), `Visor.crecer()` took 68 ms, and the paint that followed took 210 ms. Now a step change costs one re-fit and one resize, and a move only when the window must come back on screen.

**Paint first, read after** (`ui.md` «Waiting helpers»). No step of the drive route waits on the Tk thread for the volume list, the host's Python, the device verification or the fleet note: each read goes through `segundo_plano` into a `Sondeo` hung off the step's own frame (a step change destroys the frame and cancels the wait), and the write to the remote goes into `working()`. The host route and the encryption panel are `host-root.md` and `veracrypt.md`.
- **«Dispositivo»** paints its list empty with an `Indicador` «Buscando unidades…» under the card and reads `device.list_volumes()` (`lanzar_sin_repetir("unidades", …)`, waited on by `tarjeta.sondeo`); «Actualizar lista» is off while it reads and reads the same way. A read that raises says why in the same line (`Aviso.`) and leaves the list empty, with «Actualizar lista» back on. The device chosen before is set aside (`wiz.state.device = None`, so «Siguiente» is off) and selected again when the list lands, if it is listed. «Usar esta ruta» checks `is_dir()` and `device.volume_for()` in a thread too (`lecturas_asistente.examinar_ruta`, `manual.sondeo`): meanwhile there is no destination and the chip says «Comprobando la ruta…»; a path that does not qualify, or that cannot be looked at (a network folder that raises), is said (`wiz.error`) and the choice made before the **first** of the pending presses comes back (`eleccion["antes_ruta"]`: pressing again while it is checked keeps that one, not the intermediate state).
- **This step decides which drive gets written, so only the latest choice counts.** Choosing a row, «Usar esta ruta» and «Actualizar lista» bump a step-local turn; a thread result asked for in an older turn is dropped. The list that lands late is still drawn, but selects nothing if anyone chose meanwhile. The step's own `selection_set`/`selection_remove`/`delete` also fire `<<TreeviewSelect>>` (later, from the event queue), so the handler ignores a selection equal to the one the step last applied; without that, a hand path chosen after a row was undone by the row's late deselection event.
- **«Comprobaciones»** asks `device.check_python()` inside the same `working()` job that checks rclone, the remote and the catalogue, and keeps the answer in `Wizard.python_equipo`; repainting the step shows the kept row, or «sin comprobar» when there is none. The answer is forgotten when the connection is dropped (`soltar_conexion()`) or the route changes («¿Dónde?»): it belongs to that connection and that route. A question that raises is a «sin comprobar» row, never a failed remote check.
- **«Parejas y configuración»** writes `sync_config.toml` and the local folders on the click, as before (local and quick), then publishes the fleet note through `working(…, "flota", partial(deploy.publish_fleet_note, …))`: up to 45 s against a remote that does not answer, behind the bar instead of a frozen window. A failure of `working()` itself reads as «no se ha podido apuntar» (best effort).
- **«Verificación»** runs `comprobaciones_dispositivo()` (`verify_device()` plus, with VeraCrypt, the vestibule, the travelling VeraCrypt and the clear-text leftovers on the physical drive) in a thread, waited on by `tabla.sondeo`, with an `Indicador` «Comprobando el dispositivo…» above the table. «Volver a comprobar» and «Desmontar el contenedor» are off until it lands (dismounting while the thread reads the container would fail); «Llevar VeraCrypt…» stays on and re-runs it, and the single `Sondeo` drops the older read. A read that raises says so in the line and leaves no table, with the buttons back on. The helper lives in `ui/lecturas_asistente.py`, which imports no Tk (`tk_equipo.comprobaciones()` is the precedent).
- What stays on the click are small reads of the chosen volume: `install_target()` for the «already a prdrive» panel, `Matriz.para()` and the free space in «Instalación»/«Plataformas», and `_paso_cifrado`'s detection.
- `tests/test_tk_asistente.py` drives all of it with real threads and with `Encargo`s released by hand; `tests/test_install_wizard.py` and `tests/test_tk_medidas.py` set `segundo_plano.lanzar = en_el_acto`, so each read lands before the step is measured.

**Widgets per step (R5).** In the drive route every step body (the descendants of `wiz.cuerpo`) is counted against a budget of 40 widgets, and the counts below are the measured ones, pinned by `tests/test_tk_asistente.py` (the steps it does not name are at or under 40). «Verificación» is not counted that way: `tabla_estado()` stays in ttk because its detail wraps, so it is bounded per row instead, 13 fixed (counting its `Indicador`) plus 4 per check (name, chip, detail and the separator above it) minus 1. «Conexión» builds the «Importar de un rclone.conf» form the first time that card is chosen; its variables belong to the step, so switching back and forth keeps what was typed in either form. The platform list grids its two radio buttons straight into its frame and draws no empty header label (pixel-identical). In `tests/test_tk_asistente.py`'s set-up (5 catalogue pairs, two chosen) the drive route's steps count: ¿Dónde? 7, Dispositivo 14, Cifrado 14, Conexión 34, Comprobaciones 21, Instalación 39, Parejas 23, Llavero 13, Inicialización 11; the platform route's Plataformas 37. Three states are over the 40 of that budget, and the test pins their real counts: «Conexión» with «Importar» chosen, 41 (its form is built the first time that card is chosen, and stays built, hidden, when another card is chosen); «Instalación» 42 on a device that already carries the program (the button and its chip share a frame), and 45 on a drive with someone else's files (the amber notice and the line to type the path). «Instalación» on an empty drive is 39: its button goes straight into the body, since a frame that only groups it changes nothing on screen (checked leaf by leaf, same position and size, on the three states and on «Conexión»).

## Nothing in the wizard spawns a shell

To a behavioural AV engine an unsigned `.exe` in `%TEMP%` spawning `powershell.exe` is the shape of a dropper. Windows is asked directly instead:

- BitLocker state (now `common/bitlocker.py`, re-exported by `install/crypto.py`, so the device can ask it too: `common/cifrada.py`) through `IShellItem2::GetInt32` with a PROPERTYKEY from `PSGetPropertyKeyFromName` (**never** a remembered one). Only state `On` counts as protected: *Waiting for activation* must fail, or the private key lands on a volume whose key is still in the clear.
- The volume list through kernel32, needing `SetThreadErrorMode(SEM_FAILCRITICALERRORS)` (an empty card reader otherwise pops a "no disk" modal) and `TIPOS_OCULTOS` (`GetLogicalDrives` returns mapped network drives).
- There is **no recovery-key feature**: reading one needs elevation.

## The «already a prdrive» shortcut

On `device.install_target() == YA_INSTALADO` step 1 shows the device's version vs the installer's and offers **«Actualizar»**, **«Añadir plataformas…»** and **«Reinstalar desde cero»**. Reinstall is **always** offered, so re-provisioning (new remote, re-encrypt, redo pairs) never needs deleting `.prdrive/` by hand.

- `Wizard.pasos` is an **instance** attribute: three step lists (`PASOS_INSTALACION`, `PASOS_ACTUALIZACION`, `PASOS_PLATAFORMAS`); the button picks one and sets the index. `_ok_destino` stays False until a way out is chosen.
- `install_target()` looks for the **device before the content** (`.prdrive` is in `RUIDO`), or a freshly provisioned volume reads as `VACIO` and the shortcut is missing on the newest device that can exist.
- The short path installs the tree the **installer carries** (`bundle_dir()`, the source step 5 uses): no network. It calls `ensure_control_file(renew=False)`: step 5 renews because it provisions, but renewing here would strand a watcher bound to this device's id. Going back in version is allowed, never silent (`_confirmar_retroceso()`).

## Connection (step 3)

- **`Conexión` is what makes the repo publishable**: `profile.load()` returns an **empty** profile when nothing is embedded and nothing is in the checkout. Not an error: the normal start for a fresh clone. The private key goes to a temp dir recording the owning pid; `remote.sweep_stale()` cleans what hard-killed installers left, asking `store.pid_alive()` first.
- **«Usar esta conexión» talks to nobody** (#47): it turns the form into a `Profile`, so the step says «preparada, sin probar» in plain ink (no ✔, no green: those read as "connection tested"); the remote is first touched in «Comprobaciones».
  - `profile.py` checks locally, on both paths (form and import): a `type`, and `OBLIGATORIAS` = only what rclone marks `Required` with no way round (sftp `host` unless `ssh` is set: an empty host dials `:22`, this machine; webdav `url`; nothing for s3). Those block: the error goes in red in the step and the previous connection is dropped, so «Siguiente» is off.
  - `profile.avisos()` only warns (amber, still enabled): an sftp without `user` logs in as whoever runs rclone on each host. Whether the `type` exists is not checked: that needs rclone, which step 4 has.
- **The key never leaves the device**: `deploy.write_device_remote()` writes `.prdrive/rclone.conf` + `.prdrive/keys/<name>` with **relative** paths (`key_file = keys/…`), which is what makes the device work under any drive letter (rclone resolves them against `cwd = model.APP_DIR`).

## Platforms: the zero-install part

Step 5 and the «Plataformas» short path draw `_lista_plataformas()` over a `platforms.Matriz`: full/light, one checkbox per `pins.PLATAFORMAS` entry (Windows/Linux × x64/ARM64; macOS deliberately absent), per-row sizes and a live total vs free space.

- **Full** = rclone + a python-build-standalone runtime per platform in `.prdrive/runtime/<clave>/`; the root gets exactly `runsync.bat`, `runsync.sh`, `README.md` (a stale `runsync.pyw` is removed). **Light** = rclone only, plus `runsync.pyw` (useful only with a host Python **that has Tk 9**: python.org's Windows builds ship Tk 8.6 (until Python 3.15, per the owner) and the usual Linux distro Pythons link Tk 8.6 too, so they do not qualify; `device.check_python()` asks the host's Python for its Tk and rejects one below 9: see «The host's Python is asked, never imported» under «The PyInstaller build»). rclone stays in `bin/<arch>/` (`windows-x64` and `linux-x64` share `bin/x64`: `rclone.exe` vs `rclone`).
- **Deselecting a provisioned platform deletes only if confirmed** (`Matriz.quitar()` → `_preguntar_borrado()`); unconfirmed = left in place.
- **Downloads are pinned and verified** from `common/pins.py`. Python is **3.14** (3.14.8, release 20261001, since 08/10/2026): its builds ship Tcl/Tk 9.0.4 on all four platforms, so Windows and Linux run the same Tk (3.13 was Tk 8.6.15 on Windows and already 9.0.4 on Linux). **Tk 9 is the only supported Tk** (09/10/2026): a device still on the 3.13 runtime is unsupported until it updates its components from «Ajustes → Actualizaciones»; its window still opens, on the Tk 8.6 paths kept for that (`ui.md` «Which Tk»), so it can reach «Actualizar…». Windows needs `DLLs/zlib1.dll` and `DLLs/libtommath.dll` (hard imports of `tcl90.dll`/`_tkinter.pyd`); `podar()` never touches `DLLs/`. Devices on 3.13.16 see the runtime as a pending component (`components.py` compares version and release). Windows on Tk 9 is covered by real-machine row **F20** (`tests/maquina/f20_tk9_windows.py`: the pinned runtime fetched by the installer itself, then the bundled font, capture protection #59 via `GetWindowDisplayAffinity` on Tk 9's `wm frame`, and the UI test scripts run with its interpreter): ok 16/16 on 08/10/2026. That VM has no interactive desktop: looks on a real Windows remain unchecked.
  - **Linux's Tk is built without Xft** (`…no-xft.x11` in its version string), on 3.13 and 3.14 alike: X11 core bitmap fonts only, no antialiasing, `ui/fuentes/` unusable. So the Linux runtimes carry **a Tk built with Xft beside the stock one**: `.github/workflows/tk-xft.yml` builds the same Tk (`pins.TK_XFT_VERSION`, 9.0.4) with `--enable-xft --disable-rpath` and SONAME `libtcl9tk9.0.so` on `manylinux_2_28` (x86_64, aarch64), checks the sources' SHA-256 and publishes a **prerelease** `tk-xft-<version>-<revision>` (prerelease + `--latest=false`, so `update.py`'s `/releases/latest` never sees it; an existing tag is never overwritten: bump `REVISION`). `pins.TK_XFT_SHA256` pins each package (not read from its own `SHA256SUMS`). Measured 08/10/2026: needs glibc ≥ 2.14 (x86_64) / 2.17 (aarch64) plus the host's `libXft`/`fontconfig`/`freetype`/`libX11`; 1.6 MiB.
    - `runtime_bin.ensure_runtime()` also calls `ensure_tk()`, which **never fails**: no network or a hash mismatch is said through `progreso` and the runtime ships with the stock Tk. `extract()` writes the package's two members (`TK_MIEMBROS`, nothing else accepted) to `lib/tk-xft/` when `tk_xft(plat)` finds it verified in the cache, and the stamp gets `tk = <tag>`; `stamp_text()` defaults to the same rule, so the expected stamp and the written one agree. `components.python_pendiente()` reports a Linux runtime without that line as pending (only if a hash is pinned for its arch), so devices get it from «Ajustes → Actualizaciones».
    - **Choosing at start-up:** `ui.tk_con_xft()` runs when `ui` is imported, before any `import tkinter`: on Linux, if `sys.prefix/lib/tk-xft/libtcl9tk9.0.so` exists, it `ctypes.CDLL(..., RTLD_GLOBAL)`s it; `_tkinter`'s `NEEDED libtcl9tk9.0.so` then matches that SONAME and the stock one is never mapped. Without `libXft` the load raises `OSError`, silently, and the stock Tk loads as before. Anything that imports `tkinter` before `ui` gets the stock one. `tests/test_tk_xft.py`.
  - **Tk 9.0.4 does not redraw on a DPI change**: no per-monitor DPI calls in its DLL, and its manifest declares system awareness, the same as `theme.nitidez()`. It does bring `ttk::entry -placeholder` and SVG photos.
  - **The UI is tested on Tk 9.** CI runs the **whole suite** on Linux and Windows with the pinned runtime's interpreter (3.14.8, Tk 9.0.4), fetched by `tests/_runtime_ci.py` with the installer's own `runtime_bin` before the suite (job `tests` of `tests.yml`). There is no Tk 8.6 leg (dropped 09/10/2026: Tk 9 is the only supported Tk). A Linux job on `setup-python` 3.11 with no display and no `python3-tk` (`python-minimo`) keeps everything that is not a window working on the lowest host Python (`commands-testing.md`). Locally the same: `xvfb-run -a <runtime>/bin/python3 tests/run_all.py`, or one script (`test_tk_medidas.py`, `test_tk_servicio.py`, `test_tk_densidad.py`, `test_daemon_aviso.py`); a system Python runs the windows on whatever Tk it has, and only a Tk 9 result counts. The whole suite passes on the Linux runtime since 08/10/2026 (spec `2026-10-08-frontend-rapido-design.md` §4); the failure pop-up that aborted the process on 03/10/2026 is in `service.md`. `rendimiento.yml` times the real windows on that runtime against `main` (`commands-testing.md` «Timing check»).
  - `runtime_bin.extract()` validates every member before writing the first, prunes pip/idle/tests/C headers (on Linux also `share/` and `libpython*.so`: the interpreter is static), never creates symlinks (exFAT) but materialises `bin/python3` by writing its target under that name, and writes the `PRDRIVE-RUNTIME` stamp **last** (no stamp = not installed).
- **Everything is fetched before the device is touched (#49).** `deploy.conseguir_plataformas(plan)` gets every rclone and runtime into the host cache, verified; only then `apply_platforms(…, conseguido=)` deletes and copies. Step 5 calls it **before** `deploy_code()`. It stops at the first platform that fails (each file was already retried three times; the rest would be minutes more behind a bare bar) and raises one `InstallError` that names it, says the device is untouched and that it can be unticked. `wiz.revisar()` in the error branch of step 5 and «Plataformas» keeps the button in view under that dozen-line message (`test_tk_medidas`).
- **`.pyc` are precompiled on the device, with its own runtime** (`deploy.precompilar()`, `checked-hash`, best effort, 60 s cap; `updating.md` has the why). Both `deploy_code()` and `apply_platforms()` precompile by default (the latter only when a runtime for **this host** lands, `platforms.candidates(platforms.host())`), but the wizard's three jobs (install, «Actualizar ahora», «Añadir plataformas…») pass `precompilar=False` and call `deploy.precompilar_dispositivo()` **as their last write**, after launchers, guide, `rclone.conf`, control file and vestibule: on a nearly full drive the free-space check only warns, and the ~6 MB of `.pyc` must not take the room those need (`tests/test_install_wizard.py` checks the order). The other platforms' runtimes warm on their first use, since `.pyc` carry the interpreter's tag (`cpython-314`). A light install or a host root has no runtime and no `.pyc`. It writes ~6 MB (211 files) on the drive. The resident agent warms its own copy of the code the same way, under `PYTHONPYCACHEPREFIX` (`agent.md`).
- `deploy.install_runtime()` extracts beside and **swaps**; if the old dir can't be moved aside (Windows: a `pythonw.exe` running from it) it fails whole and the old runtime stays. `remove_platform()` renames before deleting for the same reason. **No self-built executables, no `.vbs`.**
- The `.bat` avoids parenthesised blocks (a `)` in the device path would break them), is written with CRLF, and uses `chcp 65001` only in the error branch.
- **Launchers are immutable after provisioning**: written by step 5 and by «Añadir plataformas…» (an old device has no `.bat`, so its runtimes would be useless), **never** by `--update`, «Actualización» or `deploy_code()` (`tests/test_install_deploy.py` guards it). The vestibule outside a VeraCrypt container follows the same rule.

## The PyInstaller build (`build_installer.py`)

Packs the tree the installer deploys (`sync.py`, `runsync.py`, `penwatch.py`, `common/`, `ui/` as `--add-data`) and optionally embeds a connection profile.

- `common/` and `ui/` are in the bundle **twice**: importable bytecode (the installer uses it) and copyable source (what lands on the device). PyInstaller cannot hand back the `.py` of a module it imported.
- **Without a profile** (a plain clone) the binary is generic and asks for the connection in `Conexión`; **with one** (`prdrive-profile.toml` + `keys/`) it is turnkey and must only be shared privately. That split is what lets the repo be public: `install/secret.py` is generated at build time, gitignored, deleted in a `finally`.
- **Frozen-only traps**: `sys.executable` is the installer, not Python (anything the wizard launches from the device goes through `deploy.device_python()`); `sys.stdout` can be None with `--windowed`.
- **The agent's files are data too**: `DATOS_FICHEROS` carries `agente.py` and `pregunta.py` (copied to the HOST by `install/agente.py`, never to a device) and every file of `install.agente.CODIGO_FICHEROS` must be in it (`tests/test_install_agente.py`; `datos()` fails at build time if one is missing).
- **Imports inside functions need no `--hidden-import`**: they are plain `import` statements, which PyInstaller's analysis finds (checked with `modulefinder` on `prdrive-install.py`: same module set before and after the lazy imports of `ui.md`). One by name (`importlib.import_module`, a proxy object) would need one; `tk.precargar()` imports by name, but only on a device, never inside the `.exe`.
- The `.exe` carries **no** runtimes or rclone: step 5 downloads them per platform (verified, cached in `%LOCALAPPDATA%/prdrive-install/`).
- **The `.exe` carries the Python, and the Tk, of whoever builds it.** The CI builds it, and so does the release job (the same action; `updating.md` «VERSION») with the device's own pinned runtime (python-build-standalone `pins.PYTHON_VERSION`, Tk 9.0.4: the wizard paints its icons with SVG) and a pinned PyInstaller, `build_installer.PYINSTALLER` (6.22.3: the spec asks for ≥ 6.22, latest patch of that line, verified by `Instalador`). It needs **Windows 10 or later** (`docs/guia/instalacion.md` says so). `build_installer.main()` runs `comprobar_pyinstaller()` and `comprobar_tk()` (`TK_MINIMO = (9, 0)`; it imports `tkinter` in the build process on purpose: that interpreter is what PyInstaller bundles) before writing the profile, and prints Python, Tk and PyInstaller. **Both are strict, everywhere** (owner's decision, 09/10/2026, since Tk 9 is the only supported Tk; there is no `--estricto` and no `GITHUB_ACTIONS` special case): another PyInstaller version, a missing one, a Python without Tk or with Tk 8.6 raise a `SystemExit` that names what is there and what is wanted and gives the recipe, `_runtime_ci.py compilador` (Windows) or any Python 3.11+ with Tk 9 (`docs/guia/instalacion.md`). The turnkey `.exe` (the profile and `keys/` are untracked) is therefore built on the owner's machine with that same recipe. `tests/test_build_installer.py`.
  - **The CI build** is the composite action `.github/actions/compilar-instalador` (Windows runners; output `exe`): `setup-python` 3.11 only to run the helpers; `tests/_runtime_ci.py compilador windows-x64 DEST CACHE` takes the same verified archive as the `runtime` subcommand (cache key `runtime-windows-x64-<clave>`, the one `tests.yml` fills) and extracts it **unpruned** (`runtime_bin.extract(..., podar=False)`: pip lives in `Lib/site-packages/`), checks its Tcl is `pins.TK_XFT_VERSION` and leaves the interpreter in `PRDRIVE_PYTHON_COMPILAR`; then `pip install pyinstaller==<PYINSTALLER>`, `build_installer.py`, and **the gate**: the built `.exe --autoprueba %RUNNER_TEMP%\autoprueba.json`, waited for 3 minutes at most (then `taskkill /T`: a one-file `.exe` runs a second process), its JSON printed, the step failing on a missing file or a non-zero exit. Composite steps take no `timeout-minutes`: the step that `uses:` the action carries it. `.github/workflows/instalador.yml` runs it on PRs touching the build's own files, by hand, and (temporarily) on the stage branch's pushes, and uploads the `.exe` and `autoprueba.json`. The release workflow (`build-installer-release.yml`) uses the same action (`updating.md` «VERSION»).
  - Observed on 09/10/2026: the PBS 3.14.8 Windows archive has no `tcl/tcl9.0/` folder; Tcl's and Tk's script libraries are zip archives appended to `DLLs/tcl90.dll` and `DLLs/tcl9tk90.dll` (`tcl/tk9.0/` holds only demos), the «embedded data archives» layout PyInstaller 6.22.0 added support for. Unpruned it is 2190 files (65 MB) with pip 26.2.1. Whether 6.22.3 bundles that Tk so that `Tk()`, the SVG probe and the bundled font work inside the `.exe` is only known from an `Instalador` run.
- **`prdrive-install.py --autoprueba RUTA`** (hidden from `--help`; the CI's, not a user's) never shows a window and never calls `report()`: `--check`/`--probe` end in `report()`, which in a windowed `.exe` opens a window and waits in `mainloop()`, so neither can gate a CI job. `cmd_autoprueba()` writes `RUTA` (UTF-8 JSON) item by item, each in its own `try`: `python`, `congelado`, `prdrive`, `tk` (`tk_patchLevel`), `tk9`, `svg` (`icons.svg_disponible()` on a withdrawn root), `tema` (`theme.apply()` on that root), `letra` (`theme.familia("texto")`: «Noto Sans» when `ui/fuentes/` travelled), `pintadas_python` (`icons.PINTADAS["python"]` after the theme: 0 on Tk 9), `asistente` (`tk_install.build()` on a second withdrawn root, then destroyed), `modulos` (`importlib.import_module` of each of `MODULOS_ASISTENTE`: what `ui/tk_install.py`, `ui/tk_crypto.py` and `ui/tk_equipo.py` import inside functions; `tests/test_autoprueba.py` fails when one is missing from it), `datos` (each of `deploy.DEPLOY_FILES`, `DEPLOY_TREES`, `GUIDE_SOURCE` and `install.agente.CODIGO_FICHEROS` under `bundle_dir()`), and, only to read, `python_equipo` and `unidades`. Exit 0 iff `tk9`, `svg`, `tema`, `asistente`, every module and every data file are right; an unexpected exception is written as `error` with what was seen before it. Importing by name here is a check, not what makes PyInstaller collect them: the wizard's own imports do that, the ones inside its functions too.
- **The host's Python is asked, never imported** (`device.check_python()`): `import tkinter` in the installer's process would answer for the `.exe`'s own Tk. Whenever it relies on `python_command()` it runs `device.preguntar_python(cmd)` (an indirection point): `cmd -I -c SONDA_PYTHON`, `stdin=DEVNULL`, captured text, `TOPE_PYTHON_S` (10 s), `CREATE_NO_WINDOW` on Windows; it never raises (a timeout is rc 124, a launch failure 127). It is its own `Popen`, not `subprocess.run(timeout=)`: past the time limit it kills the whole **tree** (`store.matar_arbol()`; on POSIX the child gets its own session so the group exists) and collects what is left for at most `TOPE_RECOGER_S` (1 s), because `run()` (and `store.correr_apuntado()`, same shape) waits without limit for the pipes after killing only the direct child, and a launcher that leaves a grandchild holding them would hang the wizard. The probe prints one JSON line, `{"version": [3, 12, 1], "tk": 8.6}` (`tk` null without tkinter; only the module is imported). No JSON answer (timeout, launch failure, a non-zero exit, garbage, or the **Microsoft Store alias**: rc 9009, or a failure without timing out from a path under `WindowsApps`, named as such in the detail; a Store Python that times out is just «no ha contestado») counts like no Python. **The light install needs Tk 9** (owner's decision, 09/10/2026; `TK_MINIMO`): a host Python whose `tk` is below 9 (python.org's Windows builds, most Linux distributions) is reported as `«…, con Tkinter 8.6»` with why («la instalación ligera pide Tk 9 y este trae Tk 8.6 (los Python de python.org para Windows traen Tk 8.6)») and makes `ok` false, both with `root` (the verification: that device would not start here, and the detail points at «Añadir plataformas…» or a Python with Tk 9) and without it («Comprobaciones», before choosing full or light: the full install brings its own, which the detail says). One **without `tkinter`** still passes: the console menu is the supported fallback. **A host Python older than 3.11** (`PYTHON_MINIMO`: `tomllib`) is said («demasiado viejo para la instalación ligera: pide 3.11 o posterior») and, with `root`, makes `ok` false: a new rule (that device would not start here); without `root` it only says it, unless its Tk is also below 9 (a Tk below 9 fails in both). Without `root` a no-answer is `ok` false too, like «no hay ninguno» always was (stage-3 plan correction m4 said «true without»; it changes nothing, `_ok_comprobaciones` does not read the Python row). The device-interpreter branch starts nothing. It now starts a process (100–300 ms on Windows, up to 10 s on a stuck launcher): keep it off the Tk thread. Both callers are off the Tk thread: «Comprobaciones» asks it inside the «Comprobar» job (`lecturas_asistente.python_del_equipo()`), and «Verificación» through `verify_device()` inside `comprobaciones_dispositivo()`. `tests/test_install_device.py`.
- **Windows on ARM.** Everything arch-dependent (`model.arch_dir()` for `bin/<arch>/`, `rclone_bin.os_arch()`/`cache_dir()`) hangs off `model.maquina_nativa_windows()`: Windows tells an emulated x64 process it is `AMD64`, and only `IsWow64Process2()` answers truthfully. Resolve on the **host**, never store it on the device. Emulated x64 runs but ARM on x64 does not, so fallbacks are one-way: `BIN_FALLBACK_DIRS`, and the runtime chain windows-arm64 → windows-x64 → host Python in `runsync.bat` (whose `%PROCESSOR_ARCHITECTURE%` *is* truthful), `platforms.candidates()` and `penwatch.runtime_keys_for()`. `tests/test_arch.py` fakes the probe.
