# UI (`ui/`)

Files: `ui/__init__.py`, `ui/tk*.py`, `ui/theme.py`, `ui/icons.py`, `ui/console.py`, `ui/segundo_plano.py`, `ui/cifrado.py`, `ui/instantanea.py`, `ui/prefs.py`, `ui/watch.py`.
Formerly AGENTS.md «UI», «Theme, icons and window sizing», «Ajustes». «Reparación» is in `repair.md`.

## Frontends

Two frontends implement the same four operations (`ask`, `approve_resync`, `info`, `run_sync`) and both return `Choice(action, pairs, minutes)`. `ui.start(config, msg)` returns the choice **together with the frontend that took it** (a window cannot dump output to a console that does not exist).

- **`import tkinter` always goes inside functions, never at module top.** `ui/` is imported by headless paths (`--auto`, the service) where tkinter may be absent; the failure must surface when the window opens, so `ui.start()` can fall back to the console menu.
- **Heavy modules are imported inside the function that uses them**, not at the top of `ui/__init__.py`, `ui/tk.py`, `common/update.py` or `runsync.py`: every window, the agent's question and the service pay what is imported at module level (`import ui` 77 → 26 ms, `import ui.tk` 98 → 55 ms, measured). `import ui` loads `common.store` only (`bisync`, `results`, `revision` come in with `pair_status_notes()`, `pair_times()`, `carpetas_del_programa()`, `avisos_de_resync()`; `Config` is `TYPE_CHECKING`). `ui.tk` loads no `update`/`components`/`conflicts`/`revision` and no screen (`progress` stays at the top: 0.8 ms, and `_tono()` would pay a lookup per output line): `main_window()` imports the first four on entry (the first paint reads them) and each click handler imports its screen (`from . import tk_pairs`); `llavero_editor` and the keychain only with `[keychain]` (`tk.linea_llavero()`, `tk_llavero` only when a keychain is involved). The technique is the plain function-level `import`, never a module-level proxy: tests patch these modules where they live, and PyInstaller sees plain imports. `from . import pair_status_notes, abrir, …` in `ui/tk.py` stay at the top: tests replace them there. `tests/test_imports_perezosos.py` counts what each entry point loads.
- **After the first paint the main window imports its screens a little at a time** (`tk.precargar_a_ratos()`, called before `mainloop()`): one module of `PRECARGA` (plus `PRECARGA_LLAVERO` with `[keychain]`) per `after(1)` turn, so a click waits for one import at most (~8–10 ms) and the first «Parejas…» no longer pays its own. It is `after(1)` and not `after_idle`: a chain of `after_idle` leaves timers and events without a turn while it lasts (measured: 90 ms with nothing handled in between, before the window's first `update()`). `PRECARGA` is also what `tk_update` imports before applying an update (`updating.md`).
- `ConsoleFrontend.approve_resync` always returns False on purpose: with a real terminal `sync.py` inherits stdin and asks itself, with more context than a dialog fits (including the warning about a program folder already on the remote).
- **`approve_resync(pending, carpetas=None)`**: `carpetas` maps a pair to the remote folder where it once uploaded the program (`ui.carpetas_del_programa()`, computed where the pending list is built in `ui.manual_args()`; the decision is `revision.carpeta_programa_en_remoto()`). `tk.preguntar_resync()` only draws the sentences `ui.avisos_de_resync()` gives it.
- `save_prefs` stores `known` (the pair names existing then) so a pair added later reads as new and comes back checked.

## Main window and output

- `output_window` colours each line by content (`tk._tono`) using the vocabulary `sync.py` already prints (`=== pair ===`, `  ejecutando:`, `[pair] OK.`…); change the wording there and a line stops being coloured, nothing breaks. It offers **Guardar el log**, the only copy of a good pass. The progress line is the exception: `_tono` recognises it by `progress.ETIQUETA`, **imported**, not retyped, and consecutive progress lines are rewritten in place, also inside one batch and across batches (`tk._Salida`, the `progreso-vivo` mark).
  - **The pass log goes in blocks.** `poll()` (every 120 ms) drains the queue once and `tk._volcar()` does one `insert` and one `see` per poll (a `Text.insert` per line cost 0.42 ms each: 10 000 lines took 4.8 s, now ~0.04–0.08 s). `_Salida` (no Tk, tested headless) decides what goes in, and keeps **the whole output apart** in `_Salida.completa`: the widget only keeps the last `LINEAS_VENTANA = 20_000` lines, but **Guardar el log** writes `"".join(salida.completa)`, never `text.get()`, because it is the only copy of a good pass. `tests/test_tk_salida.py` runs 25 000 lines (with progress lines inside batches) and saves all 24 502 end to end.
- **`output_window` shows its window first and launches the command after.** The window is built and shown (`centrar`, `ensenar`) with no process behind it, and `Popen` plus the reader thread start in `root.after(1, arrancar)`, one event-loop turn later (the modal path schedules it right before waiting). `window.proceso` is the `Popen` once it exists and `None` before (tests read it: `tests/test_matar_arbol.py` waits for it before closing). Three consequences:
  - **Closing before that turn launches nothing.** `cortar()` has nothing to kill and cancels the pending `arrancar` (an `after` that outlives its window is a Tcl background error, `invalid command name`); non-modal, `al_cerrar(1)` still fires once.
  - **A command that cannot be launched is a verdict, not an exception.** `Popen` raising `OSError`/`ValueError` writes «No se ha podido lanzar: …» in the window, which ends as `ERROR (código 127)` (a caller's `veredictos` never softens it): `state["rc"] = 127`, so `al_cerrar(127)` / the modal return value is 127. The window stays open and usable (**Guardar el log** saves that line) and no poll is scheduled.
  - **The main window never stays busy.** Its `en_curso` is set before `output_window` and cleared only by `al_cerrar` (modeless windows only), which fires on every close above: before launching, after a launch failure, and after a normal pass. `tests/test_tk_pasada.py` drives «Sincronizar ahora» through the real main window and the real output window for the three.
- **Closing `output_window` mid-run cuts the whole tree**, not just `sync.py`: a stray rclone would keep the volume's files open. All three cut points (the X, the window's `<Destroy>`, and after the wait) go through `cortar()` and from there `store.matar_arbol(proc.pid)`, so the `Popen` is started as a session leader on POSIX (`start_new_session=True`, what lets the kill signal the group) and with `CREATE_NEW_PROCESS_GROUP` on Windows. A new place that starts a pass and may cut it does the same.
- `tk_pairs.confirmar_plan()` is a real window, one line per consequence, each warning in an amber box; not an `askokcancel`. It is the dialog that governs deletions. Tests replace it, like `mostrar()`.
- **The main window runs syncs itself.** «Sincronizar ahora», and whatever «Reparación» hands back, open a modeless `output_window`; the window disables whatever touches the same state and on close re-reads `state/` and repaints. Only «Iniciar servicio» returns a `Choice` to runsync (absent when the agent is the root's service: «Pausar»/«Reanudar» take its place, see `agent-window.md`).
  - The checkboxes are shared by both buttons and open with the service's pairs. «Marcar todas»/«Desmarcar todas» (two pairs or more) and the «N de M» follow them through each checkbox's `command`, **not** a variable `trace`: a widget's command dies with it, a trace's Tcl command does not and would hold the whole window and its images until exit.
  - The interval is **not** in the main window (#65): it is set once in a device's life, so it lives in «Ajustes → Configuración», and «Iniciar servicio» reads the saved one (`prefs.startup_defaults()`) when clicked, not when painted. The console menu still asks it when starting the service.
  - `ui.manual_args()` (resync question + `--yes`) is shared with the console path. The pairs screen's «Simular», «Examinar…» and «Dispositivos…» write nothing, so none makes `open_dialog` return True.
- **«Expulsar», inside a VeraCrypt container or with the keychain** (`ui/cifrado.py`; `llavero.md`). With the keychain it first closes it (`tk_llavero.cerrar()`); without VeraCrypt it then says «Ya puedes quitarla (Quitar hardware de forma segura)» and closes the window. Closing the window does not close the `.hc`, and with it open the drive cannot be removed. This process runs *from inside* the container (the device's Python is in `.prdrive/runtime/`) and VeraCrypt retries a busy dismount only for 1.5 s, so the button does not dismount: it launches the vestibule's `Expulsar PRDRIVE` script with its cwd on the physical root (`lanzar_expulsion()`, an indirection point) and closes. The script waits, then asks VeraCrypt without `/silent`. Disabled while a pass runs; with the window open there is no service (opening it stopped it).
- **The keychain line**, only with `[keychain]`, between the pairs and «Parejas…»: how the base is (`llavero_editor.linea()`, read with the rest of `leer_estado()`: device files plus one process snapshot) and «Abrir llavero», disabled without KeePassXC or during a pass; on return the state is re-read. Daily use, so it sits in the window, not behind the gear. See `llavero.md`.
- **The watcher line**: what this host does when the device is plugged in. It comes from `watch.resumen()` (files only, no `schtasks`/`systemctl`: it is asked on first paint) and is worded by `watch.linea()`, which the console menu shares. States: `sin_instalar`, `otro_dispositivo` (a host has one watcher; `watch.json`'s `device_id` is another prdrive's), `desfasado` (amber), `instalado` + mode. Its button opens `tk_watch` and the line is re-read on return; it stays enabled during a pass.

## Theme, icons, window sizing

Warm paper, near-black ink, one blue accent, amber for warnings, monospace for paths and flags; 4 px corners (`radius-md`), pill status chips, no shadows. Styles cross **role** with **surface**, because a `ttk.Label` does not inherit its parent's background; `theme.apply()` switches to **clam**, once per Tk interpreter.

- **Drawn controls.** Everything the design rounds (buttons, the button group, entry/combobox/spinbox, cards and `Nota*`/`Ambar`/`Rojo`/`Azul` frames, chips, the progress bar) is a ttk **image element**, not clam's: `icons.caja(widget, tonos, radio, esquinas)` paints a small 9-slice piece (`-border`) with real alpha, one piece per state (disabled, pressed, active, focus, selected, invalid). The focus ring is **inside** (2 px of accent instead of the border; on an accent-filled button a 1 px line of its ink), because an outer ring would need space reserved round every control. Combobox/spinbox arrows are chevron images named `…downarrow`/`…uparrow`, the names ttk's bindings test. If a piece cannot be painted that control keeps clam's look (`_controles()` wraps each family). `tests/test_controles.py`.
- **Corners show the control's `background`** (ttk fills the widget with it before drawing the image), so it must be the colour of the surface the control sits on. Nobody passes that by hand, and it is **not a style**: it is the control's **state**. Every rounded style (`_REDONDOS[...] = True`) has the paper as its own `background` and a `style.map(base, background=[…])` over the three state bits ttk leaves free, `user1`…`user3` (`theme._superficies_por_estado()`, in `apply()`). Each non-paper surface of `_superficies()` owns one combination (`theme._BITS`, seven available, six used: `SUPERFICIE`, `GRIS_FONDO`, `AVISO_FONDO`, `PELIGRO_FONDO`, `ACENTO_SUAVE`, `OK_FONDO`; the table is per interpreter, in `theme._asientos`, because it comes from the theme in use); the most specific combination comes first, since ttk takes the first spec whose bits are all set. `apply()` binds `<Map>` on the control classes to `theme._asentar()`, which reads the parent's surface (a framed card's visible colour is in `_CARA`, since its own `background` is now the colour *under* it) and sets `w.state(["!user1", "!user2", "!user3", *bits])`: one call, no style created, no `<<ThemeChanged>>`, no re-layout. `cget("style")` keeps the style the code gave (`Primary.TButton`), and `w.state()` carries the bits of its surface (none on the paper). `Plano.*` frames are flat and are never re-seated (`_REDONDOS[...] = False`).
  - **Derived styles inherit the map by name.** ttk looks an option's state map up in the *closest style that has one* and only then at defaults. So the map goes on the **base** styles (`_REDONDOS`) and `Grande.Primary.TButton`, `Pequeno.TButton`, `Mono.TEntry` need nothing (`style.lookup(derived, "background", bits)` answers the surface). Two consequences. A rounded style must carry **no other `background` map**: clam's (`active`, `disabled`…) would answer first, which is why `_botones_propios()` and its siblings clear them with `background=[]` before `_superficies_por_estado()` replaces that map. And a style with only a `background` *default* (the `Sobre<RRGGBB>` variants, `Plano.*` frames) answers only while no bit is on, so those widgets are never given bits. Every rounded style has the paper as its default, the quiet buttons included: `CardQuiet.TButton` is the same button as `Quiet.TButton` and takes the colour of whatever it is seated on.
  - **The faces outside the palette keep their `Sobre<RRGGBB>.<style>` variant.** `_CARA` also holds the face colour of the buttons (the accent of `Primary`, the danger of `DangerSolid`): those are not surfaces in `_superficies()`, and they cannot be mapped (no free bits). `_variantes_sobre()` creates the variants for the faces that are not in the bit table, one per rounded style with the `Grande.`/`Pequeno.`/`Mono.` prefixes of `_PREFIJOS_SOBRE` (`asiento.variantes`), and `_asentar()` puts a control that lands on such a face on its variant (with all bits off, since a mapped bit would beat the variant's own default). Strip the prefix (`theme._SOBRE`) before comparing `cget("style")` with a name.
  - **No style is created, configured, mapped or laid out after the first widget of an interpreter.** Each of those operations sends `<<ThemeChanged>>` to **every** widget (75–160 ms with 177 widgets), so `apply()` does all of it and `_asentar()` does none. The styles ttk makes by itself when the first separator, `Plano.TFrame` or `Treeview` appears (`theme._IMPLICITOS`) do not send it, but the timing check counts them as late: `apply()` asks them a question so they exist before any widget. A colour that is neither a surface, nor the paper, nor a precreated face (a `tk.Frame` with a hand-made colour) does not create a variant either: the control is seated on the **nearest known surface** by RGB distance (`theme._superficie_cercana()`, remembered per interpreter) and `theme._avisar_superficie()` writes one line to stderr, once per colour and process. Its corners come out of a nearby tone; a new surface goes in `_superficies()` (and, if there are more than seven non-paper ones, a second map). `tests/test_controles.py` (seating, `<<ThemeChanged>>` while seating and when opening «Parejas» and «Ajustes») and `tests/test_superficie.py` (every rounded style and every surface, light and dark, in every state: the lookup, and on X11 with ImageMagick the four corner pixels of each control) pin it.
  - **A parent whose surface changes after its children appeared** (a list row that is selected and turns blue, the sidebar button that becomes the chosen one) leaves them on the old surface: `_asentar()` only runs on `<Map>`. Whoever restyles the parent then calls `theme.reasentar(widget)`, which re-seats it and every descendant, outside in (each reads its parent's bits; `_fondo_de()` asks a seated rounded parent *with* its bits). It only changes state bits or switches to a precreated variant: no style, no `<<ThemeChanged>>` (`tests/test_superficie.py` §7b–7c).
- **The scrollbar thumb is flat**: `gripcount=0` *and* `gripsize=0` (Tk 9's clam renamed the option and ignores the old one, so the grip came back as a light bar across the pressed thumb), and its border colours follow `background` in every state.
- **Icons carry alpha, and two painters draw them from the same primitives.** `icons._foto()` is the one choke point: every glyph, `casilla`, `opcion`, `disco`, `baldosa`, `app_icon` (`poner_icono()`'s 64/32/16 marks), `marca_estado` and each `caja()` piece goes through it. Left out on purpose: `matriz()` (the QR keeps `put()`'s hard edges) and the 1×1 rules of `theme._filetes()` (opaque). **SVG (Tk 9)**: `icons.svg_disponible(widget)` is a capability probe, not a version check (`PhotoImage(data=<2×2 svg>, format="svg")` in a `try`, answered once per interpreter and released by `icons.olvidar()`; Tk 8.6 answers it with `image format "svg" is not supported`). With it, the image is written as SVG from the very data the rasteriser reads (`GLIFOS`, `_capas_marca()`/`capas_bandeja()`, the `caja()` tones/margins/`esquinas`: `_svg_capas()`, `_svg_caja()`) and Tk paints it in C: ~0.2 ms a glyph against 5–23 ms in Python and flat across scales, and a cold `theme.apply()` goes from ~0.34/0.46/0.66 s (100/150/200 %) to ~0.16 s on Linux. **Python rasteriser** (Tk 8.6, the light install on the host's Python, a Tk 9 whose probe fails, or one image that cannot be described, which `_foto_svg()` also catches when Tk refuses the SVG or gives another size): the PNG path as before, same sizes and `borde`. `icons.USAR_SVG` is the module switch (`PRDRIVE_SIN_SVG=1` sets it off at import, to run any test through the Tk 8.6 path on a Tk 9), `icons.PINTADAS` counts images per path, and `_CACHE` keys carry the path, so flipping the switch never returns the other path's image. The `fondo` argument of `icons.get()`/`disco()`/`baldosa()` no longer changes the drawing and is kept for the callers. PNGs are cached per process (`_PNGS`), `PhotoImage`s per interpreter (`_CACHE`; the probe's answer in `_SVG`). `icons._png()` (the pure-Python painter's encoder, also behind `.ico`, tray and dbusmenu icons) converts each distinct pixel tuple to bytes once per call and each row once **by identity** (`_ensanchar()` and `_con_hueco()` repeat the same list), and its output stays byte-identical: `tests/test_iconos_bytes.py` pins the 25 headless outputs (23 whole; `ico()` and `png_marca()` by their decompressed content, because zlib-ng writes another stream at the same level) and compares `_png` with a plain copy. Nothing that has no Tk (`.ico`, tray, dbusmenu, the drive's icon) ever goes through SVG.
  - **What the SVG has to respect (nanosvg).** No `<mask>`, `<clipPath>` or `<text>`: a `None` tone of `caja()` (a ring) is the tone before it with an inner hole (`fill-rule="evenodd"`, so the hole must lie inside it), and the `None` layer of `marca_estado()`'s pill cut-out paints the `fondo` colour its callers pass (the window's), so without `fondo` that image uses the rasteriser. A dot (`d`) is a `<rect>` (a zero-length square-cap path draws nothing). The strokes of one layer with the same cap and join share one `<path>`, so they union as the rasteriser's minimum distance does. Images are authored in **physical pixels** at their exact size (`width`/`height` are the image's, `viewBox` the grid), never `-scale`/`-scaletoheight`, which round; `bajar` with a fraction is a `translate`; `caja()` pieces keep the widened 256×64 centre (`CENTRO_ANCHO`, `CENTRO_ALTO`), the one-copy tile the AA pieces need.
  - **They are not pixel-equal, and cannot be.** nanosvg splits each row in five, so a horizontal edge at mid-pixel comes out in steps of 0.2 of alpha; the rasteriser's minimum distance counts two strokes closer than a pixel as one and misreads a mitre vertex (the pencil's tip reads 0.5). Measured (`tests/test_iconos_svg.py`, 100/150/200 %): alpha differs 0.7–1.3 % on average over the 33 glyphs (worst glyph 3.3 %, worst pixel 0.50), ≤ 2.3 % over casillas, discs, tiles and marks, ≤ 2.6 % in the corners of a `caja()` piece (worst pixel 0.18); whole screens differ in 0.02–0.05 % of their pixels by more than 8 %. `test_iconos_svg` also checks that `theme.apply()` and `poner_icono()` rasterise nothing in Python on Tk 9, that Tk 8.6 answers «no» to the probe and falls back, and the sizes, `borde` and corner/centre transparency the other tests rely on.
- **Icon next to text: `theme.icono_linea()` / `theme.etiqueta_icono()`**, never a bare `icons.get()` in a text row. The image is exactly one line of the text's role high and the glyph's centre sits `ALTURA_MAYUSCULAS / 2` above the baseline (the cap-height centre, not the line box's, which reserves room for accents above and descenders below). The offset keeps its fraction (`icons.get(bajar=float)` draws the glyph that fraction lower instead of rounding). Same height as the text label, so the two align in a grid row (`sticky="nw"` for both when the text wraps). The line height and ascent come from the **per-interpreter font table** (see «The letter is measured once per interpreter» below), not from a new `tkfont.Font` per call. `boton_icono()` measures the font the button's **style** really carries (`Style.lookup(style, "font")`), not a role: if the bundled semibold failed to load and the system substituted another face, measuring the role would put the icon where the text is not. Measured on the rendered pixels, icon and cap-height centres agree within 0.1 px at 100–200 %.
- **Spacing is the design's scale, `theme.E1`…`E7`** (4, 8, 12, 16, 24, 32, 48 px as points). No other number goes in `padx`/`pady`/`padding`. A control's *height* is the design's (34 button/field, 28 `Pequeno.`, 42 `Grande.`, 32 sidebar row, 24 chip): `theme.relleno_control(widget, alto, rol, lados)` derives the vertical padding from the font's line, the side padding is a scale step.
- **On Linux the device runtime's own Tk has no Xft**, so `ui` preloads the Xft build from `lib/tk-xft/` before tkinter (`ui.tk_con_xft()`, `provisioning.md`). Import `ui` before `tkinter` in anything that opens a window.
- **The font ships with the program**: Noto Sans (Regular, SemiBold, Bold, Italic) and Noto Sans Mono under `ui/fuentes/`, SIL OFL (`OFL.txt`), subset to Latin, punctuation, arrows, maths and box drawing with `pyftsubset` (~550 KB). `theme.cargar_fuentes()` registers them **privately to the process**, before the first `Tk()` (called from `nitidez()` and again from `apply()`): Windows `AddFontResourceExW(FR_PRIVATE)`, Linux fontconfig `FcConfigAppFontAddFile` (Tk's Xft reads it). Nothing is installed. Elsewhere, or on failure, `familia()` falls back to the old stack (Segoe UI…). Semibold is its own family name, «Noto Sans SemiBold» (Tk only asks for normal or bold); Linux's `font.families()` lists only the first name of each file, so `familia()` counts the bundled families as present once loaded. `familia()` asks Tk for the installed families **once per process** (`_instaladas`; not stored while no `Tk()` exists), and `cargar_fuentes()` opens `libfontconfig.so.1` by name first: `ctypes.util.find_library` forks `ldconfig` (~5 ms) and is only the fallback.
- **The letter is measured once per interpreter** (`theme._LETRA`, one `_Letra` per Tk interpreter). `relleno_control()`, `icono_linea()` (and so `chip()`, `aviso()`, `boton_icono()`) ask `theme._metricas(widget, letra)` → `(linespace, ascent, size)`, keyed `(tk scaling, the font's Tcl-list parts)` so a style's `"{Noto Sans SemiBold} 10"` and `fuente("fuerte")` are one entry. The numbers are measured by an ordinary `tkfont.Font(root=widget, font=letra)`, once. `theme.fuente_tk(widget, rol)` hands out the same shared `Font` for measuring text (`ancho_rotulo()` uses it): never change or delete it. With Xft, measuring a font nobody holds reopens the face (0.55 ms per `metrics()`/`measure()`/`actual()`, against 2 µs when held), so each `Font` is **held by a hidden item of a canvas** (`theme.ANCLA`, created with raw Tcl so Python's `winfo_children()` never lists it, never mapped). A held font keeps the pixel size of the `tk scaling` it was opened at, which is why the scale is in the key. `theme.olvidar(interp)` destroys the canvas and the fonts, in the thread of the interpreter (see `service.md`). `tests/test_tk_letra.py`.

- **The palette is the «prdrive» design system** (the «Rediseño prdrive» canvas, its tokens under `project/ds/prdrive/`): `theme.CLARO` and `theme.OSCURO` hold the same keys (`PAPEL`, `TINTA3`, `SOBRE_ACENTO`…), and `theme.usar()` copies one into the module's names. **Always read colours as `theme.X` at call time**: a default argument or a module-level copy freezes the light value (that is why `boton_icono()` defaults to `None`, and the role/surface/chip tables are functions). Text or a glyph on a solid accent/status fill is `SOBRE_*`, never `SUPERFICIE` (in dark the fill lightens and the ink darkens).
- **The theme is decided once per process**, by the first `apply()` (`elegir_tema()`): `PRDRIVE_TEMA=claro|oscuro` wins, else `theme.sistema_oscuro()` (Windows `AppsUseLightTheme`, GNOME `color-scheme`, `GTK_THEME`; any failure reads as light). Interpreters already painted keep theirs; tests that switch call `usar()` and clear `_puestos`.
- Components: `theme.grupo_botones()` (the `ButtonGroup`: radios drawn as joined buttons, `Segmento.Toolbutton`), `theme.chip()` (status colour only in a leading **disc** with its glyph, `icons.disco()`; `solido=True` for the exception seen from afar, «falló»), `theme.aviso()` (solid **tile**, `icons.baldosa()`, + semibold title + ink-2 body on the tone's soft fill; `tk.bloque_aviso()` builds it from a text whose first line, if there are several, is the title; the action button goes under the text in `marco.acciones`), `theme.pista_campo(entry, texto)` (a placeholder, «Buscar un ajuste…»: with Tk 9 the entry's own `-placeholder`, greyed by the `placeholderforeground` that `apply()` sets on `TEntry` (TINTA3), shown by Tk while the entry is empty, focused or not, and returns `None`; Tk 8.6 has none, so `pista_etiqueta()` places a label *inside* the entry, never written into it, so the variable stays empty; it hides while the entry has focus or text and reads the **variable** in its trace because that trace fires before the entry updates), `theme.linea_estado()` (the main window's keychain and auto-start lines: a hairline above, grey icon, ink-2 sentence, quiet action; amber tone for what needs attention). Buttons: `Primary` > `Tonal` > default > `Quiet`, plus `Danger`/`DangerSolid`; `Grande.`/`Pequeno.` prefixes give the 42/28 px sizes. `grupo_botones()` styles each radio by position (`Primero.`/`Medio.`/`Ultimo.Segmento.Toolbutton`): only the outer corners are rounded and the inner ones drop their left border, like the design's `margin-left: -1px`. Separators are a flat 1 px image element (`_filetes`): clam's draws a two-tone groove. `tk.Resultado` is the slot under an action button (the design's `Notice` after «Instalar», «Guardar…»): `poner(texto, tono)` with `ok`/`peligro`/`aviso`/`info` draws a `bloque_aviso` of that tone (first line = title), empty tone a grey hint; the wizard (`tk_install`, `tk_crypto`, `tk_equipo`) says every outcome through it, never with a coloured `foreground`. A connection «preparada, sin probar» is `info` (blue), never `ok` (#47). `tk.Tabla(parent, columnas, al_elegir=None)` is the design's `Table` for lists whose cells need chips or icons (the fleet, the flags editor): `poner([FilaTabla(iid, celdas, tono)])` with cells as text, `CeldaTexto(texto, rol)`, `CeldaChip(texto, tipo, icono)` or `CeldaIcono(nombre, texto)`; row tone `aviso` (amber), `propio` (accent) or `apagado` (grey text); with `al_elegir`, click/arrow selection painted in the accent; `.filas` (iid → cell texts), `.orden`, `.elegida`, `.cabeceras` are what tests read. `tk.tabla_estado(parent, filas, palabras)` is the check table of «Comprobaciones»/«Verificación»: name, chip (`True`/`False`/`None`/`'aviso'`) and detail on a card.
- The brand mark (`icons._capas_marca`) is the system's minimal one: two thick round-capped arcs around a one-piece drive. The tray pill is **cut out** of the field (a `None`-colour layer erases), no halo; `icons.marca_estado()` paints mark + pill for a dialog header (the service failure pop-up, «Se ha conectado…»).

- **`theme.nitidez()` runs before the first `Tk()`** (all five places that open a root) and declares **system** DPI awareness, not per-monitor (Tk 8.6 ignores `WM_DPICHANGED`). Without it the compositor stretches the bitmap, the blur no font work can fix.
- **Design distances go through `theme.medida()`, never a bare integer** (Tk reads a plain number as unscaled pixels); `icons.px()` is for what Tk cannot scale at all. An eyebrow's gutter is reserved with `theme.ancho_rotulo()` + `columnconfigure(minsize=…)`, never a `width=` in characters. `tests/test_tk_densidad.py` enforces both.
- `icons.py` draws the glyphs itself (no deps, «no emoji»): as SVG when Tk can read it, with its own rasteriser when not (see «Icons carry alpha»); `icons.get()` returns None on failure and the caller keeps its text. `write_ico()` paints `runsync.ico` headless, **repainted** into `.prdrive/`, never copied, so no second glyph table drifts. A `ttk.Treeview` cannot colour one cell, so status chips are row tags (`theme.marcar_lista`).
- **Windows are shown already centred, never moved after the fact.** `modal()` returns the dialog **withdrawn** and without a grab; `mostrar(dlg, parent)` centres, shows (`ensenar()`), grabs and waits. `grab_set()` / `update_idletasks()` must stay on their current side of `ensenar()`. Tests replace `mostrar()`, not `modal()`.
- **Windows are shown already painted: `tk.ensenar(ventana)`, never a bare `deiconify()`** (all six places that show a window). On Windows every widget is a system window painted on its own `WM_PAINT`, and with the drawn controls a screen visibly filled in widget by widget. `ensenar()` cloaks the `wm frame` with DWM (`DWMWA_CLOAK`: the window is mapped and painted but not composed), runs `update()`, and uncloaks it whole; uncloaking is in a `finally`, so a window never stays invisible. No wrapper yet, DWM refusing (before Windows 8) or not Windows: a plain `deiconify()`. `_atributo_dwm()` is the one dwmapi call and an indirection point (`_encubrir()` goes through it; `tests/test_tk_ensenar.py`).
  - **The dark title bar is set there too**, on that same wrapper before showing it: `theme.barra_titulo()` says which DWM attributes (empty in light; in dark `DWMWA_USE_IMMERSIVE_DARK_MODE`, black on Windows 10, plus `DWMWA_CAPTION_COLOR` = `PAPEL` on Windows 11, which Windows 10 rejects) and `ensenar()` asks for them. Never at creation: DWM attributes belong to the wrapper HWND, and `transient()`/`resizable()`, which every window gets, make Tk destroy it and build another (`UpdateWrapper`), so the bar came back light. For the same reason, do not restyle a window after showing it. A refused attribute never stops the window showing.
- **Every screen sits inside a `tk.Visor`** (`encajar()` sizes `interior` to the content or to what fits; scrollbars only when content is left over). The wizard root centres **once**, and `Wizard.reencajar()` hangs off `revisar()`, not `repintar()`, because three things change a step's height without a step change. When even growing does not fit (a long error above the button that retries it), `Visor.ver(widget)` scrolls just enough to show that widget whole.
  - **The Visor is not a `Canvas`**: `lienzo` is a plain frame used as a viewport and `interior` sits in it with `place`; scrolling moves it (`_desplazar()` answers the scrollbars' `moveto`/`scroll` like a canvas: a unit is a tenth of the view, a page nine; `desplazado()` says where it is). A canvas maps its embedded window as soon as that window asks for room, even with the toplevel withdrawn, so everything was laid out and painted once hidden and again on show (×4 the work on «Parejas»). `place` gives `interior` its size while withdrawn (what `ver()` and the tests measure) but maps it only when the viewport is mapped, like any `grid`/`pack` child. Do not put it back in a canvas.
- `tests/test_tk_medidas.py` checks every screen against a matrix of resolution **and** `tk scaling` (the scaling column is the half that matters). The main window opens its own interpreter, so `tests/test_tk_servicio.py` measures it on the same matrix in its worst case: twelve pairs, the amber watcher line, the amber keychain line and «Expulsar» in the footer.

## Waiting helpers

- `tk.working(parent, title, funcion)` runs `funcion()` on a thread behind a bare progress bar, for slow or passphrase-carrying commands. No cancel button.
  - **The bare bar ticks every 32 ms, not every 12** (`PASO_BARRA_MS`), with a step of `SALTO_BARRA = PASO_BARRA_MS / 12` (≈2.67) so it sweeps at the same speed with a third of the ticks (12 ms cost ~10.6 % of a core; 48 ms cost ~2.6 % but looked choppy at 21 fps). `tk._arrancar_barra(barra)` is the one place that starts it, for `working()`, `Indicador` and the bar returning to indeterminate: `ttk::progressbar start ?interval? ?step?` takes the step but tkinter's `start()` only the interval, so it calls Tcl directly and falls back to `barra.start(PASO_BARRA_MS)` (steps of 1) if the Tk rejects it. `tests/test_tk_espera.py`.
  - An optional `progreso()` → `(fracción, texto)` or None turns the bar determinate with the text below while it answers, and back when it stops. It is asked from the Tk thread every 120 ms, so it must only read what another thread measured, and any exception counts as None (the poll is the only thing that closes the window). The text's row is reserved from the start (`tests/test_tk_espera.py`, the matrix in `test_tk_medidas.py`).
  - On closing it hands the grab back to whoever held it (`_devolver_captura()`): Tk keeps no grab stack, and a modal waiting in it (the remote folder picker, at every folder) would stop being modal.
- **A screen that waits for the network opens first and reads after (#66)**, instead of `working()` in front of an empty window.
  - `ui/segundo_plano.py` (no Tk) runs the read on a daemon thread into an `Encargo` (`hecho`, `resultado`, `error`). `tk.Sondeo(dlg, cada=SONDEO_MS)`, one per screen, polls it from the Tk thread every `cada` ms and calls back there, never from the worker, and **cancels with the window** (`<Destroy>` → `after_cancel`), so closing early leaves nobody painting dead widgets. `pausar()` cancels the pending `after` but keeps the `Encargo` and the callback (`esperando` stays `True`); `seguir()` calls back at once if the read finished meanwhile, else polls again. While paused it schedules nothing: an `esperar()` of an unfinished `Encargo` waits for `seguir()`, one that is already done calls back at once (no polling to save). Tests that count its polls assert the delay handed to `after` (wrap `ventana.after`), never «N polls in M ms».
  - The function handed over is a `functools.partial` of data, never a lambda among widgets: a worker holding the last reference to a Tk object frees it off-thread (`Tcl_AsyncDelete`).
  - `tk.Indicador` is the line under the header: the same indeterminate bar as `working()` (`LARGO_INDICADOR`, `theme.medida`) plus a sentence. Bar only while waiting; the sentence may stay (why the screen kept the local copy); nothing to say → the line goes. Both hang off the dialog (`dlg.indicador`, `dlg.sondeo`) for tests. `Indicador.pausar()` stops the bar (Tk animates a `ttk::progressbar` whether or not anyone sees it: 31 steps a second) and leaves the sentence; while paused `poner(…, True)` shows the bar without starting it, and `seguir()` starts it only if the line is still waiting.
  - `segundo_plano.lanzar()` is an indirection point: `test_tk_screens`/`test_tk_medidas` set it to `en_el_acto()` (the result is in before the screen shows, as they never enter the event loop); `tests/test_tk_segundo_plano.py` runs real threads against a `catalog.run()` that answers late or never.
  - **One read alive per kind.** A thread cannot be cut and closing the screen does not stop it, so reopening Parejas (or «Releer») with the previous thread still running started a second `catalog.pull()` writing `state/catalog.toml` at the same time. Both screens go through `segundo_plano.lanzar_sin_repetir(clave, firma, funcion)`: same key and same raw config while the thread lives hands back that `Encargo` (the newest screen waits on it); another config launches a new one, and so does a thread older than `VIDA_MAXIMA` (120 s; `catalog.run()` already bounds its subprocess at 90 s), so one that hangs cannot block every later read. It calls `lanzar()` through the module, so the tests' `en_el_acto()` (always `hecho`) never reuses anything; a test that swaps `lanzar()` for an `Encargo` that never ends (`test_tk_medidas`) calls `olvidar_lecturas()` between screens.
  - Writes to the remote (catalogue push, deleting a fleet note, purging versions, creating or listing a remote folder) stay in `working()`: modal, nothing to cut halfway.
  - **A read left running dies with its window.** A thread cannot be cut, but the process it waits for can. `catalog.run()` (read verbs only: `catalogue.md`) and `watch.consulta()` (the `schtasks`/`systemctl` question) go through `store.correr_apuntado()`, which notes the `Popen` while it runs; `store.matar_hijos()` kills each noted child directly (`Popen.kill()`, no tree: a read starts no processes), forgets them and returns how many it cut. It is the call for a window to make when it closes, or before it launches an eject script, so an rclone with `cwd` on the device does not hold the volume. The waiting thread gets a failed `CompletedProcess` (non-zero code), never an exception, and what it paints is for a window that is going away. Not covered: `penwatch.run_quiet()` (`penwatch.py` cannot change, so a `schtasks` it started can outlive the window), writes to the remote, and a child launched after the call. Process creation does not change (no session or group of its own): a pass cut with `matar_arbol()` still reaches the `catalog.run()` its `sync.py` made. `tests/test_hijos.py`, `tests/test_matar_arbol.py`.

## One read per refresh (`ui/instantanea.py`)

The main window, «Parejas» and «Ajustes» each used to read the device themselves, on the Tk thread (a pair's state several times, the physical root three times — each a walk over the drive letters —, the conflicts twice, a process snapshot). `instantanea.leer(config, notas=, linea_llavero=)` reads all of it in **one pass meant for a daemon thread** and returns an `Instantanea`: frozen, compared by identity, no Tk. Importing the module loads nothing heavy; each reader is imported inside the function that uses it, and each is a module-level function a test replaces (`revision.revisar`, `conflicts.cargar`, `components.pendientes`, `cifrado.expulsion`/`bloqueo`, `model.es_equipo`, `watch.resumen`, `instantanea.estados_de`, and the `notas`/`linea_llavero` it is handed; `commands-testing.md`).

- **The fields are an interface** (other screens read them by name): `estados` (per bisync pair of the user, `(PairState, FiltersState)`: «Parejas» rows; the keychain's is not there), `notas`, `hallazgos` + `cuenta`, `conflictos`, `componentes` + `componentes_texto` + `componentes_actualizables`, `fisica`, `expulsion`, `bloqueo`, `del_equipo`, `vigilante`, `llavero`, `device_id`, `fallos`, `hecha`, `firma`, `huella`. `vacia(config)` is the all-empty one (what the window keeps if the thread itself failed).
- **It never raises.** Each field is read under its own `try`; the one that fails keeps the default a window with nothing to show would use and leaves its `repr` in `fallos[field]`, and the rest is still read. On the happy path `fallos == {}`, and the tests that wait for a read assert it: a stub that does not take a new keyword raises `TypeError` inside the read, and without that assertion the field would silently stay empty («Expulsar» never appears). `estados` is all-or-nothing: one unreadable pair and the field is `{}`.
- **The physical root is looked up once** (`vestibulo.raiz_fisica()`, an indirection point) and handed down: `revision.revisar(config, fisica=)`, `components.pendientes(fisica=)`, `cifrado.expulsion(fisica=)`, `vestibulo.sin_sitio_fuera(device_id, fisica)`. **There is ONE «look it up yourself» value, `vestibulo.BUSCAR`**, the default of `revisar`, `expulsion` and `sin_sitio_fuera`; `None` means «does not live in a container». Never forward one module's private sentinel to another (`components._BUSCAR` is its own): the callee would take it for a root, `fisica / CONTENEDOR` would raise inside `_espacio()`'s `except`, and the «espacio» finding would vanish with no sign. `leer()` always passes a real value. The device id is read once by `leer()` for that lookup and is not otherwise shared: `cifrado.bloqueo()`, `watch.resumen()` and, with `[keychain]`, the keychain line (`cifrada.estado()` finds the root again) ask for theirs.
- **Freshness is a stat snapshot, not a folder date.** `leer()` records `huella` *before* reading: `(path, st_mtime_ns, st_size)` (`(path, None, None)` when missing) of `state/last_run.json` (every pass writes it), `state/conflicts.json`, the `filters/` folder and each bisync pair's workdir `state/<pair>/` (listings, a `.lck`, a shelved baseline), plus the catalogue-duplicate record **by value** (`catalog.duplicado()`, a few-line JSON): every catalogue read rewrites `state/catalog.json`, so its date would make the read stale at each «Parejas» open without changing the one thing read from it. `Instantanea.vigente(config)` is true when `firma(config)` is the same and the snapshot now is **identical** (equality, no slack; `stat`s and that one small file, so the Tk thread may ask). `ui.lock.json`, `ui_prefs.json`, `servicio.pide`, `daemon.stop` and `*.tmp` do not count: the window itself writes them (`state/`'s own date would be stale from the first click). A change made before the snapshot but after the read makes it stale, which is the safe side; a FAT32 write of the same size in the same two-second tick is missed, and that is fine because every plan re-runs `revisar()` before acting (`repair.md`). `firma` is the pairs' name, mode, endpoints and what goes into their filters file (`include`/`exclude`/code rules/`versions`) plus whether `[keychain]` is set, read from attributes only (no path is resolved on the Tk thread); an rclone flag does not change what is read, so it is not in it. `vacia()` has no `huella` and is valid for nobody.
- **What the read writes, it writes first and atomically.** `revisar()` and `pair_status_notes()` go through `bisync.filters_file_for()`, which regenerates `filters/<pair>.txt` when the config changed. `leer()` does that for every bisync pair **before** taking the snapshot (so a read never makes its own snapshot stale), and the write is atomic (`bisync._escribir_filtros()`: a temp file with its own name, then `os.replace`; in place only if the rename is refused, which Windows does for a file another process has open), so «Parejas», opened before the read lands, never reads it half written and sees a spurious `filtros changed`. The read touches nothing else.
- **`Compartida`** (Tk thread only) keeps the latest read: `poner(inst)` stores it and calls every subscriber (all of them, then it re-raises the first error); `suscribir(f)` returns the unsubscribe; `para(config)` is `actual` if it is `vigente(config)`, else `None`, and a consumer that gets `None` reads for itself as before. A screen that subscribes unsubscribes when its toplevel is destroyed.

## «Ajustes» (`ui/tk_doctor.py`): where new affordances go

The main window is deliberately lean: **anything done once in a device's life belongs behind the gear, not beside «Sincronizar ahora»**. The screen is «Ajustes» (the module keeps the old name) and is not the `--doctor` command. It is one window with a **sidebar** and, to its right, the chosen **pane drawn in place** (the «Rediseño prdrive» boards `Ajustes*.dc.html`): `GRUPOS` lists the panes (`Apartado(clave, rotulo, icono, palabras)`) under «Esta unidad» («Esta carpeta» on a host root), «Este equipo», «Conexión», «Mantenimiento», and is the list to add to. «Buscar un ajuste» filters the sidebar (`coincide()`: every typed word must start a word of the label or of `palabras`, accents and case ignored; Enter opens the first left). Next to «Reparación» goes the number of `revision.cuenta(hallazgos)`, next to «Actualizaciones» the pending version. A pane that only shows sometimes goes in `OCASIONALES` too, with a function that decides **without network** (today «Catálogo del remoto», `catalog_editor.ofrecer_renombrado()`). The whole window sits in one `Visor`, and the pane area has a minimum size (`ANCHO_APARTADO`×`ALTO_APARTADO`) so switching panes does not make it jump; a taller pane grows it (`Panel.ajustar()`).

- **Each pane is the screen that also opens on its own** (the main window's auto-start line, its «Reparación» line, the update notices): every one of them draws in a `construir(panel, …)` and its `open_dialog()` is `tk.dialogo(parent, title, construir, ensenar=mostrar)` (the module's own `mostrar`, the name tests replace). `tk.Panel` is what differs: `ventana` (parent of messages, `working()` and sub-modals), `marco`, `incrustado`, and three ways to finish: `terminar(nota)` (done: «Guardar», «Cancelar»; alone it closes, in «Ajustes» the pane is redrawn with the note in a green notice above), `cerrar(despues)` (close the whole window, dialog or «Ajustes», then call `despues()`: how a pane hands a pass to the main window, since two modals cannot hold the grab) and `devolver(valor)` (what the caller is told). `tk.pie(marco, fila)` puts the footer with a stretching row above it, so it sits at the bottom of a pane. A pane's own «Cerrar» is drawn only where the board has one (Llavero, Emparejar, Reparación); network waits hang off `panel.marco` (`Sondeo(marco)`), so switching pane cancels them.
- **A pane that is hidden instead of destroyed pauses what waits.** `Panel.sondeo()` and `Panel.indicador(padre, ancho)` create the `Sondeo` (hung off `panel.marco`, so destroying the pane still cancels it) and the `Indicador` and register them; whoever hides the pane calls `panel.ocultado()` (pauses every registered one, then calls the `al_ocultar(funcion)` callbacks) and whoever shows it again `panel.mostrado()` (resumes them, then calls the `al_mostrar(funcion)` callbacks). `mostrado()` is for showing again, never for the first build, and a stand-alone dialog never calls either. A pane that built its `Sondeo(marco)` or `Indicador(marco)` by hand still cancels with its frame but keeps polling and animating while hidden. `tests/test_tk_panel.py`.
- **Screens that can take the main window's read** (`ui.instantanea.Compartida`) accept it as a last `compartida=None` keyword: `tk_pairs.open_dialog`, `tk_doctor.open_dialog`, `tk_repair.open_dialog` and `tk_repair.construir`. `None` is the screen reading for itself, as before.
- **Results go back on close.** `open_dialog()` returns, per pane key, the last `devolver()`: `llavero` (`ACTIVADO`/`CAMBIADO`: the main window re-reads the config and, after an activation, launches the keychain's first pass), `reparacion`/`componentes` (re-read `state/`), `actualizaciones` `True` or `componentes` `tk_update.CERRAR` (the main window closes: the program or its Python changed), `arranque` (the mode asked of the agent, or `True` to re-read the watcher). The main window's `abrir_ajustes()` does all of it; the panes import nothing of it, and `lanzar` arrives from it (the output window is its child, and it disables itself during a pass).
- «Actualizaciones» shows the new release if there is one (`tk_update.construir`), else stale components (`construir_componentes`, results under `componentes`), else «Buscar actualizaciones», which calls the main window's `buscar_version(responder)` (the network read is the main window's, `mirar_version(respuesta)`; `updating.md`) and redraws with the release if one turned up.
- «Emparejar un móvil» inside «Ajustes» protects the **whole** window from capture while the code is shown (`proteger_de_capturas()` runs before Tk paints the code) and `tk.soltar_capturas()` lifts it when the pane goes (`pairing-qr.md`).

**«Configuración»** (`ui/tk_configuracion.py`, #65) holds what is *configured* rather than done: the service's interval (`ui/prefs.py` decides what is written, see `service.md`) and, only for the encrypted host root, the agent's `pedir_al_iniciar` checkbox (sent as `PIDE_AJUSTE`). Nothing is written until «Guardar», and what did not change is not written.
