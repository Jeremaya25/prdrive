# The window ↔ the agent, and updating the agent

Files: `ui/watch.py`, `ui/tk_watch.py`, `ui/cifrado.py`, `runsync.py`, `common/equipo.py`, `agente.py`, `install/agente.py`.
Formerly AGENTS.md «The window ↔ the agent (phase 5)». Core of the agent: `agent.md`; the tray: `tray.md`.

No ports: two mailboxes of JSON lines, appended by whoever asks and consumed by the agent renaming them first (`equipo.pedir(…, buzon_de=)`/`equipo.recoger(buzon_de=)`).

- **`state/servicio.pide`** (`equipo.BUZON_SERVICIO`) is the ROOT's. The agent drains it only for connected roots **in its list** (`_buzones_de_raices()`; an unlisted drive's is not even read), takes the id from WHERE the file is, never from the request, and accepts only `equipo.PIDE_SERVICIO` (`pausar_raiz`, `reanudar`, `pasada`, `bloquear`); anything else is logged and ignored. The window's «Bloquear» goes through it (`cifrado.pedir_bloqueo()`); the agent still takes `bloquear` from `agente.pide` too (the CLI, the tray).
- **With the agent as this root's service, the footer offers «Pausar»/«Reanudar», not «Iniciar servicio»** (#64). `watch.boton_servicio(res)` is the one pure rule:
  - agent alive and root listed → «Reanudar» if the root is paused (whatever the mode: that pause must never be left without a way out); else, when `watch.Resumen.servicio_del_agente` (alive, listed, mode `daemon`), «Pausar», or «Reanudar todo» while the tray's global pause is on (the label says it is everything);
  - any other case (mode `sync`/`ui`/`nada`, agent dead, drive unlisted) → «Iniciar servicio», which spawns the classic service while the agent steps aside.
  - These buttons leave a request (`watch.pedir_servicio()`: «Pausar»/«Reanudar» to the root's mailbox through `watch.pedir_a_la_raiz()`, an indirection point; «Reanudar todo» `sigue` to `agente.pide`), keep the window open, show what was asked (`watch.tras_servicio()`, like `pedido()`) and stay enabled during a pass.
- **The pause is per root, and it is kept.** The agent's own pause (`pausa`/`sigue`, the tray) stops every drive and lives in memory only; a «Pausar» in one drive's window pausing all of them would surprise. So `pausar_raiz` sets `equipo.Unidad.pausada` in `agente.json` (written by the agent, as always): `_sirve()` stops counting the root, `_contrato()` releases its lock after the pair in flight, `resumen()` carries `pausada` per drive (the tray shows the pause icon and «PRDRIVE-3 en pausa» below avisos), and it survives an agent restart.
  - What it means is «don't come back when I close the window»: while the window is open the agent already steps aside, so `watch.pausa(res)` reads «al cerrarla vuelve el agente, salvo que pulses «Pausar»» (`PAUSA_AGENTE`) under the line, and the line itself says when the root is paused.
  - `reanudar` clears `pausada` and sets `Conexion.reanudar`: when the window's UI lock goes, the agent resumes at once (no `GRACIA`) and drops that root's `marcas`, so it starts with a pass like the service it replaces. A mode change does not touch the pause; `agente.py status` shows it per root.
- **«Iniciar servicio» from the console** (`runsync._atender()`) still saves `ui_prefs.json` and, when the agent IS this root's service, writes `reanudar` (`runsync.pedir_reanudar()`, which also lifts a per-root pause) instead of spawning a daemon. The window reaches that path only if the agent came up after it was painted.
- **The agent's line** (`watch._agente_linea()`): what it does with this root, «en pausa desde esta ventana» from `agente.json`, «en pausa para todo» from `estado.json`, and amber when no agent process is alive. `watch.resumen()` asks `equipo` first: with an agent installed it reports `agente`/`agente_nueva`/`agente_raiz`. Its button («Cambiar…», «Atender…» for an unlisted drive) opens `tk_watch.open_agente()`, which asks the mode with `PIDE_MODO` (`watch.pedir_modo()` → `watch.pedir_al_agente()`, an indirection point); the line then shows what was asked (`watch.pedido()`), since `agente.json` only changes when the agent reads it. A host root is offered `daemon`/`nada` only.
- **`pedir_al_iniciar` in «Ajustes → Configuración»**: a checkbox, only for the encrypted host root (`watch.pedir_al_iniciar()` → None otherwise), sent as `PIDE_AJUSTE` on «Guardar» if it changed.
- **Wizard re-run with the agent of the same version** (`install/agente.misma_version()`): «Instalación» reuses it (`instalado_prep()`); «Arranque» is «Pedírselo al agente» → `anadir()`: mailbox only, menu entry if a root is new, start it only if it is not running. No stop, no re-register.

## A request and the agent's take in the same instant

`equipo.pedir()` returning True means the agent will read that line. Requester and agent are separate processes; what keeps the promise differs per system (`tests/test_buzon_carrera.py`, which also runs real processes).

- **POSIX: a turn on the mailbox's folder** (`equipo.turno()`, an indirection point; `flock`). There the agent can rename a mailbox another process has open; when it read and unlinked it before that process wrote, the line landed in a file already read and was deleted with it. Measured before the turn (ext4, Python 3.12, 12 requester/agent process pairs in tight loops, 10/10/2026): 25391 of 3226738 acknowledged requests never returned, every one of them found in the renamed file past the byte the agent had read.
  - The requester takes the folder's lock **shared** before opening the mailbox and keeps it until the file is closed; the agent takes it **exclusive** after its rename and before reading. So the agent reads once everyone who could have opened that file has closed it, and whoever comes later opens a new mailbox. Shared, so several requesters still append at once (`O_APPEND`). With it: 0 lost of 12.5 million in the same runs (also with four requesters per mailbox and under CPU load).
  - The lock is on the folder (`state/`, `equipo.DIR`) because the folder never changes name: no lock file is left, and no check of which file an open descriptor still is.
  - **Nobody waits for good.** Both sides try without blocking every `PASO_BUZON` (2 ms) for at most `ESPERA_BUZON` (0.5 s) and then go on without the turn, so a process stopped while holding it hangs neither the agent nor a window. Where the filesystem refuses `flock` they also go on without it: the behaviour before the turn.
  - `flock` on a folder works and excludes on ext4, tmpfs and 9p (checked). FAT32, exFAT and NTFS mounted on Linux, where a drive's `state/` usually lives, are **unverified**: row V15 of the pending list (`tests/maquina/f22_buzon_turno_linux.py`).
- **Windows: nothing to turn.** The agent's rename fails while anyone has the mailbox open, and it takes it on its next tick. The other way round, opening the mailbox while the agent renames it is refused (`PermissionError`): `pedir()` tries again every `PASO_BUZON` up to `ESPERA_BUZON` and only then returns False. Measured (NTFS, six pairs in tight loops): 3643 of 97223 requests returned False before, 0 of 89178 now; none lost either way.
- **Both ends need the turn.** The agent and a drive's window can be different versions; one with the turn against one without is as before, no worse (lost per million in one run: 3557 new window/old agent, 3900 old window/new agent, 4554 neither).
- **How likely it was.** With the agent's real tick (`TICK`, 2 s) a request was lost when its open-to-write gap (10–35 µs measured) straddled the agent's rename-to-read: about one request in 10^5 to 10^6 on ext4 (loss rate × tick stayed at 1–4 µs with spaced requests and ticks of 1, 5 and 20 ms; one loss in 4160 cold requests at a 0.25 s tick). Silent when it happened: the window showed the request as asked (`watch.tras_servicio()`).
- **A False is said.** `install/agente.aplicar_unidades()` raises `InstallError` when a request cannot be left (the wizard shows it and the button can be pressed again; asking twice changes nothing), and `parar_agente()` asks again on every turn of its wait while «parar» has not been left: an agent never told to stop launches its next pair and ends up cut by force with it.

**What a request can still lose:**

- **Windows, two requesters on the same mailbox in the same instant.** `open(…, "a")` on Windows seeks to the end and writes in two steps, so two processes appending at once overwrite each other's line and `pedir()` returns True to both. It has nothing to do with the agent: 3640 of 40000 lines lost with two processes appending and no reader (0 with `FILE_APPEND_DATA`; 0 on Linux). In the mailbox stress with two requesters per mailbox: 7646 of 126269 before this turn existed, 4574 of 115307 now; with one requester per mailbox, none. It needs two requests to the same mailbox within about 100 µs (a root's mailbox has one window; `agente.pide` has the CLI, the wizard and every window). Not fixed.
- A requester frozen for more than `ESPERA_BUZON` between opening the mailbox and writing.

## «Actualizar» (section 8 of the spec)

The agent checks every `MIRAR_VERSION` (6 h) in a thread (`agente.hilo()`, `buscar_version()`, both indirection points; `_agente_falso` runs it inline and never finds one) with `update.check(cache=)`'s 24 h cache in `equipo.DIR/update.json`, says it ONCE, and `resumen()` carries `version`/`nueva`/`actualizando` so the tray offers «Actualizar a la vX».

`PIDE_BUSCAR_VERSION` («Buscar actualizaciones», tray, shown only while no newer version is known; greyed «Buscando actualizaciones…» while `Agente.buscando`) runs `agente.buscar_version_ya()` (indirection point: `update.check(force=True, cache=)`) in a thread via `Agente._buscar_ahora()`, one at a time, and pushes `version_mirada` back so the 6 h look does not repeat it. A newer one sets `nueva` and clears `nueva_avisada`, so `_mirar_version()` says it as always; «already latest» and failures (which keep what was known) go out as one `avisar()` carrying `update.veredicto()`.

`PIDE_ACTUALIZAR` launches ONE detached `agente.py actualizar`, which downloads the tag with `update.download()` to a temp dir (never a root), runs THAT tree's `prdrive-install.py --update-agente` with the agent's Python (`update.agent_command()`, `agente.ejecutar()`), copies its output to `agente.log` and removes the temp dir.

`install/agente.actualizar()` = `preparar()` beside, `parar_agente()`, `registrar()`, menu, `instalacion.json`, `actualizar_raices()` (`deploy.deploy_code()` on each OPEN host root; a locked one is left for its window), `podar()`, `arrancar()`. **`podar()` never deletes the runtime of `sys.executable`**: «Actualizar» runs on the old Python, and deleting half a live interpreter's stdlib kills it on its next import.

### «Actualizar a la vX» of one root (the agent's version, not the latest)

A connected root **in the list** whose program is older than the agent's (`update.is_newer(agent, its VERSION)`; no `VERSION` counts as older) gets «Actualizar a la v<agent>» in its tray submenu (`Agente._actualizable()`, `resumen()` per drive: `actualizable`, `actualizando`, `a_medias`), and one notification per drive version per agent process (`_avisar_actualizable()`). Never for an unlisted drive or one with changed code (nothing of it is touched before the yes), nor while the agent updates itself (that updates open host roots anyway). A drive older than `VERSION_MINIMA` in the list is offered too: the greyed «Actualízala para que la atienda» stays only for unlisted ones.

- `PIDE_ACTUALIZAR_UNIDAD` (tray, or `agente.py actualizar ID` to the mailbox) → `_pedir_actualizacion()`: refused with a notification while the root's window is open (the window offers its own update and its program is not swapped under it); otherwise `Conexion.actualizacion`. `_contrato()` stops serving it like a lock request (released after the pair in flight, motivo «actualizándose»), `_raices()` skips it, `_abrir()` refuses window and folder.
- `_actualizaciones()` launches ONE detached `agente.py actualizar-raiz <root>` once no pass of that root (ours or the inherited one) is alive and the lock is released, re-checking the window. That child downloads **the agent's own tag** (`update.source_tag(SCRIPT_DIR)`) to a temp dir, runs that tree's `prdrive-install.py --update <root>` with the agent's Python (`update.apply_command(…, python=)`), copies its output to `agente.log` and exits with the installer's code, or `agente.SIN_TOCAR` (4) when it never reached the root (no version, download/verification failed).
- **The fingerprint.** On the first request of a connection `Conexion.confiada` records whether the code on disk is the accepted one (`huella() == Unidad.codigo`, or `codigo` empty, or a host root). Success = rc 0 and the root's `VERSION` equals the agent's: then the new `huella()` is recorded **only if `confiada`**; otherwise `cambiada` and the question. The agent placed that code but does not vouch for what was beside it (a planted `json.py` must still be asked about).
- **Failure**: `SIN_TOCAR`, or a fingerprint still equal to the accepted one, keeps serving as before. Anything else leaves `Conexion.a_medias`: not served, not opened, mailbox not read (`_por_actualizar()`, like `vieja`), the tray shows «(por actualizar)» with only «Actualizar a la vX» active. A retry keeps the `confiada` of the first attempt. A drive unplugged mid-update is forgotten; on reconnect its fingerprint decides (changed → asked again).
